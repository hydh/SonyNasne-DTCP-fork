# 33. torne mobile の DTCP-IP 資格情報の供給機構 — PvrBgApp (DEWEY) の静的解析

docs/21 で torne mobile (iOS) の PvrBgApp フレームワークに Sony の DTCP-IP ミドルウェア「DEWEY」が同梱され、AKE (相互認証) がプロセス内で完結することを確認した。docs/32 では、正規 Sink の AKE には DTLA 署名のデバイス証明書 (88 バイト) と機器秘密鍵 (20 バイト) のペアが必要で、汎用 OS 向け視聴アプリの資格情報は「全端末共有の固定ペアをオンライン配布 (アプリ内蔵を含む)」か「要求ごとに個別発行」の 2 型に整理した。本書はその続きとして、**torne mobile が資格情報をどこから得ているか (供給機構)** を静的解析で追った記録である (2026-11-15 実施)。

**範囲の明示**: 本書の対象は供給機構の特定と記録のみで、**資格情報の値の抽出、候補バイト列の切り出し、暗号学的な照合 (署名検証・鍵一致確認) は行っていない**。解析が「次は素材そのものを取り出す段階」に到達した時点で止め、その到達点を §11・§12 に記録する。鍵や証明書の値、個体を特定する情報は本書に一切含めない。

**現在の到達点**: 資格情報は (1) アプリ (torneplus) から初期化時に渡されず、(2) キーチェーンにも、(3) 同梱ファイル (`initialContent.db` を含む) にも、(4) サーバ発行にも依らず、**PvrBgApp 内部の「DAL アイテムストア」から番号付きデータアイテム (証明書 = #9、組立て相手 = #13) として供給される**。アイテムストアの実データ供給層 (プロバイダ) は制御フロー平坦化で難読化された自己完結コードで、外部 API を一切呼ばない。分類としては docs/32 の「固定ペアのアプリ内蔵」型に最も整合するが、難読化内部の最終確定 (埋め込みデータの復号なのか導出なのか) は残件として残る (§11・§12)。`initialContent.db` はコンテンツカタログの初期データベースであり、資格情報とは無関係とコード参照から判定した (§10)。

## 1. 対象と方法

- 対象: docs/21 と同じ復号済み IPA (torne mobile v1.50) の `PvrBgApp` フレームワークバイナリ (arm64 Mach-O) と、本体 `torneplus`。実機 (nasne) への接触、アプリの実行、ネットワーク接続は一切行っていない。
- 方法: marnux 上で llvm-objdump / llvm-nm による逆アセンブルと radare2 の相互参照 (axt) を使い、公開鍵管理 API から DEWEY 内部へ呼び出し経路を静的に辿った。PvrBgApp は file offset = 仮想アドレス (__TEXT 基準 0)、torneplus は PIE (基準 0x100000000) として表記する。
- 本書で「事実」とするのは逆アセンブルで直接確認できたものだけとし、意味づけは「解釈」と明記する。

## 2. 初期化経路 — アプリから資格情報は渡されない (事実)

本体 torneplus から `PvrDtcpIpKeyManagerInitialize` への呼び出しは 1 箇所のみ (ラッパ関数 `0x1004274e8` 内の呼び出し `0x100427528`)。

PvrBgApp 側の Initialize 本体 (`0x12eb8`) の引数の扱いは次の通りで、**証明書や鍵がここで渡る余地はない**:

- 引数 1 (x0) は関数 `0xc568` へ渡され、**文字列として処理される**: 既存のグローバル文字列 (アドレス `0x3bd270`) と比較し、異なれば解放して strdup で差し替える (文字列の intern)。torneplus 側でも文字列オブジェクトを構築して渡し、呼び出し直後に解放している。
- 引数 2 (x1、非 NULL のとき) は関数 `0x8aec` へ渡され、**16 バイトがそのままグローバル (`0x3bd260`) へ複写される**。16 バイトの設定構造体 (ポインタ 2 個分) であり、証明書 88 バイト + 秘密鍵 20 バイトのペアを運ぶ大きさではない。
- その後の初期化は参照カウンタ (`0x3bd288`) とシングルトンポインタ (`0x3bd290`) の管理のみで、初回に生成ラッパ `0xa4f08`、続けて phase-2 ラッパ `0xa502c` (引数 1) を呼ぶ。

つまり資格情報の供給は Initialize の入力ではなく、**DEWEY 内部の後段で完結する**構造である。

## 3. KeyManager と DEWEY コアの初期化 (事実)

- 生成ラッパ `0xa4f08` はシングルトンの get-or-create で、実体は factory `0xa65b4`。factory は 48 バイトの KeyManager オブジェクトを確保し、サブオブジェクト (オフセット +0x10 / +0x18) を構築したうえで、コアオブジェクトの初期化関数 `0x1058ac` (参照カウンタ付きシングルトン、グローバル `0x3bdad8`) を呼ぶ。`0xa4f08` の後段は内部エラーコード (12000 台・1000 台) を分類コードへ変換する領域で、そこから参照される `__const` はジャンプテーブルでありデータではない。
- phase-2 (`0xa502c` → `0xa690c`、フラグ 1) は、コアへの 12 バイト記述子コマンド (転送関数 `0x105890`)、560 バイトのサブオブジェクト生成、200 バイトオブジェクトの生成ヘルパ `0x74c20`、解放ヘルパ `0x74cd0` など、KeyManager 内部の AKE 関連サブオブジェクトの構築が中心で、資格情報そのものの読み込みはこの段階では行われない。
- 破棄は `0xa500c` → `0xa67bc`。

## 4. 証明書オブジェクト SdiDevCert と設定関数 (事実)

DEWEY の AKE クラス群 (docs/21 で RTTI から棚卸し) のうち、デバイス証明書を表すのは `SdiDevCert` (RTTI 名文字列 "10SdiDevCert" は `0x35890f`、typeinfo 候補は `0x390c98`)。

その「証明書データ設定」関数 `0x8513c` (引数: オブジェクト, データ, 長さ) の実読結果:

- **長さは 88 (0x58) または 132 (0x84) のみ受理**し、それ以外はエラー 5 を返す。88 バイトは docs/32 で確認した DTLA デバイス証明書のサイズと一致する。
- 旧データを解放したうえで同長のバッファを確保して入力を複写し (長さは +0x10 に保持)、先頭 3 バイトのビットフィールドを +0x14〜+0x1a へ展開する (版・フラグ類のフィールド)。
- サブオブジェクトを 2 個 (各 16 バイト、生成ヘルパ `0x85518` / `0x87da4`) 構築して +0x20 / +0x28 に置く。
- **証明書のバイト 3〜7 (5 バイト) を +0x20 のサブオブジェクトへ、固定 1 バイト (`0x358ada`) との XOR で難読化して格納する** (格納 `0x85558` / 読出し `0x85598` / 比較 `0x855d8`)。5 バイトは DTCP のデバイス ID の長さであり、証明書内のデバイス ID 欄をメモリ上で難読化保持する実装と整合する (解釈)。この 5 バイト処理は隣接する `SdiDevID` 系の意味論とも一致する。
- +0x28 のサブオブジェクトは証明書バイト 8 以降から構築され、公開鍵の保持 (`SdiPubKey`) とみられる (解釈)。

重要なのは、**SdiDevCert 自身は読み込みを行わず、生の証明書バイト列を呼び出し側から受け取る**点である。供給源は設定関数の呼び出し側にある。

## 5. 証明書の供給元 — 設定関数の呼び出し元 2 件 (事実)

`0x8513c` の呼び出し元は 2 件のみで、どちらも「抽象インタフェース越しに得たバイト列」を渡す形である。

### 5.1 DAL アイテム経由 (関数 `0x71928`)

- 後述の DAL アイテムストア (§7) から **アイテム #9** を取得する (レコード上限 148 バイト)。
- レコードのヘッダを検査し (状態バイト +0xb が 0x1b ならエラー 1005、非ゼロならエラー 1)、正常なら長さ (+0xc) とペイロード (+0x10) を設定関数へ渡す。

### 5.2 AKE 側オブジェクト経由 (関数 `0x9c500` 内 `0x9c658`)

- オブジェクト (+0x98) の仮想関数 (vtable +0x78) でデータポインタと長さを取得し、定数 (`0x358ac0` に置かれた 32 ビット値) の分だけ先頭を読み飛ばして、DevCert オブジェクト (+0x78) へ設定する。続けて `0x853c8` 等で後処理を行う。
- データ提供オブジェクト (+0x98) の実体と、読み飛ばし定数の意味は未確定 (§12)。

どちらの経路でも、この層にファイル読み込み・キーチェーン・ネットワークへの直接アクセスは存在しない。

## 6. 資格情報の組み立て — アイテム #9 と #13 (事実)

関数 `0x71814` が資格情報の組み立てを行う:

- DAL から **アイテム #13** を、上限 2064 バイトのレコードで取得する。
- §5.1 の経路でローカルな SdiDevCert を構築する (アイテム #9 = 証明書)。
- 組み立て関数 `0xa2964` (引数: 出力オブジェクト, アイテム #13 のペイロード, 長さ, 構築済み DevCert へのポインタ) を呼ぶ。

すなわち DEWEY の資格情報は **「アイテム #9 (証明書) + アイテム #13 (最大約 2 KB のデータ)」の組み合わせ**で組み立てられる。アイテム #13 が秘密鍵を含む鍵データ塊かどうか、その形式は未確定 (§12)。秘密鍵単体は 20 バイトであり、#13 の上限 (約 2 KB) はそれよりかなり大きい。

## 7. DAL アイテムストア (事実)

アイテム取得の実装クラスは RTTI から **`DalTrsDeviceImpl`** (型名 "16DalTrsDeviceImpl") と同定した。DAL は DEWEY のデバイス抽象層で、取得メソッド群は `0x704d0`〜`0x7219c` に並び、各メソッドがアイテム ID を即値で指定する。観測した ID は 8〜42 と 52 で、少なくとも数十件の番号付きデータアイテムが存在する (証明書 #9、組み立て相手 #13 を含む)。

取得の呼び出し鎖:

1. 取得ヘルパ `0x70388`: 記述子 {アイテム ID, 上限長} を組み、文脈オブジェクトの内部オブジェクト (+0x8) を転送関数 `0x105890` へ渡す。
2. `0x105890`: 記述子の先頭ワード (= アイテム ID) を取り、ディスパッチャ `0xf9fd0` へ尾呼出しする。
3. `0xf9fd0`: ID 1〜31 のジャンプテーブルディスパッチ。ID 1, 5, 6, 19, 22 は専用処理を持ち、**ID 9 を含む残りは汎用ハンドラ `0xfa87c`** へ落ちる (ID 32 以上も同汎用ハンドラ)。
4. `0xfa87c`: 文脈 (+0x8) をロック (`0x11280c`) し、文脈の +0x128 に保持された **プロバイダオブジェクト**を相手に `0x1b5090` を呼び、解錠する (`0x112834`)。

レコード形式は取得側の読み方から確定している: 先頭 16 バイトがヘッダ (状態バイト +0xb、長さ +0xc)、ペイロードは +0x10 から始まる。

## 8. プロバイダ実装 (`0x1b5090`) の難読化 (事実)

アイテムの実データを返すプロバイダ関数 `0x1b5090` は、PvrBgApp の他の部分とは異なる **難読化コード**である:

- **制御フロー平坦化**: 状態変数による大規模な状態機械になっており、ジャンプテーブル (`0x1c20b0`) の状態インデックス範囲は約 0x29a (約 660 状態)。
- **定数の難読化**: グローバル (`0x35f3ec`) のワードとの XOR や、マジック定数による乗算・シフトで値を組み立てる。
- 範囲 `0x1b5090`〜`0x1c6000` の呼び出し調査では、**インポートスタブ領域 (0x352xxx) への呼び出しは 0 件**だった。呼び出し先は内部関数、ログ関数 (`0x112888`)、ユーティリティ領域 (0x113xxx) のみである。

すなわちこの層はファイル・キーチェーン・ネットワーク等の外部 API を直接使わず、**アイテムデータを PvrBgApp バイナリ内部で自己完結的に生成/復元する**構造である。その内部で埋め込みデータを復号しているのか、アルゴリズム的に導出しているのかは、平坦化のため本書の範囲では確定できない (§12)。

## 9. キーチェーンは資格情報経路では使われていない (確認範囲の事実)

PvrBgApp がインポートする SecItem 系 (SecItemAdd / SecItemCopyMatching / SecItemDelete / SecItemUpdate) の呼び出し元 census:

- 汎用 CRUD ヘルパ `0x8788` (CopyMatching / Add / Delete を使用)。その C 呼び出し元は PS Vita 書き出しのメッセージ処理 `0x94b4` のみ。
- 関数 `0x61d54` の系統 (CopyMatching を使用)。
- ObjC の `NPLSKeychainWrapper` (PSN 系ライブラリのラッパ。Add / Update 等を使用)。

**DEWEY の初期化・証明書読み込み・資格情報組み立ての経路から SecItem 系へ到達する呼び出しは、確認した範囲に存在しない。** 資格情報の保存先がキーチェーンである形跡はない。

## 10. `initialContent.db` の役割 (事実と判定)

docs/21 で「高エントロピーで平文 SQLite ではない」と観測した同梱ファイルについて:

- 文字列 "initialContent.db" は **torneplus のみに存在**し、PvrBgApp / AVBase には無い。
- torneplus 内のコード参照は 1 箇所のみ (`0x100381d94`)。その関数は "PvrContent.db" も併せて扱い、ファイルの存在確認・サイズ取得・読み込みを行う。近傍の文字列は `### createDatabase failed`、`createServiceExtTable`、`createRemoteRecordedContentsTable`、`createRemoteScheduledContentsTable`、`createNasneDeviceTable` 等、データベース初期化系である。
- ファイル実体は 366,592 バイト、エントロピー 7.981 bits/byte、SQLite ヘッダを持たない (DB 層の格納形式の詳細 — 暗号化か独自形式か — は未確定)。

**判定: `initialContent.db` は、アプリ内コンテンツカタログ (録画・予約・nasne 機器の台帳) の初期 (シード) データベースであり、DTCP 資格情報の格納庫ではない。** DEWEY 側からの参照が一切ないことが根拠である。

## 11. 供給機構の分類

| 候補 | 判定 | 根拠 |
|---|---|---|
| 埋め込み固定 (バイナリ内蔵) | **最も整合** (難読化内部の最終確定は残件) | アプリから渡されず (§2)、キーチェーン (§9)・同梱ファイル (§10)・ネットワーク (下記) のいずれの外部供給も経路に無く、プロバイダがバイナリ内部で自己完結する (§8)。docs/32 の整理では「全端末共有の固定ペアをアプリ内蔵で配布」型に相当する |
| 同梱ファイル格納 | 該当なし | 資格情報用のファイル読み込みが経路に無い。`initialContent.db` はコンテンツ DB 用 (§10) |
| サーバ発行 | 該当なし (確認範囲) | 初期化・読み込み・組み立ての経路にネットワーク要求が無い |
| キーチェーン生成・保存 | 該当なし (確認範囲) | §9 の census で DEWEY 経路からの到達が無い |
| 端末上生成・導出 | 排除できない | プロバイダ内部が難読化のため (§8)。ただし観測範囲では端末固有の入力がプロバイダへ渡る形跡は無く、Initialize の入力も文字列 + 16 バイト設定のみ (§2) |

## 12. 未確定点と残工程

- **最終確定にはプロバイダ `0x1b5090` のアイテム #9 / #13 ケースの解読 (平坦化の解除) が必要**である。ここが「次は素材そのものの所在をバイナリ内で特定する段階」に当たり、本書の範囲 (機構の特定と記録) はここまでとする。
- アイテム #13 の意味論 (秘密鍵を含むか、鍵データ塊としての形式)。
- AKE 側の第 2 供給路 (§5.2) のデータ提供オブジェクト (+0x98) の実体と、ヘッダ読み飛ばし定数の意味。
- 関数 `0x61d54` 系統 (SecItemCopyMatching の呼び出し元) の同定。DEWEY 文脈でないことの完全な確定までは至っていない。
- torneplus 側 Initialize ラッパ (`0x1004274e8`) の呼び出し元 (間接呼び出しのため未同定) と、引数の文字列・16 バイト構造体の意味。
- 資格情報の組み立て (`0x71814`) の呼び出し元 (AKE 開始時のどの経路で呼ばれるか)。
- AVBase 側 CDtcpIp スタック (docs/21 で存在を確認した第 2 の DTCP 系統) の資格情報源は未調査で、本書の結論は PvrBgApp / DEWEY 系統に限る。
