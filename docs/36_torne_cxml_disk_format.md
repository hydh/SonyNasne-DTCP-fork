# torne mobile の DTCP-IP 資格情報の供給機構 第4段 — 資産ファイル `PvrAssetData.cxml` のディスク形式

docs/35 で未確定として残した「ディスク形式の変換鍵の出所」を詰める。対象は torneplus 本体 (書き手) と PvrBgApp (読み手・書き手) の保護コンテナ形式そのもので、静的実読 + Unicorn エミュレーションによる往復検証 + 純 Python 参照実装による相互検証を行った。実ファイル (本人の端末・バックアップ由来) の復号は本段の範囲外とし、合成データと、別途提供された実コンテナ由来の同形式ファイルへの鍵候補の適用結果のみを記録する。鍵・素材の値そのものは本書に記録しない (所在・導出方法・識別子のみ)。

## 1. 結論サマリ

- ディスク形式の変換は **AES-128** で確定した。コンテナは `E_K(rand16) || CBC-Enc_K(SHA-256(ペイロード) || ペイロード, IV=rand16)`。末尾の端数ブロック (<16 バイト) はパディングせず、直前の完全ブロックの暗号文を鍵ストリームとして XOR する CFB 的な尾部処理を行う。
- 変換鍵 K は固定値ではなく、アプリが保持する 16 バイト値 **G** から導出される (導出関数 ctxprep、§4)。G は **インストールインスタンス固有**で、`G = SHA-256(mobileId の先頭 48 バイト || キーチェーン内 UUID 16 バイト) の先頭 16 バイト`。
- キーチェーン項目はランダム UUID の 16 バイトそのもので、識別子はサービス `com.playstation.tornemobile.storage` / アカウント `torne moible` (バイナリ内の綴りのまま)、属性は AfterFirstUnlockThisDeviceOnly (端末束縛)。
- 書き手 (torneplus の保存関数と PvrBgApp 内の同型保存関数) と読み手 (PvrBgApp 資産ローダ) の仕様は完全に閉じており、元コード同士のエミュレーション往復 18/18 と、参照復号スクリプト (純 Python) との相互往復で検証した。
- 実コンテナ由来の同形式ファイル (Manage 配下の保存データ等) は、G の既定状態から導かれる鍵候補では復号できなかった。これは形式の否定ではなく、実ファイルがインスタンス固有の G で書かれていることと整合する (§7)。
- mobileId は **GAE バックエンドが発行する** (`op=opGetMobileId`、§8)。アプリの永続領域 (NSUserDefaults・Documents) に平文では存在しない。

## 2. コンテナ形式 (バイト配置)

書き手は torneplus の保存関数 `0x100427034`、読み手は PvrBgApp の資産ローダ `0xc5e0`。PvrBgApp 内にも同型の保存関数 (0xc8e8 付近) があり、両者は同一形式を読み書きする。

| 領域 | 長さ | 内容 |
|---|---|---|
| [0, 16) | 16 | 書き込みごとの乱数 (C ライブラリ `rand()` の下位 1 バイト × 16 回) を、鍵 K で単一ブロック暗号化したもの |
| [16, 48) | 32 | SHA-256(ペイロード) を含む平文ブロック列の CBC 暗号文 (下記) |
| [48, 全長) | ペイロード長 | ペイロードの CBC 暗号文 (同上) |

全長 = ペイロード長 + 48。組み立て順序は「乱数ヘッダ配置 → ペイロードを +0x30 へ複写 → SHA-256 を +0x10 へ格納 → 鍵導出 → [16, 全長) を CBC 暗号化 → [0,16) を単一ブロック暗号化」。書き込み後に鍵バッファは乱数で消去される。ファイル書き込みは `.tmp` への新規書き込み → 既存を `.bak` へ改名 → `.tmp` を本名へ改名 → `.bak` 削除、のローテーション (docs/35 で同定済みの手順と一致)。読み手は `.bak` からの復旧分岐も持つ。

## 3. 変換の詳細

対象関数は torneplus の `0x100488224` (CBC 本体) と `0x10048815c` (単一ブロック)。PvrBgApp 側の対応関数 (`0x35158c` / `0x3514c4` 等) も同型であることを実読で確認した。

- アルゴリズム: AES-128。単一ブロック関数の方向は独立実装 (pycryptodome) と標準テストベクタ (鍵 000102…0f、ブロック 00112233…ff → 69c4e0d8…4c55a) で照合し、`0x10048815c` = 暗号化、`0x1004881c0` = 復号と確定した。鍵スケジュールとブロック関数の組も両方向分を同定した。
- CBC 本体 `(dst, src, len, key, ivptr)`: フィードバック初期値は ivptr の指す 16 バイト。完全ブロックは通常の CBC。**最終端数ブロックは、最後の完全ブロックの暗号文を鍵で暗号化した鍵ストリームの先頭と XOR する (フィードバックなし)**。パディングは一切ないため、長さは 16 の倍数でなくてよい。
- コンテナへの適用: CBC の初期フィードバックはファイル [0,16) の平文 (乱数そのもの)。すなわち復号時は、先に [0,16) を単一ブロック復号して乱数を復元し、それを IV として [16, 全長) を CBC 復号する。復号後に SHA-256(ペイロード) と [16,48) の復号結果を照合し、一致すればペイロードを DAL アイテム 1 として投入する (docs/34 の投入経路に接続)。
- 乱数ヘッダの役割: IV の秘匿とファイルごとのランダム化を兼ねる。乱数自体は `rand()` 由来で予測可能性の議論はあるが、本形式の完全性は SHA-256 照合が担う。

## 4. 鍵導出 (ctxprep)

導出関数は torneplus `0x100429ef0`、PvrBgApp 側は `0x12118` で、アルゴリズムはバイト単位で同一 (両者で同じ G から同じ K が出ることをエミュレーションで確認)。

1. G (16 バイト) をゲッタ経由で取得する。
2. バイナリ内埋め込みブロブ 2 件 (torneplus では VA `0x1008beecf` / `0x1008bef09`、PvrBgApp では `0x354de8` / `0x354e22`、内容は両バイナリで同一) をデコーダ `0x100429e50` で各 16 バイトに展開する。デコーダは、散在する float32/float64 フィールドの `fcvtzs` 変換下位バイトと直接バイトを決められた順序で拾う難読化配置である (フィールド対応表は参照スクリプト内に再現した)。
3. `B1 = AES128-Enc_A(B)`、`T = AES128-Dec_G(B1)`、`K = T XOR B1`。
4. なお導出関数は最後に `AES128-Enc_G(K)` を計算して破棄する (形式には影響しない)。

ブロブの値・導出される K の値は本書に記録しない。参照スクリプトは実行時にバイナリからブロブを復元して導出する。

## 5. G の出所 (変換鍵の最終的な起源)

- torneplus 側の G はグローバル変数に保持され、書き手は計算セッタ 1 本のみ。その唯一の呼出し元は、キーマネージャ (シングルトン) の mobileId 文字列 (オブジェクト +0x2c8) を取り、長さ 0 でなければそのデータポインタを渡す関数である。
- 計算セッタの内容: `G = SHA-256(mobileId データの先頭 48 バイト || キーチェーン値 16 バイト) の先頭 16 バイト`。2 回目の SHA-256 入力はキーチェーン項目の値そのもの。
- キーチェーン項目: クラス = 一般パスワード、サービス = `com.playstation.tornemobile.storage`、アカウント = `torne moible` (綴りはバイナリのまま)、アクセシビリティ = AfterFirstUnlockThisDeviceOnly。値は `NSUUID` のランダム 16 バイトで、初回利用時に生成して登録し、以後は検索して再利用する (型・長さが合わない既存項目は削除して作り直す)。
- PvrBgApp 側の G は、公開 API `PvrDtcpIpKeyManagerInitialize` の第 2 引数としてアプリ (torneplus) から渡され、生セッタでグローバルへ複写される (呼出し元はこの 1 箇所のみ)。すなわち両バイナリの G は同一インスタンス値で揃う。
- 帰結: 実ファイルの復号には、そのファイルが書かれた **同一インストールインスタンス** の (a) mobileId と (b) キーチェーン UUID 16 バイトが要る。UUID は ThisDeviceOnly のため、iPhone バックアップのキーチェーンは端末固有鍵で包まれており、**他端末・PC 上では取り出せない** (同一端末への復元か、端末上での抽出が必要)。

## 6. 検証

- 単一ブロック方向: 標準テストベクタで独立実装と一致 (§3)。
- 元コード同士の往復: torneplus 暗号化経路 → PvrBgApp 復号経路を Unicorn で実行し、鍵 3 種 × ペイロード長 0 / 1 / 16 / 37 / 1000 / 2048 バイトの 18 ケース全てで、乱数復元・ペイロード一致・SHA-256 照合が成立した。端数長・空ペイロードを含む。
- 参照復号スクリプト (純 Python、pycryptodome 使用): ブロブ展開と鍵導出を再実装し、エミュレーション導出の K と 2 種の G で一致。さらに「元コード (エミュレーション) で暗号化したコンテナを参照スクリプトで復号する」相互往復でも SHA-256 照合とペイロード一致を確認した。スクリプトは作業領域 `2026-11-15-torne-diskfmt/cxml_decrypt.py` (秘密値は保持せず、実行時にバイナリから導出する)。
- 書き手・読み手の対称性: torneplus 保存関数、PvrBgApp 保存関数、PvrBgApp ローダの 3 者を実読し、同一形式であることを確認した。

## 7. 実サンプルへの適用結果

提供された実コンテナ 2 件 (LiveContainer 実行時のものと、実機バックアップから抽出されたもの) に含まれる同形式ファイル、および IPA 同梱のリソースファイルに対し、G の既定状態 2 種 (PvrBgApp グローバル初期値 = 全ゼロ、torneplus グローバル初期バイト列) から導かれる鍵を適用した。

- 対象: `Documents/Manage/PvrSaveData.cxml` (LC 版 10,048 バイト / 実機版 10,224 バイト)、同 `PvrGameConfig.cxml` (1,072 バイト)、IPA 同梱 `PvrTheme.cxml`。
- 結果: **全て SHA-256 照合不一致** (誤一致の確率は無視できる水準のため、この結果は積極的な棄却である)。
- 解釈: これらのファイルは既定状態の G では書かれていない。実機版はアプリの実利用形跡 (コンテンツ DB の成長等) があり、mobileId 取得とキーチェーン項目生成を経たインスタンス G で書かれたとみるのが整合的である。LC 版については、起動画面で停止した実行でも保存データが存在することから、Manage 配下の書き手が本形式の鍵経路とは別の経路を使う可能性が残る (書き手関数の同定には至っていない)。いずれにせよ本結果は §2–§5 の資産形式の仕様 (書き手・読み手の実読と往復検証で確定) を否定しない。
- 付随確認: 実機コンテナにも `Documents/PvrAssetData.cxml` は存在しなかった (Documents 直下は Manage/ と LICENCEDIR/ のみ)。視聴ライセンス取得まで至っていない端末では資産ファイル自体が生成されないことと整合する。
- なお Manage 配下の `.db` ファイル (PvrContent.db / PvrOperationLog.db) は本形式ではなく、ページ単位の暗号化が施された SQLite 系の別形式だった (先頭 26 バイトが全ファイル共通の固定ヘッダで、平文 SQLite ではない)。本段では形式の同定までとし、鍵経路は追っていない。

## 8. mobileId の所在

本段の追加調査項目として、mobileId の発生源・永続化先・deviceid との関係を追った。

- 発生源: **GAE バックエンドからの発行**。torneplus 内の GAE クライアントタスクが要求 `op=opGetMobileId` を組み立てる。パラメータは `deviceid`、生年 (`birthyear`)、アプリ識別トークン等で、応答はキー値リスト形式で、`result` / `mobileid` / `supportid` の各キーをパースして保持する (応答パーサを 2 実装分実読した)。削除要求 `op=opDeleteMobileId` も存在する。
- 保持先: キーマネージャオブジェクトの文字列メンバ (+0x2c8)。取得はポーリング型のゲッタで、起動後の非同期処理で設定されるまで待つ設計。
- deviceid との関係: **別物**。deviceid は要求側が送るアプリ側の識別子で、キー確認要求 (docs/35) では int64 として送られる管理値。mobileId はそれに対してサーバが発行する文字列で、mobileIdAuth 等の認証パラメータや、本形式の鍵導出 (§5) に使われる。
- 永続化先として確認できなかったもの: NSUserDefaults (実機コンテナの Preferences は `SubversionRevisionKey` と `SKPurchaseIntentUpdatesLastChecked` の 2 キーのみで mobileId は無い)、Documents 配下の平文ファイル (該当なし)。
- 残る候補: 起動ごとに deviceid から再取得する運用か、暗号化された保存領域 (PvrSaveData.cxml のペイロード内、または暗号化 DB 内) へのキャッシュかは、静的解析の範囲では確定できなかった。本人のキーチェーン書き出しの名前レベル確認でも torne 関連項目は見つかっておらず、少なくとも当該端末では DTCP キーマネージャ系の初期化 (ライセンス取得) が行われていないことと整合する。
- 本人が自分のバックアップから取り出す場合の所在として報告できるのは: mobileId はバックアップ内の平文ファイルには存在しない (上記)。鍵導出に必要なもう一方の要素であるキーチェーン UUID は §5 の識別子で端末上に存在しうるが、ThisDeviceOnly のためバックアップ経由の外部取り出しはできない。

## 9. 実ファイル入手後に残る手順

実物の `PvrAssetData.cxml` が得られた場合の復号手順は次の通りで、不足しているのはデータ側の 2 要素のみである。

1. 同一インストールインスタンスの mobileId (先頭 48 バイトを使用) と、キーチェーン UUID 16 バイト (§5 の識別子) を用意する。
2. `G = SHA-256(mobileId[0:48] || UUID) の先頭 16 バイト` を計算し、参照スクリプトで K を導出する。
3. コンテナを復号し、SHA-256 照合が一致すればペイロード (TLV) が得られる。以後は docs/34–35 の DAL 投入経路の解析に接続する。

UUID が端末束縛である点が実務上の関門で、バックアップからは (a) があっても (b) が得られない。同一端末上での抽出手段 (本人の脱獄済み検証端末の利用可否を含む) は本段の範囲外とする。
