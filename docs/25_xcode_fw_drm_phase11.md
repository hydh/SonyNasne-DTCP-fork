# XCode ファームウェア DRM モジュール解析 第11段 — SCRAMBLER ハンドラの同定と実読

対象: 第2 FW (`fw_second_plain.bin`、ロードベース `0xB00000`)。第10段 ([docs/24](24_xcode_fw_drm_phase10.md)) で縮小した SCRAMBLER ハンドラ候補 (a) 登録ハンドラ・(b) proc6 チャネルハンドラ・(c) 実行時生成タスク・(d) `0xC6B118` を SCRAMBLER への近さ順に実読した。

**結論 (本段の到達点)**:

- **SCRAMBLER (mhcmd 37) のハンドラは `0xBF894C` であると同定した**。到達経路は、全コア共通のメールボックスパケットハンドラ `0xC74BBC` (proc6 ではチャネル 8 に登録) の第2経路 (直接 FunctionNumber 振り分け) で、FN=37 の分岐から Input ポインタ (= `cmd2_stream_scrambler` 構造体) を引数に呼ばれる。呼出し元はこの 1 箇所のみ (xref 実測)。
- ハンドラ本体を全行実読した。処理は「要求の検証 → CW/IV の鍵ストア投入 (必要な場合) → DMA/スクランブラ記述子の構築 → 実行側への投入 (`0xC5C344`)」であり、**ARC コード内で control_words を暗号学的に変換・展開する処理は無い** (実読範囲での確定)。
- **鍵ストアスロットインタフェースを同定した**: 共有域 `[0xAFE004] + 0x1824/+0x1828/+0x182C` (データ 2 ワード + index ワード、index は 0x00–0x7F の 128 スロット、bit31 が消費側ハンドシェイク) を介し、CW の先頭バイトをスロット番号として CW バイト列そのものを 8 バイト単位で投入する (`0xBCE950` / `0xBCED1C`)。記述子側に載るのはスロット番号のバイト列であり、実効鍵への解決は実行側 (HW または受信プロセッサ) がスロット経由で行う構造である。
- 候補 (d) `0xC6B118` はデバッグコンソールの行入力ハンドラであり、mhcmd ディスパッチも鍵処理も含まない (全行実読による積極的な棄却)。候補 (c) の実行時生成タスクは生成サイトの census を完了し、ID 12–15 の生成元を同定した (いずれも映像系/要求処理系で、SCRAMBLER の受け口は本ハンドラの同定により不要となった)。
- (a)/(b) 境界 (トークンが ARC コードで加工されるか、そのまま渡るか) については §5 に判定を書く。SCRAMBLER 経路については (b) 寄り (ARC 側変換なし・スロット間接参照) が実読で確定したが、鍵ストアスロットの消費側と SECUREDTS (録画保存) 経路は本段の範囲外で未確定のまま残る。

## 1. 手法と素材

- 手法は第9段の M1〜M6 ([docs/22](22_xcode_fw_drm_phase9.md) §1.2) を踏襲。Ghidra の関数境界が届かない孤児域は未解析インポート側プロジェクトで線形逆アセンブル (DisRange) した。
- 一次資料として GPL ソースの `mipshost.h` を併用し、`cmd2_stream_scrambler` 構造体レイアウト・scramble_flags (SF)・scramble_mode (SM) の定義を照合した (値は §3.2)。
- 作業素材は開発側の作業領域 `2026-11-13-fw-drm/phase11/` (解析プロジェクト 2 本、スクリプト、ログ dump11a–g / gap_* / scan_afeb6c)。本書のアドレスは全てロードベース `0xB00000` の仮想アドレス。

## 2. 入口 1: proc6 チャネルハンドラ 3 本

第10段 §3.10 の登録表: proc6 メインは (4, `0xC7609C`)、(8, `0xC74BBC`)、(6, `0xC75294`) を登録する。3 本とも全行実読した。

### 2.1 `0xC7609C` (チャネル 4、proc6) — 記述子状態の保守ハンドラ

本体 `0xC7609C`–`0xC761EB`。補助レジスタ (0x101=0、0x100=0、0x102=0x200000 = proc6 のタイマ周期) を設定し、通信記述子連結リスト (`[0xAFFD04]` 起点) を走査する。条件 (記述子 +0x5C bit24 クリア、+0x64 bit5 セット、+0x60 bit 0x400000 クリア、+0x11544 bit0 クリア、+0x44 bit 0x10000 セット) を満たす記述子について、送信スピンフラグ `[0xAFEB08]` の下で `[desc + 0x1E110]` の bit0 を立て、+0x44 bit28 がクリアならカウンタ `[0xD8C02C]` を増やして `0xC16D98 (desc + 0x55C)` を呼び、bit0 を戻す。FunctionNumber の振り分けも SCRAMBLER 相当の処理も含まない。

### 2.2 `0xC75294` (チャネル 6、proc6 と proc4) と実体 `0xC7488C`

本体 `0xC75294`–`0xC75383` はメールボックスポーリングの薄い殻で、共有パケット域 (`[0xAFE004]` 基準、コア別テーブル `0xAFE7FC + idx*0x18` の +0x260/+0x268/+0x270) の語を検査し、条件成立時に実体 `0xC7488C` を呼ぶ (自己索引 4 の場合は別途 `0xB90AB0` も呼ぶ)。

`0xC7488C` はオブジェクト経由受信の処理本体 (第2のオブジェクトスロット `[0xAFF938]` 用) で、共有語 `[base+0xC34]` bit1 のスピン待ちの後、`[base+0xC58]` bit1 が立っていればオブジェクト (`[[0xAFF938]+0x1C]`) の登録コールバック `[obj+0x2C]` を `(0, [obj+0x24])` (フラグ bit1 時は第2引数に 0x80000000 を OR) で呼び、`0xC5A2B4` による変換、スピンフラグ `[0xAFEB08]` 下での後処理、プール `[0xAFEB68]` / `[0xAFF93C]` への返却を行う。FunctionNumber の振り分けは無く、呼び出すのはオブジェクトごとに登録されたコールバックである。

### 2.3 `0xC74BBC` (チャネル 8、全コア共通。proc3 ではチャネル 7 にも) — 中央メールボックスハンドラ

本体 `0xC74BBC`–`0xC75293`。自己の通信記述子 (基底 `0xAFE000 + idx*0xF4`) の +0x0C…+0xF8 をスタックへ退避し、`0xC754E4` (引数なし。内部に第10段で同定したリングキュー投入側のスイッチ `0xC75Dxx` を含む) を呼んだ後、2 つの受信経路を処理する。

**第1経路 (オブジェクト経由)**: メールボックス状態語を記述子 +0xC0 (モード 1) / +0xEC (モード 2) のマスクで検査する。エラー記録スロット (0x520/0x100520 または 0x528/0x100528) へ `{0x0B57AC1E, PCL}` を書く臨界区間の内側で、オブジェクト `obj = [desc+0xF4]` (モード 1) または `[desc+0xF8]` (モード 2) を取り、パケット `[obj+0x24]` をメールボックススロット値と照合する。`0xC5A2B4 (objptr, obj)` で変換し、スロット群を更新する。振り分けは:

- `[obj+0x2C] == 0` または `[obj+0x10]` bit0 セット → パケットを `0xC2C76C` で解放するだけ (FN 12/15 の場合は追加の語を読む)。
- それ以外 → エラー記録呼出し `0xC8B348 (0xA0, obj)` の後、**オブジェクト登録コールバック `[obj+0x2C]` を呼ぶ**。引数は `(flag, arg)` で、arg は「セル `0xAFEB6C` == 1 かつパケットの FunctionNumber == 12 の場合のみパケット全体、それ以外は `[packet+0x14]` (Input ポインタ)」。コールバックが 0 を返せばパケットを `0xC2C76C` で解放し、全体結果が 0 ならオブジェクトをプール `[0xAFEB68]` へ `0xC2C41C` で返却する。

**第2経路 (直接 FunctionNumber 振り分け)** ← SCRAMBLER の到達経路: 第2のメールボックス対 (マスクは記述子 +0xBC → モード 1、+0xE8 → モード 2) からパケットポインタを得る。

- セル `0xAFEB6C` == 1 の場合 → 全パケットを `0xC325FC (packet, mode, saved)` が処理する (§2.5)。
- それ以外の場合 → `[packet+0xC]` (FunctionNumber) で振り分ける:
  - 13 (OUTPUT_DONE) → `0xC464B8 ([packet+0x14])`
  - 31 (CMD2_OUTPUT_PTR_DONE) → `0xC46F68 ([packet+0x14])`
  - **37 (CMD2_SCRAMBLER) → `0xBF894C ([packet+0x14])`** (§3)
  - その他 → 状態 `[packet+0x10] = 2` (CMD_FAILED)
- ハンドラの戻り値は状態へ `(戻り値 != 0) + 1` と変換され (0 → CMD_OK=1、非 0 → CMD_FAILED=2)、`0xC43658 (FunctionNumber, packet, mode)` でパケットを返却する。

`0xC464B8` / `0xC46F68` / `0xC43658` / `0xC2C76C` / `0xC5A2B4` は本段ではダンプまでで個別実読はしていない (未読として §11 に残す)。

### 2.4 セル `0xAFEB6C` の census (第2経路の分岐条件)

`0xAFEB6C` は通信層の変種切替フラグで、第2経路の振り分け方式と、パケットオブジェクト生成時の Input ポインタ 8 バイト整列 (`0xBF6D7C` が実読で確認) を切り替える。ScalarScan (M6) で第2 FW イメージ全域を走査した結果、**参照 38 件は全て読み出し (ld) であり、絶対参照・解決済み基底+オフセット参照のいずれでも書込み (st) は存在しない**。読み手には `0xC74BBC`、`0xBF6D7C` のほか `0xC4EB00` (多数)、`0xC3EFE8`、`0xBDCBD0`、`0xBDD698`、`0xC6305C`、孤児域 3 件が含まれる。したがってこのフラグの書込み主体は第2 FW 内には無く、ホスト側 (主 FW / ドライバ) または一括初期化によるものとみられる (解釈)。proc6 上で実行時に 0 であることは静的には確定できないが、§2.5 の通りフラグ=1 の経路は SCRAMBLER を処理できない構造であり、SCRAMBLER が実際に proc6 で動作する以上、実働状態では 0 側であることと整合する (解釈)。

### 2.5 `0xC325FC` (フラグ=1 時の代替経路)

本体 `0xC325FC`–`0xC32767`。パケットの FunctionNumber 欄 `[packet+0xC]` を共有セル `[0xAFE004 + 0xA020]` の値で上書きし、13 (OUTPUT_DONE) / 31 (CMD2_OUTPUT_PTR_DONE) 以外は致命的エラー (エラー記録 + `0xB04900` + 無限ループ) とする。13 では 0x28 バイト、31 では 0x13C バイトの作業オブジェクトを `0xBF7D48` で確保し、`0xBF7B68` で包んで `0xC5CB48 (0, obj, [obj+0x48], 0xC49748)` へ転送する、完了系パケットの遅延処理経路である。**FN=37 はこの経路では処理されない** (上書き後の値が 13/31 でなければ致命的エラー)。

## 3. SCRAMBLER ハンドラ `0xBF894C` の実読

本体は Ghidra 上で 3 断片 ([0xBF894C–0xBF8D93]、[0xBF9030–0xBF90A3]、[0xBF9114–0xBF9D4B]) に分かれ、間の 2 域 (ジャンプ表 #1 の分岐先コード 0xBF8E00–0xBF902F、ジャンプ表 #2 のデータ 0xBF90A4–0xBF9113) は線形逆アセンブルで補って全行を読んだ。呼出し元は `0xC74BBC` 内の 1 箇所 (0xC75208) のみ。

### 3.1 入口処理と要求のステージング

- 引数 r0 = Input ポインタ = `cmd2_stream_scrambler` 構造体へのポインタ。
- 静的データ `0xCD6BEC` から 6 ワードをスタックへ複写する (用途は未確定)。
- `[req+0x00]` (stream_handle の下位ワード) を保存し、**要求全体 0xBC バイトを `0xC43DB4 (handle + 0x7F4, req, 0xBC)` でストリーム状態ブロック (handle の指す先) の +0x7F4 へそのまま複写する**。control_words (+0x34) を含む逐語コピーである。
- scramble_mode (+0x1C) の先行振り分け: 9 (IVDR_ENCRYPT) / 10 (IVDR_DECRYPT) → 専用ヘルパ `0xBFA258 (req)`、12 (AACS_BLOCK_DECRYPT) / 13 (AACS_BLOCK_ENCRYPT) → 専用ヘルパ `0xBF9D4C (req)`。いずれも戻り値がそのまま本ハンドラの戻り値になる (両ヘルパは本段では未読、§11)。

### 3.3 検証とエラーコード

戻り値は 0 = 成功、1 = 実行時失敗、4 = 引数不正。エラー総数カウンタ `[0xD8C068]`、成功カウンタ `[0xD8C078]`、詳細コードセル `[0xD8C06C]` を持つ。詳細コード:

| コード | 条件 |
|---|---|
| 1 | ストリーム文脈 (作業オブジェクト) の取得失敗 |
| 2 | numOfLine ≥ 0x800 |
| 3 | モード 0 で directBytesPerLine = 0、またはモード ≠ 0 で scrambledBytesPerLine = 0 |
| 4 | AES 系モードで scrambledBytesPerLine が 16 の倍数でない |
| 5 | sourcePitch と destPitch の片方だけが 0 |
| 6 | SF bit1 (RESET_IV_PER_LINE) が立っている (単発経路) |
| 7 | モード 0 で scrambledBytesPerLine ≠ 0 |
| 8 | モード ≠ 0 で directBytesPerLine = 0 |
| 9 | numOfLine = 1 の経路で direct 部 ≥ 0x10000 かつ scrambled 部 < 0x10000 |
| 0xA | numOfLine > 1 の経路で同条件 (閾値 0x1000) |
| 0xB | 投入 `0xC5C344` の失敗 (共通経路) |
| 0xC | residue 経路で numOfTsPid = 0 |
| 0xD | 投入 `0xC5C344` の失敗 (residue 経路) |
| 0xE | TDES 系モードで scrambledBytesPerLine が 8 の倍数でない |

検証後、モード集合で 3 経路に分かれる: residue 系 {18, 19, 20, 21, 26, 27} は §3.6.1 の専用経路 (先に `0xBF8AE0` のセットアップ)、TDES 系 {14–17, 22–25} とその他は整列検証の後で共通部へ合流する。

### 3.4 CW/IV の選択と鍵ストア投入 (ジャンプ表 #1)

共通部 (0xBF8CC0) で、記述子へ載せるバイトを選ぶ:

- IV バイト: SF bit6 (IV_AS_INDEX) がクリアなら `[req+0x4C]` (IV_seed[0])、セットなら状態ブロックの語 `[handle + 0x8B8]`。
- CW バイト: SF bit5 (CW_AS_INDEX) がクリアなら `[req+0x34]` (control_words[0])、セットならバイト `[handle + 0x8B0]`。
- CW2 側: residue 系では `[req+0x6C]` (control_words2[0])、非 residue では語 `[handle + 0x8B4]` (bit5 クリア時)、bit5 セット時は `[handle + 0x8B4]`。

状態ブロックの +0x8B0 / +0x8B4 / +0x8B8 は、ステージングした要求コピー (+0x7F4 から 0xBC バイト = +0x8B0 まで) の**直後**に位置する 3 スロットで、本ハンドラは読み出すのみで書かない。「index として使う」場合の解決済み値の置き場であり、書き手は本ハンドラの外にある (未確定、§11)。

続いて SF bit2 (NEW_CW) または bit4 (NEW_CW2) がセット、あるいは bit3 (NEW_IV) のみがセットの場合、ジャンプ表 #1 (0xBF8D94、添字 = mode − 1、27 件) でモード別の鍵ストア投入コード (0xBF8E00–0xBF902F) へ分岐する。投入先の詳細は §4。各分岐は対象フラグがクリアな側面をスキップして 0xBF9030 (鍵ワード組立て) へ合流する。分岐先の対応:

| 分岐先 | モード | 処理 |
|---|---|---|
| 0xBF8E00 | 4, 8 (C2) | NEW_IV: `0xBCED1C (IV_seed[0], &IV_seed, &IV_seed+4)`。NEW_CW: `0xBCED1C (CW[0], &CW, &CW+4)` |
| 0xBF8E70 | 2, 3, 6, 7 (AES CBC/CTR) | NEW_IV: IV_seed 16 バイトをスタックへ複写し `0xBCE950 (handle, buf)` |
| 0xBF8EAC | 20, 21, 26 (AES residue) (+ CBC/CTR から合流) | NEW_CW2 かつ対象モード: control_words2 24 バイトを複写し `0xBCE950 (CW2 選択値, buf)` |
| 0xBF8EEC | 1, 5 (AES ECB) (+ 他から合流) | NEW_CW: control_words 24 バイトを複写し `0xBCE950 (CW[0], buf)` |
| 0xBF8F30 | 16, 17, 24, 25 (TDES CBC) | NEW_IV: `0xBCED1C (IV_seed[0], &IV_seed, &IV_seed+4)` |
| 0xBF8F64 | 18, 19, 27 (TDES residue) (+ CBC から合流) | NEW_CW2: CW2 を 8 バイトずつ 3 成分、`0xBCED1C (CW2 選択値 + i, &CW2[8i], &CW2[8i+4])` |
| 0xBF8FC4 | 14, 15, 22, 23 (TDES ECB) (+ residue から合流) | NEW_CW: CW を 8 バイトずつ、`0xBCED1C (CW[0] + i, &CW[8i], &CW[8i+4])`。成分は ABC (14/15) では 3 個、ABA (22/23) では 2 個 |
| 0xBF9030 | 9–13 | 投入なし (そのまま鍵ワード組立てへ) |

NEW_CW / NEW_IV の投入はカウンタ `[0xD8C070]` / `[0xD8C074]` で数えられている。

### 3.5 鍵ワード組立てとジャンプ表 #2

0xBF9030 で、記述子へ載せる鍵ワード r24 を組む:

- r24 = (CW2 選択値 << 24) | (CW 選択バイト << 16) | (IV 由来バイト << 8) | IV 選択バイト
- (IV 由来バイトは、SF bit1 (RESET_IV_PER_LINE) セット時は大域バイト `[0xDA3EB4]`、クリア時は IV 選択バイトそのもの)

ジャンプ表 #2 (0xBF90A4、添字 = mode、28 件) でモード別の設定ワード r16 と、r24 をバイトスワップした r21 を作る (Ghidra の `swap` 第2オペランド表記は定数としてレンダリングされるが、その意味づけは未確定。バイト順変換であることのみ確実):

| モード | r16 | 備考 |
|---|---|---|
| 0 | 0 | r21 = r24 = 0 に潰し、`[req+0x24]` へ 0 を書く |
| 1 | 0 | swap 変種 A |
| 2 | 0x80 | swap A |
| 3 | 0x40 | swap A |
| 4 | 0 | swap B |
| 5 | 0 | swap C |
| 6 | 0x80 | swap C |
| 7 | 0x40 | swap C |
| 8 | 0 | swap D |
| 9–13 | — | 致命的エラー域 0xBF9340 へ (到達するのは 11 MARLIN のみ。他は §3.1 で専用ヘルパへ振り分け済み) |
| 14 / 22 | 0x100 (ABA の 22 は 0x110) | |
| 15 / 23 | 0x440 (23 は 0x450) | |
| 16 / 24 | 0xB80 (24 は 0xB90) | SF bit3 時は r21 = 0x520000 |
| 17 / 25 | 0xEC0 (25 は 0xED0) | SF bit3 時は r21 = 0x620000 |

### 3.6 記述子の構築と投入

作業オブジェクトは `0xBF6CD8` がプール `[0xAFF93C]` から確保する 0x860 バイトで、+0x820 = 0x40 を初期値とし +0x820…+0x850 を 0 化、+0x830 へ stream_handle、+0x840 へ r16、+0x844 へ r21、+0x848 へ r24 を置く (解放は `0xC2C6EC`)。

#### 3.6.1 residue 経路 (モード 18–21, 26, 27)

セットアップ (0xBF8AE0): テンプレート `0xCE1870` (0x14 バイト) から局所記述子を作り `0xB997E0` で初期化し、専用オブジェクトを `0xC443BC` で確保する。サイズ = 0x30 + 0x30 × ceil64k(scrambledBytesPerLine) (numOfTsPid > 0 の場合)。オブジェクト +0x00 = stream_handle、+0x04 = サイズ。+0x10 以降にエントリが並ぶ。

エントリ構築ループ (0xBF9384): 64KiB チャンクごとに 0x30 バイトのエントリを作る:

- +0x00/+0x04: pSrc (u64) + i × 0x10000
- +0x08/+0x0C: pDest (u64) + i × 0x10000
- +0x10: コマンドワード = 0x03080000 | r21 | min(残量, 0x10000)
- +0x14: r16、+0x18: r24、+0x1C: r23
- +0x20/+0x24: メールボックスプリミティブ `0xC94000` / `0xC94024` の対象 (後段で tsPid が書き込まれる)

モード 27/20/18 では先に `0xB9B7B0 (pSrc, scrambledBytesPerLine, tsPacketSize)` を呼ぶ。その後、共有域へのチェーンポインタ書込み (実読上、グループ数に相当する内部値は numOfTsPid の有無による 0/1 で、この書込みループは実質回らない形になっている。元の設計意図は未確定) を経て、tsPid 書込みループ (0xBF9574) が tsPid 配列 (0xFFF = 13 ビットでマスク) を各エントリの +0x20/+0x24 へ `0xC94000` / `0xC94024` で書き込む。最後のエントリのコマンドワードへ 0xA0000000 を OR し、`[fp-0x44]` (エントリ配列の基底) に bit31 を立てて `0xC5C344 (handle, 基底 | 0x80000000, 0xC4AD58)` で投入する。

#### 3.6.2 行経路 (非 residue、numOfLine > 0)

作業オブジェクト先頭から 0x20 バイト (numOfLine = 1) または 0x30 バイト (numOfLine > 1、pitch 語付き) のエントリを最大 3 個 (平文部・暗号部・終端) 構築する:

- +0x00/+0x04: 転送元 (u64。SF bit7 時は keyStoreIndexOfSrcData)
- +0x08/+0x0C: 宛先 (u64。SF bit8 時は keyStoreIndexOfDstData)
- +0x10: 平文部は 0x03080000 (+ バイト数)、暗号部は 0x03080000 | r21 | バイト数
- +0x14: 平文部は 0、暗号部は r16
- +0x18: 平文部は 0、暗号部は r24
- +0x28 (0x30 形式): (destPitch << 16 & 0x7FFF0000) | (sourcePitch & 0x7FFF)
- +0x2C (0x30 形式): (numOfLine << 16 & 0x7FF0000) | (バイト数 & 0x7FF)
- 終端エントリ: 転送元/宛先 = 0xD8E6F0、コマンドワード = 0xA3000004

最後の実エントリのコマンドワードへ 0xA0000000 を OR する。

#### 3.6.3 単発経路 (numOfLine = 0)

`0xBF6794 (ctx, src, dst, size, 0, 0, 0x3000000)` が作業オブジェクト内に直接 1–2 個のエントリを構築する (ctx の +0x840/+0x844/+0x848 に置かれた r16/r21/r24 を参照する)。

#### 3.6.4 共通投入 (0xBF9C80)

スピンフラグ `[0xAFEB10]` の下で `[handle + 0x48]` の bit3 を立て、`0xC5C344 (handle, 記述子基底, 0xC4AD58)` を呼ぶ。`0xC5C344` は記述子チェーンを走査検証 (エントリ語 [4] の bit31 = 終端、bit 0x80000 = 0x30 形式) し、プール `[0xAFEB68]` から通信オブジェクトを確保して `[obj+0xC] = 0x100`、`[obj+0x24] = handle & 0x7FFFFFFF`、`[obj+0x2C] = 0xC4AD58` (完了コールバック) を詰めて実行側へ送る。成功で成功カウンタを増やし 0 を返し、失敗で詳細コード 0xB、文脈を解放して 1 を返す。

## 4. 鍵ストアスロットインタフェース (`0xBCE950` / `0xBCED1C`)

両ヘルパとも、スピンフラグ `[0xAFFADC]` の下で共有域の同一スロット窓を書く:

- `[0xAFE004] + 0x1824` = データワード 0
- `[0xAFE004] + 0x1828` = データワード 1
- `[0xAFE004] + 0x182C` = index ワード。書き込み後、bit31 が立つのを 5 回観測するまでスピンする (消費側の受領ハンドシェイク)
- index が 0x80 以上なら何も書かずカウンタ `[0xCF8FD4]` を増やして戻る (有効スロットは 0x00–0x7F の 128 個)

`0xBCED1C (index, ptrA, ptrB)` は 1 スロット分 (ptrA の語と ptrB の語 = 8 バイト) を書く。`0xBCE950 (index, buf)` は 8 バイト単位で index を増やしながら 2 スロット分 (16 バイト) を書く。§3.4 の AES 系では control_words を 24 バイト複写して渡すが、本ヘルパが実際に投入するのは先頭 16 バイト分である (実読)。TDES 系は成分ごとに `0xBCED1C` を呼び、CW[0]、CW[0]+1、CW[0]+2 と連番スロットへ 3 成分 (ABA は 2 成分) を分けて投入する。C2 系は CW と IV_seed をそれぞれ先頭 8 バイトのみ 1 スロットへ投入する。

すなわち、**control_words[0] は「鍵そのものの先頭バイト」であると同時に「鍵ストアのスロット番号」として使われる**。記述子の鍵ワード r24 に載るのもこの番号 (と CW2・IV の番号) であり、鍵バイト列そのものは記述子には載らない。

## 5. (a)/(b) 境界についての判定

問い: ホストが渡す CW トークンは、(a) ARC コード内で実効鍵へ変換されるのか、(b) そのまま HW / 他プロセッサへ渡り、解決はそちら側で起きるのか。

本段の実読で確定した事実:

1. `0xBF894C` の全行と、その鍵関係の呼出し先 (`0xBCE950`、`0xBCED1C`) の全行に、CW バイト列に対する暗号学的な変換 (鍵スケジュール、S-box 参照、XOR 折り畳み等) は存在しない。行われるのは、逐語ステージング (0xBC バイト複写)、先頭バイトの抽出、逐語の鍵ストア投入、バイトスワップとビット packing のみである。
2. 鍵ストアへの投入は「スロット番号 = CW[0]、内容 = CW バイト列そのもの (8 バイト単位)」であり、記述子へはスロット番号だけが載る。実効鍵の解決は、記述子チェーンとスロット内容を受け取る実行側 (HW のスクランブラエンジン、または通信オブジェクトを受け取るプロセッサ) で起きる構造である。
3. バルク暗号そのものも本ハンドラでは実行されず、記述子チェーンの投入 (`0xC5C344`、完了コールバック `0xC4AD58`) で外部へ渡る。

判定: **SCRAMBLER (GENERIC スクランブル) 経路については (b) が確定した** — トークンは ARC コードでは加工されず、鍵ストアスロット経由の間接参照で実行側へ渡る。docs/02 §10 の「実効鍵はファームウェアがトークンとチップ内部状態から解決する」というモデルは、本経路では「解決 = スロット番号による鍵ストア参照であり、投入される鍵素材はホスト供給 CW の逐語」という形に具体化された。

未確定として残る部分 (不在の断定はしない):

- 鍵ストアスロットの消費側の実体 (HW が直接参照するのか、FN 0x100 の通信オブジェクトを受け取るプロセッサが読むのか) と、消費側で更なる変換があるか。本段の読解範囲 (第2 FW の proc6 到達経路) の外にある。
- 状態ブロック +0x8B0/+0x8B4/+0x8B8 (AS_INDEX 時の解決済みスロット) の書き手。
- 録画保存の SECUREDTS 経路 (docs/14 §6 で一部実読) は SCRAMBLER とは別のコマンド経路であり、本段の判定はそちらへは及ばない。録画時の CW トークン (docs/02 §10) と本経路の control_words の対応づけは解釈の域を出ない。

## 6. 入口 2: `0xC6B118` — デバッグコンソール (候補 (d) の棄却)

全行実読 (0xC6B118–0xC6B34D)。内容はデバッグコンソールの行入力ハンドラである:

- 冒頭でコア別テーブル `0xDA4278 + idx*0x20` の 7 項目を検査し `0xC939C0` を呼ぶ (チャネル別のポーリング)。
- `0xC32940 (0)` でコンソールオブジェクトを得て、`0xC481F4 (0)` で入力 1 文字を読む。行バッファ (オブジェクト +0x44 = 長さ、+0x4 から本文) を維持し、改行 (0x0A) で確定、BS (0x08) / DEL (0x7F) を処理し、ESC [ A / B の履歴操作 (文字列 "upper" / "down" を表示)、候補の回転バッファ (オブジェクト +0x70 の索引、16 件 × 0x40 バイト) を扱う。
- 確定した行は、登録コールバック `[obj+0x48]` を `(行バッファ, [obj+0x50], [obj+0x54])` で呼んで処理させる。単一文字コマンド "c" / "n" / "e" (文字列表 `0xCE188C`–) は戻り値としてその文字コードを返す。

mhcmd / FunctionNumber の振り分けも鍵関係の処理も含まれない。**候補 (d) は実読による積極的な根拠をもって棄却する**。proc6 メインがこれを周回呼出しするのは、proc6 がデバッグコンソールの応答を担うためと解釈できる。

## 7. 入口 3: 登録ハンドラ `0xC82410` / `0xC824A4`

### 7.1 `0xC82410` (通信記述子 +0x17C) — 状態依存の転送

全行実読 (0xC82410–0xC824A3)。引数の指す先から `r13 = [arg+0x10] + 0x5750` を作り `0xC56F14 (r13 - 0x2F)` を呼んでカウンタ `[0xDA3EA8]` を増やした後、`[r13-0x78] == 3` かつ `[r13-0xA0]` の bit 0x20 と bit 0x10 が共にクリアなら `0xC1B5E0 (arg)`、それ以外は `0xC01B18 (arg)` へ転送する、状態依存の振り分け口である。自らは FunctionNumber を見ない。

### 7.2 `0xC824A4` (通信記述子 +0x174) — ストリーム状態の初期化

入口部と構造を実読した (本体 0xC824A4–0xC84511、ジャンプ表 0xC8281C 以降のケース群は個別実読をしていない。§11)。通信記述子 (オフセット +0x1269C 等を持つ大きな構造) を引数に:

- スタック上に 0xBC バイト級の局所構造を組み立てる (サイズ欄の初期値 0xBC、記述子フラグ & 0x204000 時は 0xC0)。0xBC は `cmd2_stream_scrambler` のサイズと一致する。
- 索引 (`[desc+0x1269C]` の先の +0x14 の u16) ごとにテーブル `0xDA4470` へ局所構造へのポインタを登録する。
- 共有域の大域領域 (索引 × 0x10 の小領域と索引 × 0x16178 の大領域、索引 × 0x40 の領域) を初期化する。
- 記述子 +0x55C の先 (+0x1C / +0x34 / +0x38 / +0x40) からストリーム設定値を局所構造へ取り込む。
- 最後にジャンプ表 (0xC8281C) で大きなスイッチへ入る。呼出し先の census では `0xBF894C` への呼出しは無く、`0xC3EFE8` (×6)、`0xBF3B7C` (×4)、`0xC435C4` (×13) 等が並ぶ。

性格としてはストリーム/通信オブジェクトの初期化であり、パケット到着時のディスパッチではない。SCRAMBLER の受け口は §3 で同定済みのため、本関数のケース群の個別実読は次段以降の残件とする。

## 8. 入口 4: 実行時生成タスクの census

生成サービス `0xB082E8` の呼出し元はイメージ全域で 2 箇所のみ (ラッパ `0xB064FC` 内 0xB066D8、ラッパ `0xB067E0` 内 0xB069C0。xref 実測)。両ラッパは OS のタスク生成サービス (トレース ID 0x104 / 0x105) で、引数は (対象プロセッサ指定、タスク ID、引数)。対象が自プロセッサ (0 または自己文脈の +0x30 と一致) なら `0xB082E8` を直接呼び、他プロセッサ宛は文脈 +0x350 の転送コールバック経由 (コード 0x1001/0x1002) で依頼する。`0xB064FC` は生成後に参照数 ([文脈+0x1C]+0x68) の管理と `0xB07820` の呼出し (起動/スケジュールと解釈) を行い、`0xB067E0` は生成オブジェクト +0x08 へ 3 を書く。

ラッパ呼出しサイト 5 件を直前の逆アセンブルで読み、タスク ID を確定した:

| サイト | 呼出し元関数 | ラッパ | ID | タスク (第10段のタスク表) |
|---|---|---|---|---|
| 0xC4DD9C | `0xC4DB98` (proc4 パーソナリティメイン) | 0xB067E0 | 14 | avc_dec_init_task (引数 0) |
| 0xC4DF00 | `0xC4DB98` (同上) | 0xB067E0 | 12 | proc4_incoming_request_process (引数 0) |
| 0xBE6F50 | `0xBE6EB0` | 0xB067E0 | 13 | avc_encoder_task (引数 = 構造体ポインタ) |
| 0xBA2440 | `0xBA23DC` | 0xB064FC | 15 | proc4_SoftGVD |
| 0xC8A110 | `0xC899F4` (汎用生成ヘルパ) | 0xB067E0 | 引数構造体経由 (r1 = 0) | 同定できず |

ID 11 (uist_mv_conversion) の直接の生成サイトは見つからなかった。残る可能性は、汎用ヘルパ `0xC899F4` 経由 (ID を引数構造体から取る形)、他プロセッサからの転送依頼経由、または本イメージでは生成されない、のいずれかで、未確定とする。いずれにせよ生成タスクはいずれも映像処理・要求処理系であり、SCRAMBLER の受け口候補としての (c) は、受け口そのものが §3 で同定されたことにより消滅した。

## 9. 入口 5: 巨大関数 `0xBC3E58` (proc4 チャネル 4) — 部分実読

入口部 (0xBC3E58–0xBC3F94 付近) を実読した:

- 入口カウンタ `[0xDA4378]` と共有カウンタを増やし、ドアベルバイト `[0x100508]` (proc6 メインが監視するのと同じバイト) を検査する: 0x88 なら `0xB05E9C` を呼んでクリア、0xCC なら `0xB04900` の後で無限ループに入る。
- 補助タイマ (周期 0x400000 = proc4 の値) を設定し、メールボックス語を `0xC93D78 (0xA0FC, &局所)` で読み、ビット 0xF0000 のうち 0x10000 が立っていればスピンフラグ `[0xAFEB10]` の下でビットを落として `0xC93DD0` で書き戻す。
- バイト `[0x101790 + 0xB8]` == 0x33 の場合は `0xB04900` を呼んで 0x11 に書き換える。
- 状態ブロック `0xD8B05C` 内の複数のフィールドへのポインタ群をスタックに用意して、文脈 2 のパケット列処理 (本体後半) へ入る。

本体後半 (0xBC3F94–0xBC515F) の比較命令は 0/1/2/3/4 等の小さな状態値に対するものが大半で、`[packet+0xC]` を mhcmd 番号で振り分ける単純な比較鎖は実読範囲では見つからなかった。第10段 §3.8 の「FunctionNumber で振り分ける本体が中にある」という所見は、本段の実読範囲では裏付けられていない (後半のパケット列処理の個別分岐先の確定は未実施であり、不在の断定ではない)。SCRAMBLER の探索という目的では本関数は proc4 側であり優先度が下がったため、分岐先 census は残件とする。
