# 35 torne mobile の DTCP-IP 資格情報の供給機構 第3段 (資産ファイル `PvrAssetData.cxml` の出所追跡)

対象: torne mobile v1.50 のアプリ本体 `torneplus` (Mach-O arm64) と `PvrBgApp` フレームワーク (docs/21・docs/33・docs/34 の続き)。docs/34 で残した「資産ファイル `PvrAssetData.cxml` の配布経路」を解く段。

状態: **資産の出所は確定。資産は IPA には含まれず、torne の GAE (Google App Engine) バックエンドからライセンス応答として取得され、2 層の復号を経てアプリコンテナの Documents ディレクトリへ書き込まれる。** あわせて、保持中キーの有効性を確認する軽量なキー確認要求 (`op=opDtcpipKeyCheck`) の存在と構成、書き込み手順とディスク形式 (書き手側) を同定した。端末間同一性については、配布暗号文が端末側識別子 (mobileId) に束縛されることまでを確定し、資格情報の中身そのものの同一性は静的解析では判定できないことを明記する。資格情報の値そのもの (証明書・秘密鍵、および後述の埋め込み秘密文字列の値) は本書のどこにも書かない。

## 1. 解析方法

- 静的解析 (逆アセンブル実読) のみ。サーバへの実アクセスはしていない。実機 (nasne) にも触れていない。
- 対象バイナリ `torneplus` はベースアドレス `0x100000000`、ファイルオフセット = VA − ベースが全域で成立する (サイズ 11,662,848 バイト、stripped)。本書の torneplus 側アドレスはすべて VA で記す。`PvrBgApp` 側は docs/34 の表記 (ファイルオフセット = VA) に従う。
- radare2 の `aaa` は torneplus でクラッシュしたため、`aa` + 対象関数の実読を基本とし、xref は自作スキャナ (adrp/add ペア走査、BL 走査、ポインタ出現走査、CFString / selref 解決) で補った。
- 文字列の同定は `__cstring` / `__cfstring` の実読による。難読化された埋め込みブロブについては、復号処理の存在と用途までを追い、平文の値 (認証クレデンシャル等) は再構成していない。

## 2. 全体像

資産ファイルが生成されるまでの流れは次の通り (括弧内は本書の根拠節)。

1. アプリが GAE バックエンドへライセンス要求を送る (購入時 `op=opApplePurchases`、確認時 `op=opApplePurchasesCheck`、§3)。
2. 応答のライセンス辞書 (productid / expiredate / encrypteddata / key / id / data) を `PvrStoreKitHelper.updateLicence:nonce:keyNonce:` が処理し、C++ ハンドラ `0x100429bf4` が `data` を第1層復号する (base64 デコード → mobileId 束縛の鍵導出 → AES-128-CBC、§5)。
3. 復号結果は TLV コンテナで、ディスパッチ関数 `0x1004272c4` が埋め込み秘密文字列由来の鍵で第2層復号し、タグ `PRMA` の値を `PvrAssetData.cxml`、`PRMB` の値を `PvrBGMData.cxml` として保存関数 `0x100427034` へ渡す (§5)。
4. 保存関数はディスク形式コンテナ (ランダムヘッダ + SHA-256 + 暗号変換) に包んで Documents ディレクトリへ書き込む (§6・§7)。これを `PvrBgApp` の資産ローダ `0xc5e0` が読み、DAL アイテム 1 として投入する (docs/34)。
5. 並行して、C++ 側に保持中キーの確認要求 `op=opDtcpipKeyCheck` があり、サーバ応答の `keyUpdate` フラグで再取得の要否を判定する (§4)。

## 3. 入手経路 (1): ライセンスフロー (ObjC 側)

- 送信の共通実装は `PvrStoreKitHelper.sendReceiptToGae:response:op:` (`0x100418744`)。App Store レシートとともに GAE へ要求を送る。パラメータには `deviceid`、`nonce`、`keyNonce`、`requestKey=1`、`productlist` 等が含まれる (CFString 参照の実読)。エンドポイントと認証の構築には C++ 側と同じ難読化ブロブ復号関数 `0x100339d48` が使われる (ブロブは `0x1008bea38` / `0x1008bea79` 付近)。
- `updateLicence:nonce:keyNonce:` (`0x100419580`) の呼び出し元は 2 件のみで、いずれも GAE 応答処理の中からである。
  - `sendReceiptToGaeForPurchaseAsync:` (`0x100419d34`) 内 `0x100419ed0` — op は `opApplePurchases`。
  - `sendReceiptToGaeForCheckPurchase:` (`0x10041a01c`) 内 `0x10041a18c` — op は `opApplePurchasesCheck`。
  - 両者とも `nonce` と `keyNonce` を生成 (`createNonceString`、`0x10041a5b4`) して応答処理へ渡す。
- `updateLicence` が読むライセンス辞書のキーは `productid`、`expiredate`、`encrypteddata`、`key`、`id`、`data` (CFString 実読で確定)。`productid` / `expiredate` / `encrypteddata` は別途 `setToLicenceManager:nonce:` (`0x10041a83c`) でライセンスマネージャへ登録される。
- `key` の値の扱いには分岐がある。数値系の場合は `stringValue` を経てバイト列化し、文字列系の場合は直接バイト列化する (変換関数 `0x1004c2b18` / `0x1004c2bf8` は NSString → C++ バイト列の変換)。ライセンス側に使える `key` が無い場合は、マネージャ内を名前 `SCE_910_EXPORTN` で引くフォールバックがある。
- GAE の URL は `getGaeUrl` (`0x10041a460`) が返し、その実体はアプリ全体のマネージャ (シングルトン取得関数 `0x10034ceb8`) の `+0x8f8` オブジェクトの `+0x210` に保持される C++ 文字列である。**URL の具体値はバイナリ内平文には存在せず**、サーバ設定 (バイナリ内に `SVRCONFG` / `GAEURL2` 等の設定キー文字列がある) によって実行時に配布・保持される値である。未設定の間は 1 秒間隔で最大約 29 回ポーリングして待つ実装 (getGaeUrl / getMobileId / getDeviceId に共通)。

## 4. 入手経路 (2): キー確認要求 (C++ 側、`op=opDtcpipKeyCheck`)

- 実装は C++ 関数 `0x10042953c` (1720 バイト)。vtable のスロットとして 2 箇所 (`0x1009191a0`、`0x1009192f0`) から参照される仮想メソッドで、同じ vtable にはライセンス応答を解析する関数 `0x1003d49d0` (CFString の `productid` / `expiredate` / `encrypteddata` / `deviceid` を参照) も並ぶ。Xp フレームワーク系の GAE クライアントタスククラスとみられる。
- 要求の構成 (実読で確定した範囲):
  - メソッドは POST。URL は §3 と同じ `+0x8f8` オブジェクトの `+0x210` 文字列。
  - パラメータ文字列は `op=opDtcpipKeyCheck&deviceid=<deviceid>&keyid=<keyid>` の形に組み立てられる。
  - `deviceid` はマネージャ `+0x980` オブジェクトのゲッタ `0x1003a5f70` が返す 64 ビット整数を `%lld` で文字列化したもの。ObjC 側 `getDeviceId` (`0x10041a3b0`) も同じゲッタの値を `stringValue` 化して返す (両経路で同一の値)。
  - `keyid` はキーマネージャ (`+0x8b8` オブジェクト) の `+0x5c0` に保持される「保持中キーの ID」文字列。空の場合は既定値 `0` が使われる。
  - 要求オブジェクトにはフィールドとして `mobileIdAuth` (値はキーマネージャ `+0x2c8` の文字列 = ObjC `getMobileId` が返す mobileId)、`user-agent` (値は `torne 150 (iOS)`、形式文字列 `torne %3d (iOS)` にバージョン 150 を埋めたもの)、`authorizAtion` (綴りはバイナリの通り。値は `Basic ` + base64) が設定される。Basic 認証のクレデンシャルは、埋め込み難読化ブロブ 2 件 (`0x1008bedd9` / `0x1008bee1a` 付近) を復号関数 `0x100339d48` で復号し `:` で連結して base64 化 (エンコーダ `0x1003429f0`) したもので、バイナリに埋め込まれたアプリ共通の値である (値は再構成していない)。ほかに `Content-Type` という名前のフィールド設定も観測された (値として応答解析側のキー名と同じ文字列が使われており、HTTP ヘッダではなくこの実装の要求オブジェクトのフィールドとみられる。詳細な意味は未確定)。
- 応答処理: 応答オブジェクトから `result` / `responseCode` を読み、内部コード (0x7534 / 0x75fa / 0x7629–0x762b / 0x765d–0x765f 等) で分岐する。`keyUpdate` というキーが応答に含まれていれば、更新フラグ (this `+0x71`) を立てて仮想コールバックを呼ぶ。処理の最後に、次回確認の基準値 (this `+0x78` の文字列) を `+0x8f8` オブジェクトの `+0x13c` の値 × 60 秒で更新する。関数冒頭ではこの基準値が有効期間内であることを確認し、その場合は要求を送らず早期 return する。すなわちキー確認は「毎回」ではなく、有効期間管理付きの確認である。
- `keyUpdate` フラグから §3 のライセンス再取得フローへの発火を直接結ぶコードは本段では同定できていない (仮想コールバック先の追跡が残る、§10)。

## 5. 復号チェーン (ライセンス `data` から資産ファイルまで)

### 5.1 第1層 (C++ ハンドラ `0x100429bf4`)

- `updateLicence` から 3 つの C++ バイト列オブジェクトを受け取る。第1 = ライセンス `key` 由来のバイト列、第2 = ライセンス `data` 由来のバイト列、第3 = keyNonce オブジェクト。いずれかの長さが 0 ならエラー (0xff010007) で終了する。
- 第2引数 (`data`) を base64 デコードする (デコーダ `0x100342adc`。対になるエンコーダ `0x1003429f0` の出力長計算が base64 の形であることから同定)。
- 鍵導出はハッシュの Init/Update/Final 型 API (`0x100488b18` / `0x100488b28` / `0x100488b44`、§7.3 の SHA-256 と同じモジュール) で、投入順に (a) mobileId 文字列 (キーマネージャ `+0x2c8`) 全体、(b) デコード済み `data` の先頭 16 バイト、(c) keyNonce の先頭 16 バイト。
- 復号は暗号関数 `0x1004883bc` (AES-128-CBC と同定、§7.3) で、デコード済みデータの先頭 16 バイトを除いた部分に適用される。復号結果が §5.2 の TLV コンテナになる。
- 成功後、第1引数 (`key` 由来バイト列) がキーマネージャへ登録される (関数 `0x1003564e4`)。保持中キーの ID (次回キー確認の `keyid`) はこの登録で更新されるものとみられる。
- なお、復号の直前には難読化ブロブ由来の値を生成する関数 `0x100429e50` と暗号モジュールの関数 `0x10048815c` が使われるが、この 2 つの正確な役割 (鍵・IV の配線) は未確定 (§10)。

### 5.2 第2層 (TLV ディスパッチ `0x1004272c4`)

- 冒頭で、基底パスの大域変数 (後述 §6) をパスヘルパの値に設定する。
- 埋め込みの **50 文字の秘密文字列** (`__cstring` 内、値は記録しない) を作業バッファへ複写し、**バイト順を反転**したうえで SHA-256 (ワンショット関数 `0x100488ab0`) にかけ、得た 32 バイトの前半 16 バイトを鍵、後半 16 バイトを IV として、入力全体を AES-128-CBC 復号 (`0x1004883bc`) する。
- 平文は TLV 列である。各レコードは タグ (4 バイト) + 長さ (u32、オフセット +4) + 値 (オフセット +8 から長さ分) の形式で、終端までの走査で処理される。タグが `PRMA` なら保存ファイル名 `PvrAssetData.cxml`、`PRMB` なら `PvrBGMData.cxml` として、値を保存関数 (§6) へ渡す。形式不正はエラー 0xe6000002。
- 処理後の平文バッファはランダム値で上書きしてから解放される (第1層・保存関数でも同様の消去が観測された)。

## 6. 書き込み経路と配置場所

- 保存関数は `0x100427034` (引数 = ファイル名、データ、長さ)。
- 基底パスはパスヘルパ `0x1004c39a0` の種別 4 で得られる。種別 4 の実装は `NSSearchPathForDirectoriesInDomains(9, 1, YES)`、すなわち **NSDocumentDirectory (アプリコンテナの Documents ディレクトリ)** である。基底パスは大域変数 `0x1009b9958` (char*) にセッタ `0x100426fbc` で設定され、未設定のまま保存関数が呼ばれるとエラー 0xe6000003 になる。
- `PvrDtcpIpKeyManagerInitialize` の呼び出しラッパ `0x1004274e8` も、同じ種別 4 のパスを第1引数として渡す。**書き手 (torneplus) と読み手 (PvrBgApp 資産ローダ、docs/34) の基底パスは同一**であり、資産の実配置は次の通り確定する。
  - `<アプリコンテナ>/Documents/PvrAssetData.cxml`
  - `<アプリコンテナ>/Documents/PvrBGMData.cxml`
- 書き込み手順 (保存関数の実読): ディスク形式コンテナ (§7) を組み立て、`<ファイル名>.tmp` へ書き込む。次に既存の本ファイルを `<ファイル名>.bak` へ rename し、`.tmp` を本ファイル名へ rename してから、`.bak` を削除する。docs/34 でローダ側に見えた `.bak` 兄弟処理は、この書き手側のローテーションと対応する。

## 7. ディスク形式 (資産ローダ保護形式の書き手側)

### 7.1 コンテナ構造

保存関数が組み立てるコンテナは全長 = ペイロード長 + 48 バイトで、構造は次の通り。

| 領域 | 内容 |
|---|---|
| [0, 16) | `rand()` で生成する 16 バイトのランダム値 (書き込み毎に変わる) |
| [16, 48) | ペイロードの SHA-256 (32 バイト、関数 `0x100488ab0`) |
| [48, ...) | ペイロード |

組み立て後、オフセット 16 以降の領域 (SHA-256 + ペイロード) が暗号変換関数 `0x100488224` で処理され、最後に関数 `0x10048815c` による仕上げ処理が入る。変換の文脈は関数 `0x100429ef0` が用意し、使用後はランダム値で消去される。変換の鍵の出所 (固定鍵か、ランダムヘッダ由来か) と `0x10048815c` の役割は未確定 (§10)。

### 7.2 docs/34 のローダ側観測との対応

docs/34 では、PvrBgApp の資産ローダ `0xc5e0` について「16 バイト値の生成 + 48 バイト照合を伴う復号」と記録した。本段の書き手側の構造では、ヘッダ領域がちょうど 16 (ランダム) + 32 (SHA-256) = 48 バイトであり、ローダ側の「48 バイト照合」はこのヘッダ領域に対応すると構造的に読める。ローダ側で「生成」される 16 バイト値が書き手側のどの値と照合されるか (ランダムヘッダそのものか、ペイロード由来の導出値か) の完全な対応付けは未確定 (§10)。

### 7.3 暗号プリミティブの同定根拠

- ハッシュ: SHA-256 と同定する。根拠は (a) SHA-256 の K テーブル定数 `0x428a2f98` がバイナリ内に存在する (ファイルオフセット `0x8d5900`)、(b) 出力が 32 バイト、(c) Init/Update/Final 型の構造、の 3 点。MD5 / SHA-1 の定数は検出されなかった。実装は torneplus に静的リンクされた暗号モジュール (関数群は `0x1007eexxx` 付近、アルゴリズム選択子とみられる定数 `0xC0000001` を各ラッパが用いる) で、内部実装の全行実読はしていない。
- 暗号: AES-128-CBC と同定する。根拠は (a) 復号関数 `0x1004883bc` が鍵スケジュール関数 `0x1007eec5c` へ鍵長 128 (ビット) を渡す、(b) AES 逆 S-box がバイナリ内に存在する (ファイルオフセット `0x8d7a28`)、(c) 16 バイトを IV として受け取り 16 バイトブロック境界で処理する、の 3 点。連鎖 (CBC) の実読による最終確定はしていない。
- torneplus は CommonCrypto (CCCrypt / CCHmac / CC_MD5 / CC_SHA256) もリンクしているが、上記の資産経路で使われるのは静的リンク側のモジュールである (呼び出し先アドレスの実読による)。

## 8. 端末間同一性についての判定材料

- キー確認・ライセンスの両要求には、端末 (登録) を識別する情報が含まれる。`deviceid` (64 ビット整数)、`mobileId` (文字列)、`keyid` (保持中キーの ID) で、いずれもマネージャオブジェクトに保持される実行時値であり、バイナリには含まれない。
- **配布物の暗号文は端末ごとに異なることが確定する。** 第1層の鍵導出 (§5.1) に mobileId が含まれるため、ライセンス `data` の暗号文は mobileId に束縛されており、異なる mobileId の下では復号できない。サーバは要求元の識別子を見て応答を返せる立場にもある。
- **資格情報の中身 (TLV 平文) が全端末で同一か個別発行かは、静的解析では判定できない。** 第2層の鍵はアプリ共通の埋め込み秘密文字列であり、サーバが全端末へ同じ TLV 平文を返せば中身は共通になるし、端末ごとに異なる平文を返すことも構造上可能である。判定には 2 台分の実データの比較が必要で、本段 (静的解析のみ) の範囲外である。
- `deviceid` と `mobileId` の初期発行フロー (初回登録) は未追跡である。いずれも未設定時にポーリングで待つ実装 (§3) であり、起動後の非同期処理 (登録または設定ダウンロード) で埋まる設計と読めるが、これは推測として記す。
- `deviceid` の意味論 (何の ID か) も未確定である。少なくとも torneplus 側マネージャ (`+0x980`) が保持する int64 で、ObjC `getDeviceId` と C++ キー確認が同じ値を共有することだけが確定している。

## 9. IPA 内の再確認

- バンドル全ファイルの棚卸しで、`PvrAssetData.cxml` という名前の loose ファイルは存在しない。同梱される cxml は `PvrResource.cxml`、`PvrTheme.cxml`、`PvrVersionHistory.cxml`、`NicoJkResource.cxml`、`TwitterResource.cxml` の 5 件で、いずれも先頭から全面暗号化様 (平文ヘッダなし) の別資産である。
- 展開済み `.app` の全ファイルに対するバイト列走査で、文字列 `PvrAssetData` および `PvrBGMData` の出現は `torneplus` と `PvrBgApp` の 2 バイナリのみ (いずれも名前文字列としての出現)。タグ `PRMA` の出現は `torneplus` のみ。`GCRESOURCEDIR.psarc` は docs/34 で全 41 エントリが画像のみと確認済みで、本段の走査でも該当文字列は検出されなかった。
- 以上と §2–§6 の書き手の同定により、「資産は IPA に含まれず、実行時にサーバから取得して生成される」ことが、単なる不在確認ではなく書き手経路の積極的な同定によって裏付けられた。

## 10. 未確定点

- ライセンス `data` の TLV 平文が端末ごとに同一かどうか (§8)。実データ比較が必要。
- 第1層復号における関数 `0x10048815c` と難読化ブロブ由来値 (関数 `0x100429e50` が生成) の正確な役割・鍵と IV の配線。
- ディスク形式の暗号変換 (`0x100488224`) の鍵の出所と、`0x10048815c` の仕上げ処理の内容。docs/34 のローダ側観測 (16 バイト値の生成) との完全な対応付け。
