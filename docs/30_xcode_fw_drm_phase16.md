# XCode ファームウェア DRM モジュール解析 第16段

2026-11-15。DRMCTRL 内部に入る段。第15段で、SECUREDTS (復号) の鍵束縛は鍵ストアスロットとは別系統の **DRMCTRL 鍵オブジェクト機構** (`0x261B7C`) であることが確定した。本段はその内側 — 鍵オブジェクト (KO) の初期化・素材の出所・エンジンへの受け渡し — を追い、SECUREDTS の実効鍵がどこから来るのかを静的に確定することを狙った。

手法は第9段の M1–M6 を踏襲 (Ghidra 実読を主とし、静的データはイメージのバイト列から直接読んで照合)。素材は開発側作業領域 `2026-11-13-fw-drm/phase16/` (Ghidra プロジェクト `ghp16` = 第2 FW、`ghp16m` = 主 FW、いずれも phase15 プロジェクトの複製)。アドレス表記は各イメージのロードベース基準 (主 FW = 0、第2 FW = 0xB00000) で、ファイルオフセットと一致する。ただし **DRMCTRL 系ライブラリのデータ参照は +0x100000 ビュー**であり、本段で扱う表・文字列・リストの実内容は「コード上の参照アドレス − 0x100000」のファイルオフセットにある (各所で実測により確認した。コードアドレスとファイルオフセットを併記する)。

用語: **KO (鍵オブジェクト)** = DRMCTRL 文脈 (表 `0x69735C` のエントリが指す構造) の +0x148 にインラインで置かれる 0x3F8 バイトの作業域。第15段までの「文脈 +0x148 の作業域」と同一物であり、`0x261B7C` が束縛時に読む能力フラグ・素材欄はこの KO の欄である。**セッションオブジェクト** = KO +0x48 のポインタが指す大きなオブジェクトで、AKE 実体 (gen_kauth / setexchgkey、第6・7段) が操作するセッション文脈 (+0x10C20 起点) を内包する。

## 2. 課題と入口

### 入口 (1) DRMCTRL 初期化 `0x2629F4` の実読

`drmctrl_open` (`0x261520`) が文脈登録時に呼ぶ初期化関数 (第15段 §4.2)。文脈構造 (作業域 0x3F8 バイト) の初期化内容、6 件の鍵オブジェクト表 (`0x69735C`) の初期状態、初期値の出所 (静的データか、OTP / チップ ID 由来か、ゼロか) を確定する。本関数は計算呼出し経由でスロットアロケータ `0x1BC3E8` を呼ぶことも分かっている。

### 入口 (2) モード別ハンドラ表 `0x3ED500` の列挙

`drmctrl_open` がモード一致で引く表 (ストライド 5 ワード)。静的イメージの当該範囲は初期値を持たず実行時登録とみられる (第15段 §4.2) ため、登録側 (表への書込み元) を census して、誰がいつ何を登録するかを洗う。モードとハンドラの対応を確定し、SECUREDTS に関わるハンドラを特定する。

### 入口 (3) 暗号セットアップ `0x15490C` の実読

鍵オブジェクト束縛 `0x261B7C` が、KO の能力フラグ 0x20 の場合に呼ぶ関数 (第15段 §4.1)。鍵オブジェクトがエンジンへどう渡るか (記述子経由か、スロット経由か、レジスタ直書きか) を実読し、DRMCTRL 側の消費側の構造を確定する。

### 入口 (4) 鍵オブジェクトへの素材投入経路

`0x261B7C` が束縛する KO の素材欄 (作業域 +0x34C〜+0x378、第15段で文脈 +0x81EC〜+0x8248 へ複写されることを確認) は、誰がいつ書くのか。候補: ホストコマンド (どの FN か)、AKE の交換手続き (gen_kauth / setexchgkey — 第6段で「文脈内の生成値と相手方素材の 12 バイト XOR が交換鍵」であることがコードで確定しているが、対象は AKE セッション文脈であり DRMCTRL の KO と同一かは未確認)、OTP / チップ由来の導出、B-CAS・デスクランブラ側からの供給。SECUREDTS の実効鍵の出所を、事実の取れる範囲で確定する。

### 入口 (5) DRMCTRL 文脈自身のスロット欄 (+0x49C/+0x4B4/+0x4B8) の消費側

モード 0x100000 / 0x200000 のときに `drmctrl_open` が予約するスロット対 3 組 (第15段 §4.2)。予約したスロット番号を誰がどう使うか (SCRAMBLER 的な投入を受けるのか、記述子に載るのか) を追う。

### 入口 (6) `0x261260` の対象オブジェクト同一性

docs/27 §2.2 以来の留保。巨大関数 `0x23FFC8` の case 0x11 分岐から呼ばれる `0x261260` は、`0x261B7C` が格納する KO 作業域ポインタ (文脈 +0x825C) を読むことが第15段で判明している。本段の DRMCTRL 実読と交差したら、対象オブジェクトがストリーム文脈と同一か否かを判定する。

## 3. 前提 (確定済み事項)

- 録画保存は非対称構成: SECUREDTS (復号) = DRMCTRL 鍵オブジェクト束縛 (`0x261B7C`)、GENERIC-AES (保存暗号化) = 鍵ストアスロット + SCRAMBLER CW。保存される `.dat` の鍵は GENERIC 側であり、残る未知はエンジン内部変換の有無のみ ([docs/29](29_xcode_fw_drm_phase15.md))。
- `0x261B7C` は鍵指定ペア (要求 +0x38/+0x3C、+0x40/+0x44) を DRMCTRL 文脈の 6 件表 (`0x69735C`) から解決し、ポインタをストリーム文脈 +0x81D0 / +0x81D4 へ、KO 作業域ポインタを +0x825C へ格納する。KO の能力フラグ (作業域 +0x10) と文脈 +0x818C (8/0x10/0x20) の対応を検証し、フラグに応じて KO 素材欄 (作業域 +0x34C〜+0x378) を文脈 +0x81EC〜+0x8248 へ複写する。フラグ 0x20 では暗号セットアップ `0x15490C` を呼ぶ。鍵ストアスロットへのアクセスも +0x8B0 台へのアクセスも無い ([docs/29](29_xcode_fw_drm_phase15.md) §4.1)。
- `drmctrl_open` (`0x261520`) は DRMCTRL 文脈 (最大 6 件、表 `0x69735C`、ストライド 0x10) を登録し、文脈 +0x148 (作業域) がゼロなら 0x3F8 バイトをゼロ初期化して初期化関数 `0x2629F4 (作業域, モード, 0)` を呼ぶ。モード 0x100000 / 0x200000 のときのみ文脈 +0x49C / +0x4B4 / +0x4B8 へスロット対 3 組を予約する。本体に鍵素材の読み書き・変換は無い ([docs/29](29_xcode_fw_drm_phase15.md) §4.2)。
- AKE 実体 (gen_kauth / setexchgkey) では、交換鍵 12 バイトがセッション文脈内の 2 つの 12 バイト列 (gen_kauth の生成値と相手方素材) の XOR で導出されることがコード実読で確定している。gen_kauth の中核計算は HW RSA/ECC エンジンのドライバである。ただし対象は AKE のセッション文脈であり、DRMCTRL の KO との同一性は未確認 ([docs/14](14_xcode_fw_drm_phase6.md) §5、[docs/15](15_xcode_fw_drm_phase7.md))。
- DRMCTRL 実行コードは +0x100000 アドレスビューのライブラリとして到達した経緯がある ([docs/13](13_xcode_fw_drm_phase5.md))。アドレスの読み替えが必要な箇所ではその旨を明記する。
- 変位ベースの全数 census は方法限界が実測済み (分割アドレッシングで既知のアクセスすら拾えない) のため、全数否定の根拠には使わない ([docs/27](27_xcode_fw_drm_phase13.md) §2.4)。

## 4. 調査経路と結果

### 4.1 入口 (1): `0x2629F4` — モード別静的テーブル駆動のスロット予約/解放

**同定**: 呼出し元は `drmctrl_open` の 1 箇所のみ (xref 全数 1)。引数は (KO 作業域ポインタ, モード, 予約/解放フラグ)。入口で呼出しカウンタ (ビュー `0x4ECDB8`) を進める。

**処理**: モードで静的テーブルを 1 つ選び、エントリごとにスロットアロケータを呼んで、返されたスロット番号を **KO 作業域 + エントリ指定オフセット + 4×j** へ格納する (予約時)。解放時 (第3引数 = 1) は同じテーブルを辿り、格納済みスロット番号を読んで解放関数を呼ぶ。エントリ形式は 8 バイト:

| 欄 | 意味 |
|---|---|
| +0 (ワード) | KO 作業域内の格納先オフセット |
| +4 (バイト) | アロケータ選択: 0 → `0x1BC3E8` / 解放 `0x1E4124`、非0 → `0x1BC46C` / 解放 `0x1E4190` |
| +5 (バイト) | 割当てサイズ (全エントリとも 2 = 2 スロット連続) |
| +6 (バイト) | 繰返し回数 |
| +7 (バイト) | 0 (未使用) |

**静的テーブルの全列挙** (コード上の参照アドレス / ファイルオフセット = 参照 −0x100000。内容はイメージバイト列から直接読んだ):

| モード | テーブル (参照 / ファイル) | エントリ (格納先, 選択, 回数) |
|---|---|---|
| 0x20 | `0x5305A8` / 0x4305A8 | (0x1B0,0,1) (0x1B4,0,1) (0x1BC,0,1) (0x1C8,1,1) (0x1B8,0,1) (0x1CC,1,2) (0x1D4,1,1) (0x1D8,1,1) |
| 0x40 | `0x52D304` / 0x42D304 | (0x3A8,0,1) (0x3AC,0,1) (0x3B0,1,2) (0x3B8,1,1) (0x3BC,1,1) |
| 0x80 | `0x52EA68` / 0x42EA68 | (0x1C4,0,1) (0x1C0,0,1) (0x1DC,1,1) (0x1C8,1,1) (0x1B8,0,1) (0x1CC,1,2) (0x1D4,1,1) (0x1D8,1,1) |
| 0x100 | `0x4ECBCC` / 0x3ECBCC | (0x36C,0,1) (0x370,0,1) (0x374,0,1) (0x378,1,1) (0x37C,1,1) |
| 0x200 | `0x4ECDEC` / 0x3ECDEC | (0x378,0,2) (0x380,1,2) (0x388,0,1) |
| 0x20000 | `0x4ECB84` / 0x3ECB84 | (0x370,0,1) (0x374,0,1) (0x378,1,1) (0x37C,1,1) |

- モード 0x10000 / 0x100000 / 0x200000 / 0x400000 / 0x1000000 は予約なしで 0 を返す。未知のモードはエラー (戻り値 1、エラー記録セル (ビュー `0x4ECDC0`) = 0xFFFF)。割当て失敗時は失敗エントリ番号を同セルへ記録して 1 を返す。
- すなわち本関数は「文脈の初期化」ではなく、**モードごとに決まった KO 欄へ鍵ストアスロット番号を埋める (または解放する) 処理**である。KO の初期値の出所という観点では、初期化されるのはスロット番号欄のみで、静的データ・OTP・チップ ID 由来の初期値は本関数には存在しない (文脈のゼロ初期化は `drmctrl_open` 側の memset)。
- 解放側 (第3引数 = 1) の呼出し元は参照 census では見つからなかった (呼出し元は予約側の 1 件のみ)。計算呼出し経由の到達は否定できないため、解放経路の実在そのものはコード上に確認したが、その呼出し元は未同定としておく。

### 4.2 入口 (2): ハンドラ表 `0x3ED500` は静的だった (第15段の読みの訂正)

**訂正**: 第15段 §4.2 は「表は静的イメージからは内容を列挙できなかった (ファイルイメージの当該範囲は初期値を持たず、実行時登録とみられる)」とした。これはファイルオフセット 0x3ED500 を読んだための誤りである。本ライブラリのデータ参照は +0x100000 ビューであり、**実内容はファイルオフセット 0x2ED500** にある。イメージバイト列から直接読んだ静的初期値は次の通り (コード上の参照アドレスは `0x3ED500`、ストライド 5 ワード):

| # | モード (+0x00) | open ハンドラ (+0x04) | close ハンドラ (+0x08) | +0x0C | +0x10 |
|---|---|---|---|---|---|
| 0 | 0x01000000 | `0x156830` | `0x156AD0` | 0 | 0 |
| 1 | 0x00010000 | `0x26EE7C` | `0x26EE04` | 0 | 0 |
| 2 | 0x00020000 | `0x228C90` | `0x166B7C` | 0 | 0 |
| 3 | 0x00000200 | `0x2653F0` | `0x16BBE8` | 0 | 0 |
| 4 | 0 (終端) | — | — | — | — |

- 表の走査は `drmctrl_open` (open ハンドラを `(文脈, 文脈+0x148)` で呼ぶ) と `drmctrl_close` (`0x260874`、close ハンドラを同じ引数で呼ぶ) の双方とも「モード = 0 のエントリで停止」であり、静的な終端と整合する。+0x10 の値は open 時にタスク生成 (`0x3B4ED0`) の引数へ渡される (静的エントリでは全て 0)。
- この表は第3段で「0x2ED500 レジストリ」として実読された表と同一物である ([docs/09](09_xcode_fw_drm_phase3.md) §2)。第3段は「8 件のコードポインタはいずれも関数入口を指していない」としてハンドラ表であることを否定したが、現在のプロジェクトの関数切りでは 8 件全てが関数入口に一致する (本段で全て実読した)。第3段の否定は当時の関数切りの未熟によるもので、本段の同定が優先する。
- 登録側の census: `0x3ED500` への参照は読み手 2 関数 (`0x261520` / `0x260874`) からの 4 件のみで、書込み参照は無い。ビュー形式 `0x4ED500` への参照は 0 件。したがって「実行時登録」の積極的な証拠は無く、表は出荷時点で静的に完結していると判定する。もっとも参照 census は計算アドレッシングを取りこぼし得るため (前提の方法限界)、実行時にエントリが追加・変更される可能性そのものは否定しない。

### 4.3 モード別ハンドラ 4 組の実読

#### モード 0x1000000: open `0x156830` / close `0x156AD0` — AKE セッション初期化

- セッションオブジェクト (`*(KO+0x48)`) のセッション文脈 (+0x10C20) をサイズ 0x3CB4 で登録し、オブジェクト +0x148F4 の 0x24C4 バイトをゼロ初期化して +0x10C40 に自己参照を置く。これは第6段で gen_kauth / setexchgkey が操作したセッション文脈と同一レイアウトであり、**DRMCTRL 文脈 (モード 0x1000000) が AKE セッションを所有する**ことが確定した。
- 機器素材の用意: KO +0x54 の bit0 が 0 なら生成関数 (`0x370950`) で 5 単位ずつ値を生成してセッション +0x10F04 / +0x10EF0 へ置き先頭バイトの bit7 を落とす。bit0 が 1 なら静的データ (参照 `0x3D356C` / `0x3D3580` から 0x14 バイトずつ、参照 `0x3D3594` から 0x10 バイト。実内容はファイル 0x2D356C / 0x2D3580 / 0x2D3594 に非ゼロで存在) を複写する。続いて `0x1601DC` と `0x16024C (+0x10F04, +0x10F18, +0x10F2C)` で 2 つの 0x14 バイト欄から派生値を計算する (中身の同定は本段の範囲外)。
- 鍵ストアスロットの割当て: 静的オフセットリスト (参照 `0x3D35A4` / ファイル 0x2D35A4) の 6 エントリ {0x124, 0x12C, 0x128, 0x138, 0x13C, 0x144} (第2ワードは全て参照 `0x3D35DC` で共通) について `0x1BC3E8 (2)` を呼び、スロット番号をセッション文脈 +オフセットへ格納する。失敗時は割当て済みを全て解放して 1 を返す。成功後、+0x10D50 / +0x10D54 へリスト [2] / [1] のスロット番号を複写し、`0x160C98 (+0x10D3C)` の結果でセッション +0x10CD8 に 0x79 / 0x6E を設定する。
- KO 側へは +0x36C / +0x380 / +0x384 のゼロクリアのみ。**KO の能力フラグ (+0x10)・状態 (+0x0C)・素材欄 (+0x94/+0xA4/+0x154) への書込みは無い**。
- close `0x156AD0`: 同リストのスロットを全て解放し、セッション内のサブオブジェクト群を `0x161490` で解放、KO +0x36C / +0x380 / +0x384 をゼロクリアする。

#### モード 0x10000: open `0x26EE7C` / close `0x26EE04` — AKE 簡易変種

- セッション文脈 (+0x10C20) をサイズ 0x2F0 で登録し、+0x10F30 をゼロ初期化して自己参照を置く。スロット対 1 組を `0x1BC3E8 (2)` で確保しセッション +0x10C9C へ格納する。KO へは +0x368 のゼロクリアのみ。close はスロット解放と +0x368 のゼロクリア。

#### モード 0x20000: open `0x228C90` → `0x166918` / close `0x166B7C` → `0x162114`

- open は KO +0x34C = 0x800、KO +0x350 = 8 と置いて `0x166918` を呼ぶ。`0x166918` は `0x161E58` の後、`0x15D414 (ハンドル, 0x202, 0, 0x400, セッション+0x161EC, &長さ)` で**外部データ (最大 0x400 バイト) を読み込み**、長さが 0xAF を超えれば 16 件のエントリをセッション +0x12050 の表へ構築する (各エントリは 7 バイトの日付時刻様フィールドを数値化した値を含む)。読み込み元の同定 (どのデバイス/ファイルか) は本段の範囲外。
- close は `0x162114` を呼び、`0x1635BC (KO)` で得たオブジェクトの +0x15C に対して `0x163D64 (…, 0x60000)` の終了処理を行う。

#### モード 0x200: open `0x2653F0` / close `0x16BBE8`

- open は `*(KO+0x1C) + 0x108` から 0x20 バイトを KO +0x3D0 へ複写し、KO +0x58 = 2、KO +0x1C = 0 と置いて `0x16B4E0` を呼ぶ。`0x16B4E0` は静的テンプレート (参照 `0x3D51A4` 付近の 0x58 バイト / 0x14 バイト) からセッション側の構造を構築する処理で、本段では冒頭部までの確認に留めた。close `0x16BBE8` は小さな終了処理。

**4 組を通じた判定**: モードハンドラはセッションの初期化・スロット割当て・パラメータ欄 (+0x34C/+0x350 等) の設定までであり、**KO の素材欄 (+0x94/+0xA4/+0x154、+0x1E0/+0x1E4、+0x38C/+0x390) や能力フラグ (+0x10)・状態ビット (+0x0C) を書くものは 1 つも無い**。

### 4.4 入口 (3): 暗号セットアップ `0x15490C` → `0x154594` — 共有バッファへのコマンドパケット構築

**呼出し条件** (`0x261B7C` 内): 束縛対象 KO の能力フラグ 0x20 が立ち、KO +0x0C の bit 1|2|4 が全て立ち、ストリーム文脈 +0x818C の値 (8 / 0x10 / 0x20) に対応する能力ビット (0x20 / 0x40 / 0x80) が KO にあること。呼出し前に `0x261B7C` はグローバルセル (0x6902E0) へストリーム文脈ポインタを置く。`0x15490C` 自体は引数を素通しする薄いラッパで、実体は `0x154594`。

**`0x154594` の処理** (第1引数 = KO):

1. バッファ基底 = `*(KO+0x48)` (セッションオブジェクト) とし、その **+0x4000** に 0x28 バイトのパケットを構築する。構築したパケットのポインタを第3引数 (呼出し側の出力欄) へ返す。
2. パケットレイアウト:

   | オフセット | 内容 |
   |---|---|
   | +0x00 | 0x02, 0x09, 0x01, 0x00, 0x00, 0x00, 0x28 (ヘッダ。末尾は全長 0x28) |
   | +0x07 | KO +0x154 の 16 バイトを複写 (`0x2ACFB0`) |
   | +0x17 | KO +0x1A7 / +0x1A6 / +0x1A5 の 3 バイトと、KO +0x1A4 のカウンタ (インクリメント後) の下位 1 バイト |
   | +0x1B | 権利属性 4 バイト (`0x154B90` が呼出し側構造体 {+0x08 種別, +0x0C/+0x0D フラグ} から構築。種別 1/2/5/その他で分岐) |
   | +0x1F 以降 | 本関数では書かない |

3. KO 内の素材 3 欄を更新する: `0x1544CC (KO+0xD4, KO+0x94, 0x10, カウンタ)`、`0x1544CC (KO+0xE4, KO+0xA4, 0x10, カウンタ)`、`0x1544CC (KO+0x164, KO+0x154, 0x10, カウンタ)`。
4. 最後に戻らないプリミティブ `0x3B8A64` を尾部呼出しする (第15段で致命的エラートラップの先として現れたものと同一アドレス。本経路ではエラーではなくタスク切替え相当の脱出とみられるが、性格の確定は本段の範囲外)。

**`0x1544CC` の変換**: 作業バッファに素材 16 バイトを置き、カウンタをビッグエンディアン 4 バイトで連結した 0x20 バイトを `0x1EFC2C` に通し、出力の先頭 16 バイトを宛先へ複写する。`0x1EFC2C` は 64 バイトブロック処理 (ブロック関数 `0x30A1E0`)、5 ワードの最終状態へのバイトスワップ、0x80 から始まるパディング定数 (参照 `0x52EC54` / ファイル 0x42EC54)、定数 0x5A827999 のコード内存在から、**160 ビットハッシュ (SHA-1 系) とみられる**。ただし初期値配列はイメージ内に連続した形では確認できておらず、同定は構造的推定に留める。いずれにせよ、ここでの変換は「素材 ‖ 連番カウンタ」のハッシュによる**作業欄の導出**であり、鍵素材そのものの生成ではない。

**判定**: DRMCTRL 側の消費構造は、記述子チェーンでも鍵ストアスロットでもレジスタ直書きでもなく、**セッションオブジェクト内の共有バッファ (+0x4000) にコマンドパケットを組み立てて実行側へ渡す**方式である。パケットに載る鍵関係の素材は KO +0x154 の 16 バイトのみで、それも平文の複写である (変換は KO 側の作業欄更新のためのハッシュのみ)。パケットの宛先 (どのプロセッサ/エンジンが +0x4000 を読むか) は本段では追っていない。

### 4.5 入口 (4): KO の構造と素材投入経路

**KO の欄配置** (本段と過去段の実読で確定したもの):

| 欄 | 意味 |
|---|---|
| +0x0C | 状態ビット (暗号セットアップの前提として bit 1|2|4 を要求) |
| +0x10 | 能力フラグ (0x20 = ハッシュ変換+パケット系、0x200 / 0x20000 / 0x100000 / 0x200000 = 複写系) |
| +0x1C | ポインタ (モード 0x200 の open が素材複写元として使い、使い終わると 0 に戻す) |
| +0x2C | ストリーム文脈への逆ポインタ (`0x261B7C` が束縛時に書く) |
| +0x48 | セッションオブジェクトへのポインタ |
| +0x54 | フラグ (bit0 でモード 0x1000000 の機器素材が生成/静的のどちらか) |
| +0x58 | モード 0x200 の open が 2 を書く |
| +0x94 / +0xA4 / +0x154 | 素材 (各 16 バイト)。暗号セットアップがハッシュ変換の入力にする。+0x154 はパケットにも載る |
| +0xD4 / +0xE4 / +0x164 | 上記素材のハッシュ変換出力 (作業欄) |
| +0x1A4 | 連番カウンタ。+0x1A5〜+0x1A7 は ID 様の 3 バイト |
| +0x1E0 / +0x1E4 | blob (長さ / 本体)。能力 0x20 系で `0x261260` が取り出す |
| +0x22C〜+0x34C | 属性テンプレート域。`drmctrl_open` が後段の `0x297B54` で既定値を書く (0x22C〜0x24C と 0x24C〜0x34C をゼロ初期化し、+0x242 に bit 0x10、+0x2FF = 0x0C、+0x243 に bit 0x80、+0x304 = 8、+0x22C に bit 0x80、+0x24C = 6) |
| +0x34C〜+0x388 | パラメータ/スロット番号域。モードハンドラと `0x2629F4` のテーブルが書き、`0x261B7C` が能力別にストリーム文脈へ複写する |
| +0x368 | フラグワード (束縛時の前提検査に使う。モード 0x10000 の open がゼロクリア) |
| +0x38C / +0x390 | blob (長さ / 本体)。能力 0x200 系で `0x261260` が取り出す |
| +0x3D0 | モード 0x200 の open が複写する 0x20 バイト |

**`0x261B7C` の能力フラグ別処理** (第15段の要約を本段の実読で精密化):

- 能力 0x20: 前提 (KO +0x0C の bit 1|2|4、ストリーム +0x818C との対応) を満たせば暗号セットアップ `0x15490C` を呼ぶ (§4.4)。
- 能力 0x200: 検証関数 `0x16C8B8 (0, KO)` (KO +0x368 の状態ビットとセッション状態の整合検査。変換はしない) の後、KO +0x378/+0x37C/+0x380/+0x388 の 4 ワードをストリーム文脈 +0x81F0〜へ複写する。この 4 ワードは §4.1 のテーブル (モード 0x200 / 0x20000) が予約した**スロット番号**である。
- 能力 0x20000: KO +0x36C の bit 0x40 を前提に、KO +0x370 / +0x378 (スロット番号) を複写する。
- 能力 0x100000 / 0x200000: KO +0x368 の bit 0 を前提に、KO +0x34C / +0x350 / +0x354 / +0x36C / +0x370 を複写する (パラメータとスロット番号の混合)。

すなわち複写系の能力でストリーム文脈へ渡るのは**スロット番号と小さなパラメータ**であり、鍵バイト列そのものは渡らない。鍵バイト列が関わるのは能力 0x20 の暗号セットアップ系のみで、その素材は KO +0x94/+0xA4/+0x154 に既に在ることが前提である。

**書き手の探索結果 (陰性の範囲)**: 本段で実読した `drmctrl_open` / `drmctrl_close` / `0x2629F4` / ハンドラ 8 関数とその主要な呼出し先、`0x261B7C`、`0x261260`、`0x154594` 一式、および過去段で実読した DRMCTRL 周辺関数の範囲では、**KO +0x94/+0xA4/+0x154、+0x1E0/+0x1E4、+0x38C/+0x390、能力フラグ +0x10、状態 +0x0C への書き手は存在しない**。AKE の素材はセッションオブジェクト側に在り (第6・7段)、セッションオブジェクトから KO の素材欄への橋渡しは、この読み範囲の外にある。残る候補は、`drmctrl_open` が文脈ごとに生成する **`uist_drmctrl` タスクの本体** (とそこから到達するホストコマンド処理) である。タスク生成 `0x3B4ED0` の第1引数は RAM 上のタスク制御ブロック (参照 `0x398CCC`、ファイルイメージ内はゼロ域) であり、本段ではタスク本体の入口を同定できなかった。

### 4.6 入口 (5): 文脈スロット欄 (+0x49C/+0x4B4/+0x4B8) の消費側

- 予約側は第15段 §4.2 の通り (モード 0x100000 で +0x4B4 ← `0x1BC3E8 (2)`、+0x4B8 ← `0x1BC46C (2)`、+0x49C ← `0x1BC46C (2)`。モード 0x200000 では +0x498/+0x494 の値が異なる)。
- 消費側として確認できたのは、GENERIC の AACS_BLK 束縛 `0x20D918` が文脈 +0x4B8 起点の 4 ワードをストリーム文脈 +0x8BC (素材欄) へ複写する 1 件のみ (第15段 §4.3)。スロット番号が入っているはずの欄を「素材」として複写する形であり、複写先の使われ方 (SCRAMBLER の IVDR 的な素材欄) とあわせ、意味論の確定はできていない。
- +0x49C / +0x4B4 の消費者、およびモード 0x100000 / 0x200000 (ハンドラ表にエントリを持たない) の close 側でのスロット解放は、本段の読み範囲では未同定である。`drmctrl_close` はハンドラ表の close ハンドラを呼ぶのみで、これらのモードでは表に一致が無く何も呼ばれない。

### 4.7 入口 (6): `0x261260` の対象同一性 — 解決

**`0x261260` の全行実読** (第15段のダンプで再確認):

```c
FUN_00261260(stream_ctx, len_out, dst):
    KO = *(stream_ctx + 0x825C)
    if KO == 0: return 1
    if (KO+0x10 & 0x20) == 0:
        if (KO+0x10 & 0x200) == 0: *len_out = 0; return 0
        if *(stream_ctx + 0x81D0) == 0: return 1
        *len_out = *(KO + 0x38C); memcpy(dst, KO + 0x390, len)
    else:
        *len_out = *(KO + 0x1E0); memcpy(dst, KO + 0x1E4, len); return 0
```

すなわち本関数は「束縛済み KO の blob を取り出すゲッタ」であり、第1引数は +0x825C (KO ポインタ) と +0x81D0 (束縛済み文脈ポインタ) を持つ**ストリーム文脈**である。呼出し側は巨大関数 `0x23FFC8` の case 0x11 分岐 (0x24E7B4) で、第13段のデコンパイルでは `FUN_00261260 (*unaff_r21, unaff_r15 + 0x8b4, unaff_r15 + 0x8b8)` の形であり、長さの宛先と blob の格納先は当該ストリーム文脈の +0x8B4 / +0x8B8 である (レジスタの由来が異なる点は第13段の読みの留保として残るが、`0x261260` 自身が読む +0x825C/+0x81D0 が `0x261B7C` の書くストリーム文脈の欄であることと矛盾しない)。

**判定**: 対象オブジェクトはストリーム文脈で**同一**である。docs/27 の留保は「同一オブジェクトだが、+0x8B4/+0x8B8 の意味論は経路依存」という形で解消する。GENERIC 経路ではスロット番号 (アロケータ由来) が入る欄が、AACS 状態機械の経路では KO blob の (長さ, 格納先バッファ) として使われる。両経路が同一ストリームで同時にこの欄を取り合うことは、モード上 (AACS 系の状態機械は OPEN_STREAM 側、スロット予約は GENERIC 側) 考えにくいが、その排他性の証明はしていない。

## 5. 判定

- **入口 (1)**: `0x2629F4` は DRMCTRL 文脈の一般初期化ではなく、モード別静的テーブル駆動のスロット予約/解放関数である。6 モード分のテーブルを全列挙した。KO の初期値に OTP / チップ ID 由来のものは本関数には無い。
- **入口 (2)**: ハンドラ表 `0x3ED500` は静的初期値を持ち、4 モード分の open/close ハンドラ対が確定した。第15段の「実行時登録」読みと第3段の「ハンドラ表ではない」読みは、いずれも本段の実測 (ファイル 0x2ED500 の内容と現在の関数切り) により supersede される。実行時登録の積極的証拠は無い (census の範囲は §4.2 の通り)。
- **入口 (3)**: 暗号セットアップの消費構造は「セッション共有バッファへのコマンドパケット構築」と確定した。記述子・スロット・レジスタのいずれでもない。パケットに載る鍵素材は KO +0x154 の 16 バイトの平文複写のみで、FW 側の変換は KO 作業欄のハッシュ導出に限られる。
- **入口 (4)**: SECUREDTS の鍵の「束縛以降」は確定した: 能力 0x20 の KO では、KO 内素材 (+0x154) がコマンドパケットで実行側へ渡り、複写系の能力ではスロット番号とパラメータがストリーム文脈へ渡る。しかし**素材が KO へ入る経路は未同定**であり、SECUREDTS の実効鍵の最終的な出所 (AKE 由来か、ホストコマンド由来か) は本段では確定しなかった。読み範囲と候補は §4.5 の通りで、`uist_drmctrl` タスク本体が次の入口である。
- **入口 (5)**: +0x4B8 の消費 (複写) のみ確認。+0x49C/+0x4B4 の消費者とハンドラ無しモードの解放は未同定。
- **入口 (6)**: 解決。同一オブジェクト (ストリーム文脈) で、意味論は経路依存。

## 6. 残件

1. **KO 素材の書き手と `uist_drmctrl` タスク本体**: KO +0x94/+0xA4/+0x154、+0x1E0/+0x1E4、+0x38C/+0x390、能力フラグ +0x10、状態 +0x0C の書き手は未同定。タスク生成の引数 (RAM のタスク制御ブロック) からタスク入口を辿るか、AKE 完了経路 (セッションオブジェクト側) から KO へ橋渡しする関数を探すのが次の入口。ここが SECUREDTS の実効鍵の出所の最後の未確定点である。
2. 文脈スロット欄 +0x49C/+0x4B4 の消費者、モード 0x100000/0x200000 の close 側スロット解放、`0x2629F4` の解放側呼出し元。
3. コマンドパケット (+0x4000) の宛先: どのプロセッサ/エンジンがセッションオブジェクト +0x4000 を読み、ヘッダ (02 09 01 …) が何のコマンドに対応するか。
4. `0x1EFC2C` のハッシュ同定の確定 (初期値の出所の確認)。機能上の結論 (素材 ‖ カウンタのハッシュ導出) には影響しない。
5. モード 0x20000 の open が読む外部データ (`0x15D414`、コマンド 0x202) の読み元の同定と、構築される 16 件表の意味論。
6. エンジン内部での鍵の扱い (E2 候補 (i)) は、従来通り FW イメージからは観測不能で実験系の問いとして残る。

第17段 ([docs/31](31_xcode_fw_drm_phase17.md)) で本段の残件 1・3 が進展し、本段の記述 2 件が訂正された:

- **残件 1 (KO 素材の書き手) は中核を解決**: `uist_drmctrl` タスク本体は `0x398CCC` であり、その内部のコマンド処理 (能力 0x20 のコマンド 0x15/0x11/0x13 のハンドラ) が KO の素材欄・導出欄・状態欄を書く。+0x154 の素材は共有域メールボックス越しにエンジンが生成した値である。blob 欄 (+0x1E0/+0x1E4、+0x38C/+0x390) と能力フラグ +0x10 の書き手は第17段の実読範囲でも未同定。
- **訂正 1**: §4.5 の「タスク生成 `0x3B4ED0` の第1引数は RAM 上のタスク制御ブロック (参照 `0x398CCC`、ファイルイメージ内はゼロ域)」は誤読だった。`0x398CCC` はタスク本体の入口そのもので、実体は +0x100000 ビューのブロックに属するファイルオフセット 0x298CCC の実コードである (ファイル 0x398CCC が全ゼロなのはビュー取り違えによる)。ハンドラ表 (ビュー 0x3ED500 → ファイル 0x2ED500) と同型の構造がコードにも及んでいた。
- **訂正 2**: §4.4 で暗号セットアップの尾部として現れた `0x3B8A64` (第15段では「戻らないプリミティブ/タスク切替え相当の脱出」とされたもの) は、実体は AUX レジスタ 4 から現プロセッサ/文脈の識別子を返すゲッタであり、通常復帰する。非復帰という読みは Ghidra の誤判定に基づくもので、本関数を含む関数の本体が切断されていた原因でもある。
- **残件 3 (+0x4000 の宛先) は部分進展**: 束縛時パケットの呼出し側として、タスク側の遅延束縛 `0x262C38` を同定した。+0x4000 を直接読む命令は第17段の実読範囲にも無く、読み手は登録先のエンジン/ストリーム機構側という範囲明記つきの未確定として残る。なおコマンド応答も +0x4000 に組まれ、送信関数 `0x305B78` 経由で送出されることは同定済みである。
