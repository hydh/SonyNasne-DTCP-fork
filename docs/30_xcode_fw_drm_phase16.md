# XCode ファームウェア DRM モジュール解析 第16段

2026-11-15。DRMCTRL 内部に入る段。第15段で、SECUREDTS (復号) の鍵束縛は鍵ストアスロットとは別系統の **DRMCTRL 鍵オブジェクト機構** (`0x261B7C`) であることが確定した。本段はその内側 — 鍵オブジェクト (KO) の初期化・素材の出所・エンジンへの受け渡し — を追い、SECUREDTS の実効鍵がどこから来るのかを静的に確定することを狙う。

手法は第9段の M1–M6 を踏襲 (Ghidra 実読を主とし、GPL ドライバ一次資料で配送・構造体・モード定義を照合)。素材は開発側作業領域 `2026-11-13-fw-drm/phase16/` (Ghidra プロジェクト `ghp16` = 第2 FW、`ghp16m` = 主 FW、いずれも phase15 プロジェクトの複製)。アドレス表記は各イメージのロードベース基準 (主 FW = 0、第2 FW = 0xB00000) で、ファイルオフセットと一致する (+0x100000 ビューのライブラリについてはその旨を明記する)。本段の主対象は主 FW の DRMCTRL 系ライブラリ域である。

## 2. 課題と入口

### 入口 (1) DRMCTRL 初期化 `0x2629F4` の実読

`drmctrl_open` (`0x261520`) が文脈登録時に呼ぶ初期化関数 (第15段 §4.2)。文脈構造 (作業域 0x3F8 バイト) の初期化内容、6 件の鍵オブジェクト表 (`0x69735C`) の初期状態、初期値の出所 (静的データか、OTP / チップ ID 由来か、ゼロか) を確定する。本関数は計算呼出し経由でスロットアロケータ `0x1BC3E8` を呼ぶことも分かっている。

### 入口 (2) モード別ハンドラ表 `0x3ED500` の列挙

`drmctrl_open` がモード一致で引く表 (ストライド 5 ワード)。静的イメージの当該範囲は初期値を持たず実行時登録とみられる (第15段 §4.2) ため、登録側 (表への書込み元) を census して、誰がいつ何を登録するかを洗う。モードとハンドラの対応を確定し、SECUREDTS に関わるハンドラを特定する。

### 入口 (3) 暗号セットアップ `0x15490C` の実読

鍵オブジェクト束縛 `0x261B7C` が、KO の能力フラグ 0x20 の場合に呼ぶ関数 (第15段 §4.1)。鍵オブジェクトがエンジンへどう渡るか (記述子経由か、スロット経由か、レジスタ直書きか) を実読し、DRMCTRL 側の消費側の構造を確定する。

### 入口 (4) 鍵オブジェクトへの素材投入経路

`0x261B7C` が束縛する KO の素材欄 (作業域 +0x34C〜+0x378、第15段で文脈 +0x81EC〜+0x8248 へ複写されることを確認) は、誰がいつ書くのか。候補: ホストコマンド (どの FN か)、AKE の交換手続き (gen_kauth / setexchgkey — 第6段で「文脈内の生成値と相手方素材の 12 バイト XOR が交換鍵」であることがコードで確定しているが、対象は AKE セッション文脈であり DRMCTRL の KO と同一かは未確認)、OTP / チップ由来の導出、B-CAS・デスクランブラ側からの供給。SECUREDTS の実効鍵の出所を、事実の取れる範囲で確定する。

### 入口 (5) DRMCTRL 文脈自身のスロット欄 (+0x49C/+0x4B4/+0x4B8) の消費側

モード 0x100000 / 0x200000 のときに `drmctrl_open` が予約するスロット対 3 組 (第15段 §4.2)。予約したスロット番号を誰がどう使うか (SCRAMBLER 的な投入を受けるのか、記述子に載るのか) を追う。

### 入口 (6) `0x261260` の対象オブジェクト同一性

docs/27 §2.2 以来の留保。巨大関数 `0x23FFC8` の case 0x11 分岐から呼ばれる `0x261260` は、`0x261B7C` が格納する KO 作業域ポインタ (文脈 +0x825C) を読むことが第15段で判明している。本段の DRMCTRL 実読と交差したら、対象オブジェクトがストリーム文脈と同一か否かを判定する。

## 3. 前提 (確定済み事項)

- 録画保存は非対称構成: SECUREDTS (復号) = DRMCTRL 鍵オブジェクト束縛 (`0x261B7C`)、GENERIC-AES (保存暗号化) = 鍵ストアスロット + SCRAMBLER CW。保存される `.dat` の鍵は GENERIC 側であり、残る未知はエンジン内部変換の有無のみ ([docs/29](29_xcode_fw_drm_phase15.md))。
- `0x261B7C` は鍵指定ペア (要求 +0x38/+0x3C、+0x40/+0x44) を DRMCTRL 文脈の 6 件表 (`0x69735C`) から解決し、ポインタをストリーム文脈 +0x81D0 / +0x81D4 へ、KO 作業域ポインタを +0x825C へ格納する。KO の能力フラグ (作業域 +0x10) と文脈 +0x818C (8/0x10/0x20) の対応を検証し、フラグに応じて KO 素材欄 (作業域 +0x34C〜+0x378) を文脈 +0x81EC〜+0x8248 へ複写する。フラグ 0x20 では暗号セットアップ `0x15490C` を呼ぶ。鍵ストアスロットへのアクセスも +0x8B0 台へのアクセスも無い ([docs/29](29_xcode_fw_drm_phase15.md) §4.1)。
- `drmctrl_open` (`0x261520`) は DRMCTRL 文脈 (最大 6 件、表 `0x69735C`、ストライド 0x10) を登録し、文脈 +0x148 (作業域) がゼロなら 0x3F8 バイトをゼロ初期化して初期化関数 `0x2629F4 (作業域, モード, 0)` を呼ぶ。モード 0x100000 / 0x200000 のときのみ文脈 +0x49C / +0x4B4 / +0x4B8 へスロット対 3 組を予約する。本体に鍵素材の読み書き・変換は無い ([docs/29](29_xcode_fw_drm_phase15.md) §4.2)。
- AKE 実体 (gen_kauth / setexchgkey) では、交換鍵 12 バイトがセッション文脈内の 2 つの 12 バイト列 (gen_kauth の生成値と相手方素材) の XOR で導出されることがコード実読で確定している。gen_kauth の中核計算は HW RSA/ECC エンジンのドライバである。ただし対象は AKE のセッション文脈であり、DRMCTRL の KO との同一性は未確認 ([docs/14](14_xcode_fw_drm_phase6.md) §5、[docs/15](15_xcode_fw_drm_phase7.md))。
- DRMCTRL 実行コードは +0x100000 アドレスビューのライブラリとして到達した経緯がある ([docs/13](13_xcode_fw_drm_phase5.md))。アドレスの読み替えが必要な箇所ではその旨を明記する。
- 変位ベースの全数 census は方法限界が実測済み (分割アドレッシングで既知のアクセスすら拾えない) のため、全数否定の根拠には使わない ([docs/27](27_xcode_fw_drm_phase13.md) §2.4)。
