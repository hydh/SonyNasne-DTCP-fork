# 32. pydtcpip (オープンソース DTCP-IP 実装) の調査 — 構成・証明書モデルと nasne への適用可能性

2026-11-15 に公開されたオープンソースの DTCP-IP 実装 **pydtcpip** (著者: tsukumijima、https://github.com/tsukumijima/pydtcpip) を静的に調査した記録 (2026-11-15 実施)。対象はバージョン 0.1.0 (コミット `e726fc5`) のソースツリーと README・付属文書で、**実機への接続・実行は一切行っていない** (コードとドキュメントの読みのみ)。

**現在の到達点**: pydtcpip は DLNA/UPnP の発見・一覧取得から DTCP-IP の相互認証 (AKE)、暗号化転送 (PCP) の復号、Move 転送までを一貫して実装した **Sink (受信側) 専用** の Python ライブラリ + 参照 CLI で、東芝のテレビ・レコーダー 2 機種では実機検証済み。**nasne 向けのデバイスプロファイル (`sie_nasne`) が実装済みだが、著者に実機がなく未検証** と明記されている。認証に必要なデバイス証明書と秘密鍵は **同梱されておらず、利用者が正規のペアを用意する前提** で、この点が nasne へ接続できるかの成否を分ける。本書の評価では、正規 Sink として nasne から配信を受けて復号する経路は、既存の 2 つの線 (PC 復号・オラクル方式) とは別の **「第 3 の線」になり得る** と判断する (成立条件と未確定点は §7)。

## 2. 実装の全体像 (事実)

### 2.1 位置づけ

- **Sink (受信側) 専用**。クライアントとして録画機器 (Source) へ接続する機能と、送り出しダビングの受け側として待受ける機能を持つ。**DTCP Source (配信サーバ) は実装しない** (README の仕様範囲表に明記)。
- 非同期 (asyncio) Python ライブラリ (`DLNAClient`、`DTCPClient`、`DubbingReceiver`) が本体で、動作確認・研究用の参照 CLI (`pydtcpip` コマンド: `discover` / `info` / `stream` / `move` / `resume` / `receive` / `dump`) が同梱される。
- 対応範囲 (README の仕様範囲表とコードの対応):
  - UPnP/DLNA: SSDP 発見・広告、ContentDirectory の Browse、CreateObject / DestroyObject、GENA イベント通知 (受け側)、`protocolInfo`、`TimeSeekRange`、`X_GetDLNAUploadProfiles`。予約録画・EPG・再生制御は対象外。
  - DTCP-IP 認証/暗号: **Full Authentication (ECDSA / ECDH)**、IP TTL = 3 の制限、RTT 近接チェック、**PCP (AES-128-CBC 復号と E-EMI 取得)**、SRM の署名検証・失効チェック・相互更新。Enhanced Full Authentication、PCP2、宅外リモートアクセス、DTCP+ は対象外。
  - 転送: 通常ストリーミング (コピーを消費しない)、GET Move (`FINALIZE` / `COMPLETE` / `CANCEL` / 再開)、POST Move 受信 (送り出しダビングの受け側)。
- 転送品質は保存形式 (`DLNA.ORG_CI=0`) を優先し、無劣化 (DR 録画なら放送 MPEG-2 のまま) を既定とする。

### 2.2 AKE (相互認証) の実装 — `pydtcpip/dtcp/ake.py`

Sink としての Full Authentication が一通り実装されている。

- 制御フレーム (11 バイトヘッダ) のコマンドとして CHALLENGE (0x01)、RESPONSE (0x02)、EXCHANGE_KEY (0x03)、SRM_UPDATE (0x04)、RTT_SETUP / RTT_TEST / RTT_READY / RTT_VERIFY (0x11 / 0x12 / 0x91 / 0x92)、Move 系の MV_INITIATE (0xA0)、MV_EXCHANGE_KEY (0x21)、MV_FINALIZE (0x22)、MV_COMPLETE (0x23)、MV_CANCEL (0x28) を扱う。
- 手順: (Move 時は MV_INITIATE を先行) → 自分の証明書 (88 バイト) と nonce (16 バイト) を CHALLENGE で送る → 相手の CHALLENGE (nonce + 証明書) を受けて **相手証明書の DTLA 署名検証と SRM 失効チェック** を行う → 相手の RESPONSE 署名 (ECDSA-SHA1) を検証 → 一時鍵による ECDH で共有秘密を求め、その x 座標の下位 96 ビット (12 バイト) を認証鍵とする → 自分の RESPONSE (一時公開鍵 + SRM 版/世代 + 署名) を送る → 相手主導の RTT 近接チェックに応答 (相手の測定往復は 7 ms 制限とコメントされ、MAC を事前計算して即応する実装) → EXCHANGE_KEY (通常) / MV_EXCHANGE_KEY (Move) で交換鍵を受け取る (認証鍵との XOR、Move 時は SHA1 由来の別マスクで復元)。
- SRM は双方向に扱う: 相手が新しい SRM を持てば受け取って署名検証し保存コールバックへ渡し、自分の SRM が新しければ相手へ送る。認証用 TCP 接続は **IP TTL = 3** をソケットに設定して開く (TTL が大きいと CHALLENGE 受理後に切断するレコーダーがある旨のコメントがある)。
- 認証の入口はメディアへの HTTP HEAD 応答で、Content-Type (`application/x-dtcp1`) のパラメータ `DTCP1HOST` / `DTCP1PORT` から認証先を得る (DTCP-IP の標準的な形)。GET Move では `BLKMove.dtcp.com` ヘッダに交換鍵ラベルを載せる。

### 2.3 暗号まわり — `pydtcpip/dtcp/crypto.py`、`pcp.py`、`srm.py`

- DTCP の楕円曲線 (公開仕様ではパラメータが省略されている独自曲線、160 ビット級) のパラメータ、**DTLA の公開鍵 2 件** (証明書・SRM の署名検証用)、E-EMI ごとのコンテンツ鍵導出定数と IV 定数がコードに内蔵されている。公開仕様 (Informational Version) だけでは実装できない部分を、実機挙動との整合で補った互換実装という位置づけ (著者明記)。
- 証明書検証 (`verify_certificate`): 88 バイトのベースライン証明書であること (先頭バイト = 種別 1、SRM 世代上限の検査を含む)、先頭 48 バイトに対する末尾 40 バイトの DTLA 署名 (ECDSA-SHA1) の検証、公開鍵 (証明書の 8〜48 バイト) の取り出し。機器 ID は証明書の 3〜8 バイト (SRM 失効チェック用)。
- コンテンツ鍵導出 (`derive_content_key`): 交換鍵 (12 バイト) + E-EMI 別の定数 (12 バイト) + PCP の nonce (8 バイト) から AES-128-ECB ベースの導出でコンテンツ鍵 (16 バイト) と CBC の IV (16 バイト) を得る、いわゆる J-AES 系の導出関数が実装されている。
- PCP (`pcp.py`): 14 バイトヘッダ (種別、暗号アルゴリズム、E-EMI、交換鍵ラベル、nonce、コンテンツ長) を解釈し、AES-128-CBC で復号する。HTTP のチャンク境界に依存しない読み取りを行う。
- SRM (`srm.py`): 世代ごとの累積署名を DTLA 公開鍵で検証し、失効機器 ID (個別指定と範囲指定) を読み取る。`check_device` で相手・自分の双方の証明書の失効を検査する。
- Move の確定 (`move.py`、`transfer.py`): 受信データの永続化 (`Sink.persist()`) が完了してから `FINALIZE` を送り、応答 MAC を検証してから `Sink.commit()` と `COMPLETE` へ進む。確定応答が失われた場合は交換鍵と nonce を `MoveResumeState` として保持し、データを再受信せず確定だけを再開できる。

### 2.4 DLNA 側と受信データ形式

- 発見は SSDP (ユニキャスト応答は UDP 57000)、一覧は ContentDirectory の Browse。DIDL-Lite の解析では ARIB の私用領域文字を Unicode へ正規化し、番組メタデータは受信データ (`.m2ts`) と並べて DIDL-Lite XML (`.xml`) をサイドカー保存する。
- 受信データは 192 バイトパケットのタイムスタンプ付き TS (M2TS 形式)。内容は対象番組のみのパーシャル TS (PAT / PMT / DIT / SIT を含む)。
- 機種依存の吸収は「プロファイル」 (継承ツリー: `generic` → `toshiba` → `toshiba_regza_tv`、`generic` → `sie_nasne`) に分離され、残コピー数の読み取りや HTTP ステータスの解釈だけを差し替える設計。プロファイルの混入を防ぐため、テストで import 境界を AST レベルで検査している。

### 2.5 診断用 `dump`

- `dump` サブコマンドは **資格情報なし・コピー消費なし** で機器の description、サービス定義、一覧、メディアへの HEAD 応答を採取できる。`--mask-private` で番組名・機器名・UDN・IP・MAC 等をマスクして互換性報告に使える形で出せる。未検証機種の適合調査の第一歩として設計されている。

## 3. 証明書の扱い (最重要、事実)

### 3.1 同梱なし — 利用者が正規ペアを用意する前提

- README の CLI 手順 §1「Preparing credentials」に明記: **受信には DTCP デバイス証明書 (88 バイト) と対応する機器秘密鍵 (20 バイト) が必要で、このパッケージはプロトコル実装のみを提供し、証明書も秘密鍵も含まない。利用者が自分の資格情報を用意すること。**
- 与え方は 16 進文字列で、`credentials.env` ファイル (`PYDTCPIP_CERTIFICATE`、`PYDTCPIP_PRIVATE_KEY`) または同名の環境変数。SRM は事前準備不要 (初回は版 0 で認証し、相手から受けた新しい SRM を `srm.bin` に自動保存して次回以降使う)。
- コード側でも `DeviceCredentials` はバイト列を外部から受け取るだけのモデルで、生成・配布の機能はない (`store.py` はファイル読み書きのみ)。著者の開発規約 (AGENTS.md) にも「証明書・秘密鍵は利用者が提供する」「SRM をパッケージに同梱しない」と明記されている。

### 3.2 ペアの正当性はローカルで検証できる

- `DeviceCredentials` は構築時に (1) 証明書の DTLA 署名検証 (コード内蔵の DTLA 公開鍵による ECDSA-SHA1 検証)、(2) 20 バイト秘密鍵から導いた公開鍵が証明書の公開鍵と一致すること、を検証する。**自己署名や適当な鍵ペアではこの検証を通らない** — 通るのは DTLA に署名された実在の証明書と、その正規の秘密鍵のペアだけである。
- したがって「接続できるか」は、プロトコルの問題である前に **DTLA 署名の正規ペアを合法的に用意できるか** の問題になる。合計 108 バイトの素材である。

### 3.3 正規クライアントにおける資格情報の来歴 (README の研究記述)

著者は README の研究資料の節で、汎用 OS 向け視聴アプリの資格情報の持ち方を 2 型に整理している (特定の製品名や手法の特定は、著者自身の方針で避けられている。本書でも特定はしない)。

- **共有固定鍵の配布型**: 初回起動時にオンラインの配布 API から証明書と秘密鍵を取得する型。デバイス識別子を変えて要求しても同じ証明書 (88 バイト) と秘密鍵 (20 バイト) が返り、全端末が同じ機器 ID を共有する。
- **要求ごとの個別発行型**: 要求のたびに異なる証明書・秘密鍵・初期 SRM が発行される型。クライアントアプリ同士で同じ鍵配布基盤 (SaaS) を使う場合もある。
- いずれの型でも、通信用の認証素材と応答の復号処理がアプリ内のコードとネイティブライブラリに完結しているため、著者は「復号処理そのものを再実装せず、バイナリの復号ルーチンを CPU エミュレータ上で実行して出力を得る」アプローチと、得られたペアを `DeviceCredentials` の署名・公開鍵検証でオフライン判定する閉ループを、技術的な調査手法として提示している。
- SRM による失効の運用実態についても言及がある: 実機との相互認証で **版 2・十数件の機器 ID だけを含む古い SRM を保持し続けるレコーダー** が観測されたこと、クライアント側にも最新 SRM を定期取得する経路や失効後の再取得経路が無い場合があることから、「仕様に失効機構があることと、実効的な失効が運用できることは別」と論じている。

### 3.4 プロトコル構造としての含意 (著者の主張)

- README は、DTCP-IP の相互認証が暗号学的に証明できるのは「相手が有効なデバイス証明書に対応する秘密鍵を使えること」までであり、Source 側は接続先で公式アプリが動いているか・復号後に再保護されているかを検証できない、と整理している。そのうえで **正規の証明書と秘密鍵を持つ受信実装は、通常の機器と同じ手順で相互認証と受信を完了できるようプロトコルが設計されている** というのが著者の主張であり、pydtcpip はその前提で実装されている (東芝 2 機種での実機検証がその傍証として提示されている)。

### 4.2 nasne プロファイル (`pydtcpip/dlna/profiles/sie_nasne.py`) の内容

プロファイルが担うのは DLNA 層の機種差 3 点だけで、AKE や転送は汎用経路に乗る設計になっている。

1. **一致条件**: デバイスディスクリプションの modelName が `nasne` であること。
2. **残コピー数**: DIDL-Lite の Sony 拡張要素 `av:COGCount` (名前空間 `urn:schemas-sony-com:av`) から残コピー数を読む。コード内コメントに **「共通フィールドと違い、最終ムーブを含むかどうかは実機未検証」** と明記されている (汎用側の規約では表示上の残数は最終ムーブを含まず、0 = ムーブのみ残り、と整理されている)。
3. **HTTP 403 の解釈**: 一覧・メディア要求への 403 を「この PC は nasne にクライアントとして許可されていない。nasne HOME のメディアサーバー設定 > クライアント機器管理で許可すること」という `ClientNotAllowedError` として解釈する。テスト (`tests/test_profiles.py`) もこの 403 解釈のみを対象にしている (nasne の実機フィクスチャは存在しない)。

- nasne への言及はリポジトリ全体でこのプロファイルとそのテスト、README の対応表だけに限られる。DMS のポートや URL 形式など、転送先の詳細は DIDL の `res` 要素から得る汎用設計のため、プロファイル側に nasne の転送詳細は書かれていない。

### 4.3 ムーブ/コピー制御との関係

- `move` (GET Move) と `receive` (送り出しダビング受信) は **Source のコピーを 1 回消費する**。残りが最終ムーブのみの場合やコピーワンス録画では元録画が削除され復元できないため、CLI では実行前にタイトルと残コピー数を表示して確認を求める (ライブラリ API の `move()` は確認を出さないので呼出側の責任と明記)。
- `stream` (ストリーミング) は **コピーを消費せず**、元録画を残したまま復号済み TS を逐次出力する。交換鍵のローテーション時は再認証して継続する。`TimeSeekRange` による範囲指定にも対応する。
- 保護情報は出所ごとに分離管理される: 一覧メタデータの残コピー数、`protocolInfo` の `DTCP.COM_FLAGS` (bit31 = ムーブ対応、bit30 = トランザクション型ムーブ対応)、転送開始後に PCP の E-EMI から分かる転送時コピー制御、の 3 系統を混同せず、それぞれ取得状態 (`known` / `not_observed` / `omitted` / `unsupported`) 付きで保持する。

## 6. docs/21 (torne mobile 解析) との突き合わせ (事実)

- docs/21 で torne mobile から読み取った DTCP-IP の構造 — 転送メタデータからの `DTCP1HOST=` / `DTCP1PORT=` の受け渡し、HTTP 拡張ヘッダ `BLKMove.dtcp.com`、クライアント (Sink) 側で AKE と復号を完結させる設計 — は、pydtcpip の実装方式と一致する。docs/21 §7 が「自作 DTCP-IP クライアントを実装・検証する場面の一次資料になる」とした痕跡群について、実際に動くオープン実装が対応物として現れた形になる。
- docs/21 では nasne 側に DTCP-IP クライアントを管理する面があること (WebAPI の `status/dtcpipClientListGet`、`config/dtcpipClientStop`、クライアント側の `CanBecomeDtcpipClient`) を確認していた。pydtcpip の nasne プロファイルが前提とする「未登録クライアントへの 403 と nasne HOME でのクライアント機器管理による許可」は、これと整合する運用像である (解釈)。
- docs/21 で torne 側に見えた DLNA プロファイル名は `DTCP_AVC_TS_JP_AAC_T` 等の AVC 変換形式が中心だった。pydtcpip は保存形式 (`DLNA.ORG_CI=0`) を優先選択する設計であり、nasne が保存形式リソースをどう提示するか (protocolInfo の実値) は実機でしか分からない (未確定、§7.3)。

## 7. 評価 (解釈・評価 — 事実とは分けて読むこと)

### 7.1 自作クライアントの基盤として

- AKE・PCP 復号・Move の実働コード、実機検証済みの既知値テスト、機種差をプロファイルに閉じる設計が揃っており、DTCP-IP スタックをゼロから実装するのに比べ大幅に進んだ出発点である。docs/21 の API 面 (WebAPI 62 件、UPnP テンプレート) と合わせると、「公式 FW の nasne に対する自作クライアント」のうち **再生・転送 (Sink) 側は pydtcpip が、予約・機器管理側は WebAPI が** 担う形の設計が描ける (予約録画そのものは pydtcpip の対象外)。
- ライセンスは MIT で、組み込み・改変の自由度は高い。

### 7.2 「第 3 の線」としての見立て

- 既存の 2 線は、保存 `.dat` の復号をめぐるものだった — (1) PC 復号: 保存鍵はファームウェア側で解決され PC 側に素材がない、(2) オラクル方式: 実機チップを復号オラクルとして使う。これに対し pydtcpip の経路は **保存鍵には触れず、正規 Sink として配信 (DTCP-IP) を受け、クライアント側で復号して平文 TS を得る** もので、鍵の系統が根本的に異なる (docs/21 §4.3 の「配信鍵と保存鍵は別系統」と一致)。本人が「DTCP-IP 経由で復号できるならそれもあり」としていた方向そのものであり、**第 3 の線として有望** と評価する。
- ただし成立条件が 3 つある。(i) DTLA 署名の正規の証明書 + 秘密鍵ペアを用意できること (§3 — ここが最大の関門で、pydtcpip 自体は素材を提供しない)。(ii) nasne 側の AKE がその証明書を受け付けること (§7.3)。(iii) nasne HOME でクライアントとして許可されること (§4.2)。
- 利用形の限定: この線で平文が得られるのは **nasne 実機が稼働し、DTCP-IP Source として配信できる間** に限る。既に取り出してある `.dat` の単体復号には使えない。一方で、本プロジェクトの目的 (Sony のサポート終了後も公式 FW のまま録画・再生を使い続ける) に対しては、実機が生きていることが前提の利用形であり、目的と矛盾しない。
- 救出用途での手順の評価: 録画の救出が目的なら、コピーを消費する Move より先に、**コピーを消費しない `stream` で平文 TS が得られるかを確認する** のが安全な順序になる (Move は最終ムーブのみの録画では元を消す)。また実機検証の最初の一歩は、資格情報なし・コピー消費なしの `dump` で nasne の応答を採取し、`sie_nasne` プロファイルの前提 (modelName、DIDL の形、protocolInfo) を照合することになる。

### 7.3 実機検証が必要な未確定点

1. **DIDL / プロファイル適合**: `sie_nasne` の一致条件 (modelName) が実機の description と一致するか。`av:COGCount` の値の意味 (最終ムーブを含むか — コード内でも未検証と明記)。保存形式リソースの `protocolInfo` の実値 (`DLNA.ORG_CI`、`DTCP.COM_FLAGS` のムーブ可否ビット)。
2. **クライアント登録**: nasne HOME のクライアント機器管理に汎用 PC を登録でき、403 が解けるか。登録が何 (機器情報・アドレス等) に紐づき、AKE の証明書とどう関係するか。
3. **AKE の受け入れ**: nasne 側 AKE が、提示するデバイス証明書の種別 (携帯アプリ等へ配布される種別の証明書を含む) を受け付けるか。証明書のカテゴリや機器種別で弾く実装があり得るかは、コードの外からは分からない。SRM の版・世代の整合 (nasne が保持する SRM と、提示側証明書の世代上限) も含む。
4. **近接チェック**: RTT 近接チェックと TTL = 3 が同一 LAN 内で通過するか (東芝機では通過実績があるが、nasne の実装差は未確認)。
5. **転送の実挙動**: DMS (docs/21: ポート 60151、ObjID 形式 URL) への HEAD/GET で `DTCP1HOST` / `DTCP1PORT` が返るか、交換鍵ローテーションの有無と頻度、`TimeSeekRange` への応答。
6. **Move の可否**: nasne の録画が GET Move を受け付けるか (`DTCP.COM_FLAGS` bit31 の提示と実挙動の双方)。受け付けない場合でも `stream` は別経路として成立し得る。
7. **資格情報の調達そのもの**: §3.3 の 2 型のうち、自分が正規に利用できるクライアント (自分が所有・利用するアプリ/機器) から、検証可能なペアを正規の範囲で用意できるか。調達できなければ、この線は AKE 以前で止まる。

## 8. まとめ

- pydtcpip は、20 年以上オープン実装がなかった DLNA/UPnP + DTCP-IP の受信側一式を、実機検証 (東芝 2 機種) とともに公開した初期版 (0.1.0、MIT) である。nasne 向けプロファイルは「実装済み・実機未検証」という、こちらに実機がある側にとって最も検証しがいのある状態で置かれている。
- 成否の分岐はプロトコル実装ではなく **証明書 (DTLA 署名の正規ペア 108 バイト) の調達** と **nasne 側の受け入れ (クライアント登録・AKE)** にある。どちらも静的調査では決着せず、実機検証 (まず `dump` による無消費の採取、次に `stream` による無消費の受信確認) で切り分ける対象である。
- 位置づけ: 保存 `.dat` 復号の本線 (オラクル方式) の代替ではなく、配信経由で平文を得る独立した第 3 の線。自作クライアント構想 (docs/21 が土台) の Sink 側の基盤としても、そのまま使える候補である。
