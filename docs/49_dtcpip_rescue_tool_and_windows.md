## 3. ツール整理 (tools/dtcpip-rescue/)

作業領域にあったパイプラインを、リポジトリ内の `tools/dtcpip-rescue/` に正式なツールとして移した。手順の正本は同梱の README。

- 構成: `rescue.py` (CLI ドライバ)、`list_recordings.py` (列挙)、`rescue_gui.py` (GUI)、`credentials.env.example` (空テンプレート)、`README.md`。
- **pydtcpip は同梱しない。** `--pydtcpip-home` / 環境変数 `PYDTCPIP_HOME` で「`.venv` を含む pydtcpip のチェックアウト」を指す方式にした (POSIX の `bin/` と Windows の `Scripts/` の両レイアウトに対応)。未指定時は、このインタプリタで import できる pydtcpip と、PATH 上の `pydtcpip` コマンドへフォールバックする。
- パスは差し替え可能にした: `--credentials` / `--data-dir` / `--out-dir` / `--logs-dir` (環境変数 `RESCUE_*` でも可)。既定値は、初期構築時の作業領域レイアウトが存在するマシンではそちらを指す **互換動作** とし、存在しなければツール自身のディレクトリ配下 (`data/` `out/` `logs/`) になる。data-dir の既定は資格情報ファイルと同じディレクトリで、SRM (`srm.bin`) が資格情報の隣に保存される従来の配置を保つ。
- `data/` `out/` `logs/` はツール内 `.gitignore` で除外し、資格情報実物・SRM・救出済み TS が誤ってコミットされないようにした。コミット前に `git status` と追加ファイル一覧を精査し、混入がないことを確認済み。
- Windows の文字コード対策として、ドライバは子プロセスの環境に `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8` を加え、`list_recordings.py` とドライバ自身の標準出力を UTF-8 に寄せた (理由は §4)。
- CLI のサブコマンドと意味論 (list / fetch / fetch-all、既救出のスキップ、失敗時は `.partial` を残し manifest に入れない、等) は docs/48 の設計から変更していない。

## 4. Windows 実機検証

手元の Windows 11 実機 (所有者の日常環境) で検証した。実機は自宅 LAN 内にあり、nasne と同一ネットワークにいる。

### 4.1 環境と pydtcpip

- OS は Windows 11、リモートシェルは PowerShell 5.1。Python 3.13.2、git、uv が導入済みだった。
- pydtcpip は GitHub から clone し、`uv sync` で `.venv` を構築 (システムの CPython 3.13.2 を使用、47 パッケージ)。`.venv\Scripts\pydtcpip.exe` の起動 (ヘルプ表示) を確認した。
- リポジトリも同機に clone し、ツールを `tools\dtcpip-rescue\` の配置のまま使った。

### 4.2 到達性

nasne の 4 ポート (DMS 58888 / 配信 58890 / WebAPI 64210 / XSRS 64230) 全てに TCP 到達可能だった。

### 4.3 list (資格情報なし)

- 録画 6 件を取得し、内容 (タイトル・ID・res・コピー数) は Linux での列挙と一致した。日本語タイトル (ARIB 外字を含む) も JSON データとして欠落なく取得できた。
- **観測された差異**: 発見時のプロファイル名が、Linux では `sie_nasne` と表示されるのに対し、Windows では `nasne` と表示された。pydtcpip 側のプロファイル一致の差異と見られるが、列挙内容に差はなく、列挙スクリプトは `sie_nasne` 優先・無ければ単一サーバーへフォールバックする設計のため実用上の問題はなかった。**原因は未確定** (§6)。

### 4.4 空テンプレートでの fetch

- 資格情報が空テンプレートの状態では、Linux と同一の挙動だった: pydtcpip の資格情報読み込み段階で終了コード 1、書き込み 0 バイト、`.partial` は 0 バイトのまま残り、manifest には入らない。エラーメッセージは資格情報ファイルのパスと変数名のみで、値を含まない。

### 4.5 実配置での fetch (AKE 実走)

- 本人の許可のもと、資格情報ファイルの **実物を中身を開かずにファイルコピーで** Linux 側から Windows 側へ転送した (本人のファイル・本人の機械同士)。整合確認は **バイトサイズの一致まで** とし、ハッシュは取っていない (記録にも残さない)。転送後の Windows 側ファイルには、所有者本人のみフルコントロール・継承なしの ACL を設定した。
- DR 録画 1 件 (Linux で取得済みのタイトルと同一のもの) を fetch し、**AKE が完走して 494,434,560 バイトを取得**。SHA-256 は **Linux で取得した同一タイトルと完全一致** し、全 2,575,180 パケットで MPEG-TTS 同期バイト正常 (不良 0) だった。`data\` に `srm.bin` が生成され、manifest / SHA256SUMS も作成された。
- → **Windows でも DTCP-IP 救出の一連 (発見・列挙・AKE・復号・保存・検証) が実証された。**

### 4.6 Windows の癖 (手順に反映済み)

- PowerShell 5.1 の `>` リダイレクトは UTF-16LE で書く。ツールの出力 JSON をファイル経由で読む場合はエンコーディングに注意 (ツール自身が書くファイルは UTF-8 で統一されており、そちらが正)。
- 既定コンソール (cp932) では ARIB 外字等の文字が表示できない。ツールは `PYTHONUTF8=1` の伝播と標準出力の UTF-8 再設定で回避しているが、コンソール上でタイトルを目視する場合は文字化けではなく表示側の制約である点に注意。
- venv の実行ファイルは `Scripts\` レイアウト (`python.exe` / `pydtcpip.exe`)。ツールの解決ロジックは両対応済み。
- SSDP 発見 (応答ポート UDP 57000) は今回の環境ではファイアウォールに阻まれず動作した。環境によっては Python の受信許可が必要になりうる。

## 8. 手動登録 (アドレス直接指定) の追加と Mac / Tailscale 実走 (2026-11-17 追加)

本人の使い方として「SSDP は使わない、手動登録」が示されたため、SSDP 発見を経由せず nasne のアドレスを直接指定する経路を追加した (実装 commit `30b4ddd`)。

### 8.1 動機

- 列挙は pydtcpip の SSDP 発見が前提だったが、SSDP のマルチキャストはルーテッド経路 (Tailscale のサブネットルーティング等) を越えられない。Mac (192.168.1.0/24 側) からは nasne (192.168.11.129) のポート 58888 へのユニキャスト到達はあるのに、`list` は "no media servers found" になっていた。
- Browse 自体はユニキャスト HTTP なので、発見だけを直接指定に置き換えれば経路を越えて使える。torne mobile HB で手動アドレス登録が主経路の一つになっているのと同じ思想。

### 8.2 実装

- pydtcpip の `DLNAClient.get_server(location)` (SSDP の LOCATION から MediaServer を作る公開メソッド) を使い、description の取得だけを直接指定に置き換えた。nasne の description URL は `http://<host>:58888/` (SSDP 経路で得られる location と同一)。
- `list_recordings.py`: `--host` を追加 (既定は環境変数 `RESCUE_HOST`)。指定形式はホスト名 / IP (ポート 58888 を補う)、`host:port`、description URL そのものの3形。到達不能なアドレスは traceback でなく明示メッセージで終了コード 1。
- `rescue.py`: `--host` / `RESCUE_HOST` を共通オプションとして追加し、`list` / `fetch` / `fetch-all` の全てで効くようにした。`fetch` は一覧取得時の `server.location` を pydtcpip `stream --server` に渡すため、手動指定の一覧から取得すれば転送先も同じ nasne になる。
- `rescue_gui.py`: 「nasne アドレス (手動指定)」欄を追加 (空欄 = SSDP 自動発見)。入力値はデータディレクトリの `gui_settings.json` に保存され、次回起動時に読み戻される。資格情報には一切触れない (保存されるのはアドレスのみ)。

### 8.3 検証

- **marnux (有線 LAN)**: `rescue.py list --host 192.168.11.129` の結果が SSDP 経路と完全一致 (サーバー情報・録画 8 件の content_id とタイトル)。`RESCUE_HOST` 指定、`host:port` 形、URL 形でも同一結果。到達不能アドレス (192.0.2.1) は明示エラーで終了コード 1 を確認。
- **marnux GUI (Xvfb ハーネス)**: アドレス欄への入力 → 設定保存 (`gui_settings.json`) → 再起動での読み戻し → GUI 経由の列挙 (手動指定で 8 件) を確認。
- **Mac (192.168.1.0/24 側、Tailscale サブネット経由)**: SSDP 経路は従来通り発見不可 (終了コード 1、"no media servers found")。一方 `--host 192.168.11.129` では列挙が成功し、録画 8 件の content_id とタイトルが marnux の結果と完全一致した。**発見を越えられない経路でも手動登録で列挙できることを実証。**
- Mac でも発見プロファイル名は `sie_nasne` でなく `nasne` と表示された (§6 の Windows の現象と同件。列挙内容に差はなく、原因は引き続き未確定)。

### 8.4 残件への影響

- §6 の「macOS での実機確認」は、CLI の列挙については本節で解消した (GUI の起動確認も別途済み)。GUI の操作を伴う列挙・fetch の完走確認は引き続き残件。`fetch-all` の実走は §9 で解消した。
- fetch の手動指定での実走 (AKE を伴うもの) は未実施。一覧取得と同じサーバー location を使う構造であり、LAN では SSDP 経路で実証済みの転送と同一経路になる。

### 9.3 連続取得中の観測 (異常なし)
