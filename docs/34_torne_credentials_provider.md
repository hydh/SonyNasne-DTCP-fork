# 34 torne mobile の DTCP-IP 資格情報の供給機構 第2段 (難読化プロバイダ `0x1b5090` の解読と素材の出所)

対象: torne mobile v1.50 の `PvrBgApp` フレームワーク (Sony 製 DTCP-IP ミドルウェア DEWEY、docs/21・docs/33 の続き)。docs/33 で残した「難読化プロバイダ内部の最終確定」と「アイテム #13 の意味論」を解く段。

状態: **プロバイダの GET 経路と素材の出所は確定。素材はバイナリ内埋め込みではなく、暗号化された資産ファイル `PvrAssetData.cxml` を実行時に復号して DAL へ投入するものであることを同定した。投入処理の成立再現と資産ファイルの配布経路、アイテム #13 の内部構造は未確定。** 実際の資格情報ペイロードは本段では再構成していない (投入を有効な入力で再現できていないため)。証明書・秘密鍵の値は本書のどこにも書かない。

## 1. 解析方法

- 静的解析 (逆アセンブル実読) と、Unicorn (arm64) による関数単位エミュレーションの併用。対象バイナリはファイルオフセット = 仮想アドレスの配置 (サイズ 4,106,640 バイト) で、イメージをそのままマップして実行した。
- インポート関数はスタブ化し、メモリ割当て・メモリコピー・ミューテックス等は実働相当の疑似実装で置き換えた。ログ関数は読み飛ばした。
- **検証は合成データで行った**: 実在しない目印パターン (位置依存のバイト列) を投入側に置き、取得側に逐語で現れるかで「コピーか変換か」を判定した。実素材は一切使っていない。
- エミュレーションの環境忠実度には限界がある (後述 §8)。結論は「エミュレーションで再現できた範囲」と「静的実読のみ」を区別して書く。

## 2. プロバイダ `0x1b5090` の構造 (難読化機械の実態)

- 制御フロー平坦化は 2 つの状態変数による機械である。状態1 (10 ビット、ジャンプ表 666 エントリ、表は `0x1c20b0`) と状態2 (32 ビット) を持ち、遷移は `t = (状態2 × ブロック固有の定数) >> 17`、`次状態1 = (A − t) & 0x3ff`、`次状態2 = B − t` の形 (A・B はブロック固有の定数)。初期状態は 状態1 = 0xd9、状態2 = 0x7d0fdf45。
- 定数 XOR 難読化に使われる大域語 (アドレス `0x35f3ec`) は **値 0 で、バイナリ全体で書き込みサイトが存在しない** (読み取りはプロバイダ内の 3 件のみ)。すなわち XOR/加算による定数攪拌の一部は見かけだけのノイズであり、実データには影響しない。
- アイテム ID (引数) を読むブロックは 8 件のみ。プロバイダへの直接呼び出しはディスパッチャ側の `0xfa8bc` の 1 件だけである。
- フレームは 0x7c0 バイト。引数は self (プロバイダオブジェクト)、アイテム ID、出力レコード、上限長の 4 つ。

## 3. GET 経路の確定 (アイテム #9 / #13 とも逐語コピー、変換なし)

プロバイダはアイテムごとに「ビルダー」関数へ委譲し、ビルダーはプロバイダオブジェクト内のポインタ先オブジェクトから長さ付きバイト列をレコードへ複写するだけであることを、静的実読と合成データによるエミュレーションの双方で確認した。

| アイテム | ビルダー | 素材オブジェクト | 長さの所在 | データの所在 | オブジェクトの割当て |
|---|---|---|---|---|---|
| #9 (証明書) | `0x1166f4` (プロバイダ内 2 サイトから呼ばれる) | プロバイダ +0x48 のポインタ先 | +0x78 (u32) | +0x7c から長さ分 | 352 バイト |
| #13 | `0x1178a4` (プロバイダ内 1 サイトのみ) | プロバイダ +0x38 のポインタ先 (以下 S) | +0x97c (u32) | +0x980 から長さ分 | 4496 バイト |

- ビルダーはレコード +0x10 へ `memcpy` し、ヘッダ (状態バイト +0xb = 0、長さ +0xc) を書く。**暗号化・復号・XOR・展開等の変換は GET 経路に存在しない** (合成パターンがバイト同一で往復した)。
- 上限との整合: S のデータ域は 4496 − 0x980 = 2064 バイト (docs/33 の「#13 上限 2064 バイト」と一致)、#9 側のデータ域は 352 − 0x7c = 276 バイト (証明書 88/132 バイトを十分に収める)。
- **モードゲート**: GET は S +0x944 の語が **4** でないとエラー 22 で失敗する (プロバイダ内 3 ブロックがこの語を読む)。モード語が 4 でない状態では、どのアイテムの GET も同一のエラー経路に入る。

## 4. 「バイナリ内埋め込み」候補の棄却 (プロバイダ内の復号テーブルはロギング用)

プロバイダ内には遅延デコードの仕掛けが 5 サイトあり、当初は素材の埋め込み候補に見えたが、実態は **ログ出力用の文字列テーブル** であった。

- デコーダ `0x1c2e58` は call_once 型で、初期化子 `0x1c2f44` が `h = 種 × 0x2b8431d (mod 2^32)`、`u = src[i] XOR h`、`h += src[i] + u`、`dst[i] = u` の逐語復号を行う (種・元データは `__const` 領域、復号先は BSS)。
- 5 サイトはいずれもデコード直後にログ関数 `0x112888` を呼ぶ形であり、GET 実行時に復号済みデータを資格情報として読む経路は存在しない (モード違反時のエラー実行では 1 テーブルのみがデコードされログに使われることをエミュレーションで確認)。
- ファクトリ (§5) にも同系の 2 語デコード (姉妹デコーダ `0x1764e4` → `0x18b62c`) があり、こちらはプロバイダ内のスロット名 (アイテム名) テーブルの生成である。構造情報のみで素材ではない。

以上により、**プロバイダのバイナリ内に資格情報のバイト列は (難読化された形でも) 存在しない**と判定する。根拠は「見つからなかった」ではなく、(a) GET 経路のデータ源が 2 つの素材オブジェクトに限られることの実読、(b) 埋め込み候補だった復号テーブルの用途同定、(c) §5 の空コンテナ実測、の 3 点である。

## 5. オブジェクトのライフサイクル (生成時は空、投入は別工程)

- DAL 文脈のコンストラクタ `0xfd014` が 312 バイトの文脈を確保し、ファクトリ `0x1765d0` の生成したプロバイダオブジェクト (8784 バイト) を文脈 +0x128 に格納する。文脈の取得側ラッパは 48 バイトで、先頭フィールドが文脈へのポインタである (転送層はこのラッパ越しに文脈を引く)。
- ファクトリはプロバイダの他に S (4496 バイト)、#9 用オブジェクト (352 バイト)、スロット構造体 (64 バイト ×3、スロット数 36、ストライド 0x70 バイトの内蔵配列、スロット名を書き込む) 等を確保する。DAL 実装のバージョン表示は "swagner" 系の文字列を含む。
- **ファクトリ単体をエミュレーション実行し、生成直後の状態を実測した**: S のモード語 = 0、#13 の長さ = 0、S のデータ域は全ゼロ (非ゼロは S 自身のヘッダ/ミューテックス等の 71 バイトのみ)、#9 用オブジェクトは全ゼロ。この状態では全アイテム (0〜35) の GET がエラー 22 で失敗する。
- すなわち **素材の投入はファクトリにも GET にも含まれず、別の工程** である。公開 API (`PvrDtcpIpKeyManagerInitialize` 等、書き出しは全 5 件) にも素材設定用の口は無い (初期化は文字列と 16 バイト設定のみ、docs/33 §確定分)。

## 6. 投入経路 (出所 = 暗号化資産ファイル `PvrAssetData.cxml`)

- C++ 層の関数 (0xa66a0 付近) が、資産ローダ経由で **`PvrAssetData.cxml` という名前の資産** を 2120 バイトのバッファへ読み、続いて記述子 {第1語 = 1, 第2語 = 読み取り長 + 8} (データは記述子 +8 から内蔵) を組み立てて DAL 転送 `0x105890` へ渡す。第二の資産 (`PvrBGMData.cxml` 系) についても同型の読み取り+転送のサイクルがある。
- 資産ローダ `0xc5e0` の動作 (実読): 初期化 API に渡された文字列 (基底パス) + 資産名でパスを構築し、`.bak` 兄弟ファイルの扱いを含む読み取りを行う。内部で 16 バイトの値を生成し、ファイル内容の 48 バイト域を照合したうえで、ペイロード部分を呼び出し側バッファへ複写し長さを返す。ディスク上の cxml は **暗号化/保護されたコンテナ** であり、DAL へ渡るのはローダが取り出した後の内容である (アプリ内の他の cxml 資産も一見ランダムなバイト列で始まることと整合する)。
- この転送はディスパッチャ経由でプロバイダの **アイテム 1 の処理** へ到達することをエミュレーションで確認した (プロバイダが記述子の第1語と +8 の語を読むところまで)。ただし合成データでは投入は成立せず (転送層の戻り値 4、プロバイダ直接呼び出しでは戻り値 2)、**検証条件 (入力形式の要件) は未同定**。アイテム 1 の処理は複数ブロックにまたがる多段手続きで、アイテム ID − 1 の比較ブロックが複数存在する。
- 資産ファイルの **配布形での所在は未確定**: IPA 内に同名の loose ファイルは無く、リソースアーカイブ (GCRESOURCEDIR.psarc、全 41 エントリ) の中身は torne のマスコット画像類のみであった。アプリ本体 (torneplus) 側には資産名をタグ ('PRMA') として扱う TLV 形式の表と、DTCP-IP 鍵確認を指す操作文字列 (`op=opDtcpipKeyCheck`) が存在し、資産の受け渡しがアプリ側で行われる可能性を示すが、経路は追い切れていない。

## 7. 変換チェーン全体像 (保存形と使用形)

```
[暗号化資産ファイル PvrAssetData.cxml]
   |  資産ローダ 0xc5e0: パス構築 → 保護コンテナの検証 (48 バイト照合等) → ペイロード取出し
[平文の資産内容 (≤2120 バイト)]
   |  DAL 転送 (記述子 {1, 長さ+8}) → プロバイダのアイテム 1 処理 (形式未同定)
[DAL アイテムストア内の保存形: #9 = オブジェクト +0x7c の長さ付きバイト列、#13 = S +0x980 の長さ付きバイト列、モード語 = 4]
   |  GET: 逐語コピー (変換なし、本書 §3)
[取得ヘルパ 0x71928 等 → 組立て 0xa2964]
   |  SdiDevCert 設定関数 0x8513c: 88/132 バイトを受理し、バイト 3〜7 (デバイス ID) を固定バイトとの XOR で難読化して保持 (docs/33)
[AKE での使用形]
```

- プロバイダが返すペイロードは「保存形そのまま」であり、最終形への変換は受け口側 (SdiDevCert の XOR 保持と公開鍵側の構築、docs/33) で行われる。
- もう一つの供給路 (AKE 側 `0x9c500`、docs/33) も同じ保存形を vtable 経由で受け取る構造であり、保存形が唯一の素材表現であることと整合する。

## 8. アイテム #13 の意味論 (未確定の範囲)

- 確定しているのは所在と上限のみ: S 内 +0x980 から最大 2048 バイトの長さ付きバイト列として保存され、GET では逐語で返る。秘密鍵 (20 バイト、docs/32) がこのバイト列の一部として含まれるかどうか、その他の構成要素 (証明書側との対応、ヘッダ類) は **未確定**。
- 未確定の理由: 投入処理 (アイテム 1) を有効な入力で再現できておらず、投入後の S の中身を (合成データでも) 観測できていない。投入の入力形式が分かれば、合成データ投入 → GET の往復で「資産内容のどの範囲が #13 になるか」を実測できる。
- 補足: 資産内容全体の上限が 2120 バイトであり、#9 (≤132 バイト) と #13 (≤2048 バイト) の単純合計を下回るため、資産は両アイテムを素朴に連結した形ではない (構造化された形式か、片方が短い実長を持つ)。

## 9. 全端末共通性についての判定

プロバイダ・ファクトリ・資産ローダの入力を棚卸しした結果:

- プロバイダの入力は (アイテム ID、上限長、ストア内容) のみで、端末固有値 (シリアル、チップ ID、キーチェーン、ネットワーク由来の値) を読む経路は無い (自己完結コード、docs/33 の census と本書 §2・§3 の実読)。
- ファクトリの入力は所有者文脈へのポインタのみで、生成物は定数と空コンテナだけである (§5 で実測)。
- 資産ローダの入力は (基底パス文字列、資産名、出力バッファ) のみ。素材の内容は **資産ファイルの内容だけ** で決まる。

よって **「資格情報は端末ではなく資産ファイルに由来する」** ことは積極的な根拠をもって確定できる。一方、その資産ファイルが全端末で同一か (アプリ同梱/同一配布か、端末ごとに発行・ダウンロードされるか) は §6 の通り未確定であり、**全端末共通性の最終判定は資産ファイルの出所の同定待ち** とする。なお分類としては docs/33 の「埋め込み固定」型を「アプリ資産由来」型へ更新するのが正確である (バイナリ埋め込みではない)。

## 10. 未確定点

1. 投入処理 (プロバイダのアイテム 1) の入力形式と検証条件。合成データでは成立せず、資産内容が #9/#13 へどう振り分けられるか未観測。
2. アイテム #13 の内部構造 (秘密鍵 20 バイトの内包の有無を含む)。
3. 資産ファイル `PvrAssetData.cxml` の配布経路と端末間同一性 (アプリ本体側の TLV 表・鍵確認操作との関係を含む)。
4. 資産ローダの保護形式の詳細 (16 バイト値の生成と 48 バイト照合の意味、復号の段数)。
5. 初期化全体をエミュレーションで通す試行は、資産パス処理の中で関数ポインタ呼び出し (アドレス 0) に落ちて完走しなかった (環境忠実度の問題)。投入が初期化のどの段階で起きるかは、この方法では未観測。

## 11. 再構成素材について

- 本段では実際の資格情報ペイロードは **再構成していない** (投入を有効な入力で再現できていないため)。検証に使った合成データの記録ファイルは作業領域から破棄済みで、リポジトリにも作業領域にも実素材は存在しない。
- 作業は開発用計算機上の作業領域 (`SonyNasne-DTCP.work/2026-11-15-torne-dal-provider/`) で行い、実機 (nasne 本体) には触れていない。
