# XCode ファームウェア DRM モジュール解析 第14段

2026-11-15。第13段 ([docs/27](27_xcode_fw_drm_phase13.md)) の残件のうち本命 1 件 — OPEN_GENERIC_STREAM (FN=25) の主 FW 側ハンドラ同定と、録画保存の GENERIC-AES セッションへの鍵装填経路の特定 — に専念した段。結論を先に書くと、**ハンドラは同定でき、鍵装填経路は「open 時に FW が鍵ストアスロットを予約し、鍵素材は確立後の SCRAMBLER コマンドでホスト供給 CW が逐語投入される」という形で確定した**。判定したい問い (a)(b)(c) への答えは §5。

手法は第9段の M1–M6 を踏襲 (Ghidra 実読を主とし、GPL ドライバ一次資料で配送・構造体・モード定義を照合)。主 FW の表 D 周辺は Ghidra の既存解析でほぼ孤児域だったため、再同期線形スイープ (本段追加の Sweep14.java) を M2 の変種として併用した。素材は開発側作業領域 `2026-11-13-fw-drm/phase14/` (Ghidra プロジェクト `ghp14` = 第2 FW、`ghp14m` = 主 FW、いずれも phase13 プロジェクトの複製)。アドレス表記は各イメージのロードベース基準 (主 FW = 0、第2 FW = 0xB00000) で、ファイルオフセットと一致する (+0x100000 ビューのライブラリについてはその旨を明記する)。

## 1. 結果サマリ

| 項目 | 結果 |

## 2. 課題と判定したい問い

**課題**: FN=25 (OPEN_GENERIC_STREAM) の主 FW (procIdx=0) 側ハンドラを同定し、そのセッション生成処理を実読して、GENERIC-AES セッションの鍵がどこから来るかを追う。

判定したい問い:

- (a) 鍵装填は鍵ストアスロット経由か。経由するなら、パケット/セッション構造のどの欄がスロット番号を持つか。
- (b) SCRAMBLER 経路と鍵素材を共有するか (§49 トークンが投入されるスロットと GENERIC セッションの鍵の関係)。
- (c) 鍵の出所は、ホスト供給・トークン解決・OTP 由来・エンジン内部生成のどれか。

副次的に、§49 トークンと GENERIC セッションの関係が事実として取れたら対応づけ、E2 (docs/02 §12) 失敗の候補 (iii) — 「`.dat` の暗号化そのものは GENERIC-AES セッション側の内部処理であり、録画時の SCRAMBLER 呼出しは別目的である可能性」 (docs/27 §4.3 で未判定) — の判定に繋がる所見があれば明記する。

## 3. 前提 (確定済み事項)

- SCRAMBLER 経路は投入・消費の両側で閉じている: 鍵ストアスロット (128 スロット、共有域 +0x1824/+0x1828/+0x182C) へホスト供給 CW が逐語投入され、消費はエンジン (HW) がスロットを直接参照する。FW 側の変換は無い ([docs/25](25_xcode_fw_drm_phase11.md) / [docs/26](26_xcode_fw_drm_phase12.md))。
- 製品構成のホスト SCRAMBLER は第2 FW 実装 `0xBF894C` (procIdx=6) が受ける。主 FW の `0x22F9E0` は proc0 ローカル文脈用の同型実装 ([docs/27](27_xcode_fw_drm_phase13.md) §3)。
- 録画保存の実形態は SECUREDTS (復号) + GENERIC-AES (generic_mode=0x4000、req_size=0xFC00)。鍵コマンド 0x113/0x114 は録画ログに皆無 (docs/02 §10)。
- OPEN_GENERIC_STREAM は FN=25、procIdx=0 = 主 FW 宛 (GPL 一次資料 txcdev.c)。パケット `cmd_open_generic_stream` とドライバ API `param_opengeneric` の双方に鍵欄は無い。録画時の実測ではゼロ初期化後に generic_mode / req_size / 共有入力バッファサイズのみが刻まれ、残りは全て 0 (docs/27 §4.1、docs/02 §10.2)。
- §49 トークンの行き先は「SCRAMBLER 要求の control_words 欄 → 状態ブロック語 `[handle+0x8B0]` が指す鍵ストアスロットへの逐語投入 (先頭 16 バイト、2 スロット分)」まで具体化している (docs/27 §4.3)。

## 4. 調査経路と結果

### 4.1 主 FW の中央メールボックスハンドラと表 A

入口として、主 FW の SCRAMBLER 実装 `0x22F9E0` の呼出し元を xref で引いた (実測 2 件: `0x3729CC` と `0x2C3808`)。前者を含む関数が、主 FW における第2 FW `0xC74BBC` の相方 — 中央メールボックスハンドラである。構造は `0xC74BBC` と同型で:

- **第1経路 (オブジェクト経由)**: オブジェクト登録コールバック `[obj+0x2C]` を呼ぶ。FN=12 の場合の特例処理も含め、第2 FW 側と同型の振る舞いが読める。
- **フラグ分岐**: 変種切替フラグ (記述子基底 +0x370 のセル) が 1 の場合は代替関数 `0x289A1C (packet, mode, saved)` が全パケットを処理する。
- **第2経路 (直接 FunctionNumber 振り分け)**: `[packet+0xC]` (FunctionNumber) から 9 を引いた値をインデックスとし、範囲 9–50 (42 エントリ) のジャンプ表で振り分ける。表の実体はファイルオフセット `0x27285C` にあり、+0x100000 ビューのライブラリから参照される (命令上の表アドレスは `0x37285C`)。

### 4.2 表 C — フラグ=1 変種の振り分け器 `0x2C35D4`

もう一つの SCRAMBLER 呼出し元 `0x2C3808` は、関数 `0x2C35D4` の中の FN=37 ケース (`0x2C3804`、呼出しは +4) だった。この関数は引数のオブジェクトの +0x54 欄にあるパケットを取り、`[packet+0xC]` を表 C (ファイルオフセット `0x1C363C`、FN 9–37 の 29 エントリ) で振り分ける第2の振り分け器で、ケースの並びとワーカーはハンドラ A の第2経路と同型である (FN=24 → `0x36C8C8`、FN=11 → `0x298218` 経路、FN=13 → `0x2B7088` 等が一致)。

`0x2C35D4` への参照は、ハンドラ A のフラグ=1 代替関数 `0x289A1C` の中での PARAM 参照 1 件のみ (実測)。すなわち表 C はフラグ=1 変種の振り分けであり、**FN=25 はここでも共通尾部 `0x2C38DA` (同じリスト `0x699FF8` への enqueue + 信号) 行き**である。どちらの変種でも FN=25 はメールボックス段では処理されない。

### 4.3 共通キューの消費タスクと表 D (第2段ディスパッチ)

リスト `0x699FF8` / 信号 `0x699FF4` の参照を ScalarScan (M6) で census した。enqueue 側は §4.1 / §4.2 の 2 箇所のみ。消費側は関数 **`0x3992B0`** で、基底レジスタに `0x699FF8` を置いてリストからパケットを取り出す (dequeue は `0x3993DA`) キュー消費タスク関数である。この関数は `[packet+0x8] == 2` の完了系サブ処理 (コールバック `[packet+0x1C]` の呼出し等) を経た後、FN 振り分けへ進む。

### 4.4 ワーカー `0x33FFC8` (OPEN_GENERIC_STREAM の実体) の実読

本体 `0x33FFC8`–`0x3407FD` (3 断片、間の域は分岐先コードとエラー記録ブロック)。呼出し元は FN=25 ケースの 1 箇所のみ (xref 実測)。

- 引数 r19 = `cmd_open_generic_stream*`。セッション状態オブジェクト r18 をプール (セル `0x6B3AA8` の指す先を `0x20FAA8` で取得) から確保し、Input の DMA バッファ配列・サイズ・モード類を複写して初期化する。状態オブジェクトはストリームハンドルの指す先そのものである (ケース側後処理が `[handle+0x40]` を generic_mode として読むこと、および [docs/27](27_xcode_fw_drm_phase13.md) §2.1 の「ハンドルは主 FW (proc0) が作る」と整合)。
- `[state+0x40] = generic_mode` (Input+0x10。一次資料の構造体定義 `cmd_open_generic_stream` でオフセットを照合した)。
- 初期化の過程で、状態ブロックの `[state+0x7E8]`、`+0x8B0`、`+0x8B4`、`+0x8B8`、`[state+0x904]` を全て -1 (無効) にする。**すなわち本関数は docs/27 残件 (1) が探していた +0x8B0/+0x8B8 の書き手の一つ**であり (初期化としての -1 と、後述の予約結果の書込み)、スロット番号の意味ある書込みも本関数が行う。
- generic_mode のビットによる分岐 (ビット名は一次資料 sttype.h の GENERIC_MODE_* で照合):

| モードビット | 経路 |
|---|---|
| 0x400 (BCAS) | セッション表 (セル `0x645954`) を使う BCAS セッション設定。2 つのサブオブジェクト (+0x280/+0x284 欄) をアロケータで確保する |
| 0x840000 (TDES_TS 0x40000 / TDES_ABA_TS 0x800000) | IV スロットを `0x1BC46C(2)` で予約し +0x8B8 へ。CW スロットを `0x1BC3E8(n)` (n = TDES_ABA_TS なら 2、それ以外は 3) で 2 本予約し +0x8B0 / +0x8B4 へ |
| 0xE000 (IVDR 0x2000 / AES 0x4000 / MARLIN 0x8000) | CW スロットを `0x1BC3E8(2)` で予約し +0x8B0 へ。MARLIN の場合のみ第2 CW を +0x8B4 へ追加予約。IV スロットを `0x1BC46C(2)` で予約し +0x8B8 へ |
| 0x80000 (AACS_BLK) | `0x20D918 (state, generic_session_handle)` で AACS 認証のセッション鍵を束縛する (generic_session_handle の消費先はこの経路のみ) |
| 0x2000000 (KEYLADDER) / 0x1330260 (AACS・DRM_AES・DRM_C2・CPRM・IVDR・BCAS 等の複合マスク) / 0x400000 | 後段設定関数 `0x261520 (state, Input)` への委譲フラグを立てる。`0x261520` 自身もスロットアロケータの呼出し元である (xref 実測) |
| 0x4000000 | `0x29E5D8 (state)` を呼ぶ |

- **録画の generic_mode=0x4000 (AES) は 0xE000 分岐に入り、+0x8B0 = CW 2 スロット予約、+0x8B8 = IV 2 スロット予約、+0x8B4 は -1 のまま**となる。予約に失敗した場合はエラーコード (0xA / 0xB / 0xC / 0x10 等) を記録し、確保済みスロットを解放 (`0x1E4124`) してセッションを破棄する。
- **本関数内に鍵素材の書込みは無い**。呼出し先はセッション確保・初期化・memcpy (`0x2ACFB0`、DMA 配列の複写)・スロット予約/解放・モード別設定関数のみで、スロットへの素材投入ヘルパ (主 FW の `0x200E68` / `0x203274`) への呼出しは無い (全行実読で確認)。Input の `rng_data` 欄も鍵として読まれない (複写対象は DMA 情報とモード類のみ)。

### 4.5 スロットアロケータ `0x1BC3E8` / `0x1BC46C` / 解放 `0x1E4124`

- `0x1BC3E8 (count)`: 128 エントリの使用ビットマップ (バイト配列、基底 `0x6AE3E8`) から、count 個の連続空きスロットを偶数境界で走査してマークし、先頭インデックスを返す。失敗時は -1。走査上限は `0x81 - count` で、ビットマップの大きさは鍵ストアの 128 スロットと一致する。
- `0x1BC46C (count)`: `0x1BC3E8` への tail call の別入口 (同一実体)。呼出し側の使い分けは呼出し元の文脈 (CW 系と IV 系) に対応するが、処理は同一。
- `0x1E4124 (slot, count)`: 対の解放。`slot + count ≤ 0x80` の範囲検証つきでビットマップを戻す。
- 予約はインデックスの確保のみであり、**鍵ストアのデータ窓 (共有域 +0x1824 台) には触れない**。スロットへの素材投入は SCRAMBLER 経路の専属である (docs/25/26)。

## 5. 判定

- **(a) 鍵装填は鍵ストアスロット経由である**。GENERIC セッションの鍵の器は、open 時に FW が予約する鍵ストアスロットであり、スロット番号は状態ブロック +0x8B0 (CW) / +0x8B4 (第2 CW、TDES・MARLIN 等のモードのみ) / +0x8B8 (IV) に保持される。確立パケットに鍵欄が無いこと (docs/27 §4.1) と符合する。
- **(b) SCRAMBLER 経路と鍵素材を共有する**。SCRAMBLER ハンドラが AS_INDEX クリア時に CW スロットとして参照する `[handle+0x8B0]`、IV スロットとして参照する `[handle+0x8B8]` は、OPEN_GENERIC_STREAM が予約して書き込むのと同じ欄である。GENERIC セッションの暗号鍵は、同一ハンドルへの SCRAMBLER 呼出しで投入された CW を、エンジンがスロット経由で参照する形になる。
- **(c) 鍵の出所はホスト供給である**。open の時点ではスロットは空 (予約のみ) で、FW は鍵を生成も導出もしない。OTP 由来の素材が GENERIC 経路へ入る箇所は本関数の実読範囲に無く、READ_FROM_OTP は表 D の FN=45 として独立に処理され GENERIC セッションとの接続は無い。エンジン内部生成については、空のスロットを記述子が参照する構造上、FW/スロット経由の観測範囲では支持されない (エンジン内部の振る舞いそのものは従来どおり観測不能として残る)。
- **§49 トークンの対応づけ (具体化の完了)**: 録画時の SCRAMBLER (mode 2、AS_INDEX 常時クリア) が control_words 先頭 16 バイトをスロット `[handle+0x8B0]` 起点の 2 スロットへ逐語投入する先 (docs/27 §4.3) は、本段で同定した「OPEN_GENERIC_STREAM (generic_mode=0x4000) が状態ブロック +0x8B0 に予約する 2 スロット」と一致する。予約幅 (2 スロット = 16 バイト) と投入幅 (16 バイト) も一致する。すなわち §49 トークンは GENERIC-AES セッションの CW スロットへ入り、エンジンがそれをセッション鍵として参照する、という対応が静的に閉じた。docs/02 §10 のモデルはこの形に確定する: 「解決 = スロット番号による鍵ストア参照、投入素材はホスト供給 CW の逐語」であり、GENERIC セッション側も同じスロットを参照する。
- **E2 候補 (iii) への所見**: GENERIC open は鍵素材を一切持たず (ワーカー全行実読)、その鍵スロットは空で予約され、FW イメージ内でスロットのデータ窓へ素材を書くのは SCRAMBLER 投入経路のみである (docs/25 のハンドラ実読と docs/26 の消費側 census の範囲)。したがって「GENERIC 側に内部鍵源があり、録画時 SCRAMBLER は別目的」という強い形の (iii) は、FW で観測できる範囲では棄却できる。残る逃げ道は「エンジンが空スロットに対して内部生成・変換する」場合のみで、それは候補 (i) (エンジン内部の扱い) の領域に帰着する。候補 (ii) (投入が先頭 16 バイトのみ) については、本段で AES モードの予約幅も 16 バイトと判明したため、AES-128 前提では実質的に解消する (鍵が 16 バイトを超えるモードでのみ残る論点)。
