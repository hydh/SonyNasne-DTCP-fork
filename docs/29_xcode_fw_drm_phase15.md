# XCode ファームウェア DRM モジュール解析 第15段

2026-11-15。第13〜14段に残った静的残件を片付ける段。本命は OPEN_STREAM 側ワーカー `0x32FC54` の実読で、状態ブロック +0x8B0 台の書き手の網羅を (実読範囲として) 閉じることを狙った。あわせて後段設定関数 `0x261520`、AACS_BLK 経路 `0x20D918`、表 D の共通既定ケース `0x39A0BC` を実読した。

手法は第9段の M1–M6 を踏襲 (Ghidra 実読を主とし、GPL ドライバ一次資料で配送・構造体・モード定義を照合)。素材は開発側作業領域 `2026-11-13-fw-drm/phase15/` (Ghidra プロジェクト `ghp15` = 第2 FW、`ghp15m` = 主 FW、いずれも phase14 プロジェクトの複製)。アドレス表記は各イメージのロードベース基準 (主 FW = 0、第2 FW = 0xB00000) で、ファイルオフセットと一致する (+0x100000 ビューのライブラリについてはその旨を明記する)。本段の実読対象は全て主 FW である。

## 2. 課題と入口

### 入口 (1)OPEN_STREAM 側ワーカー `0x32FC54` の実読

第14段で同定した第2段ディスパッチ表 D の open 系ケースのうち、FN=8 (OPEN_STREAM) の実体。SECUREDTS を含む OPEN_STREAM セッション生成で、状態ブロック +0x8B0 台への書込み・鍵ストアスロット予約が GENERIC 側ワーカー `0x33FFC8` と同型か、SECUREDTS セッションの鍵がどの欄・どのスロットに対応するかを確定する。

### 入口 (2) 後段設定関数 `0x261520` の実読

第14段で、GENERIC ワーカー `0x33FFC8` がモード別後段設定として呼ぶことが分かっている関数。KEYLADDER/DRM 系モード用とされ、録画経路 (generic_mode=0x4000) では未使用とされる。鍵ストアや +0x8B0 台に触れるか、鍵ラダー的な変換処理が実在するかを判定する (録画経路と無関係であることの積極的な裏付けにもなる)。

### 入口 (3) AACS_BLK 経路 `0x20D918` の実読

GENERIC の AACS_BLK モード (0x80000) でのみ `generic_session_handle` を束縛する処理 (第14段で同定)。鍵・スロットとの関係を判定する。

### 入口 (4)表 D の共通既定ケース `0x39A0BC` と完了系サブ処理

キュー消費タスク `0x3992B0` の表 D で専用ケースを持たない FN が落ちる共通既定ケースと、完了系サブ処理の詳細。

## 3. 前提 (確定済み事項)

- SCRAMBLER 経路は投入・消費の両側で閉じている: 鍵ストアスロット (128 スロット、共有域 +0x1824/+0x1828/+0x182C) へホスト供給 CW が逐語投入され、消費はエンジン (HW) がスロットを直接参照する。FW 側の変換は無い ([docs/25](25_xcode_fw_drm_phase11.md) / [docs/26](26_xcode_fw_drm_phase12.md))。
- 製品構成のホスト SCRAMBLER は第2 FW 実装 `0xBF894C` (procIdx=6) が受ける。主 FW の `0x22F9E0` は proc0 ローカル文脈用の同型実装 ([docs/27](27_xcode_fw_drm_phase13.md) §3)。
- GENERIC-AES の鍵装填は確定: OPEN_GENERIC_STREAM (FN=25) のワーカー `0x33FFC8` が open 時にスロットアロケータ `0x1BC3E8` でスロットを予約し、番号を状態ブロック +0x8B0 (CW) / +0x8B4 (第2 CW) / +0x8B8 (IV) に格納する。鍵素材は確立後の SCRAMBLER でホスト CW が逐語投入され、§49 トークンの投入先 = この予約スロットで対応づけは静的に閉じた ([docs/28](28_xcode_fw_drm_phase14.md))。
- +0x8B0/+0x8B8 の書き手は `0x33FFC8` がその一つと判明したが網羅は未完で、OPEN_STREAM 側が残っている。変位ベースの全数 census は方法限界が実測済み (分割アドレッシングで既知のアクセスすら拾えない) のため、全数否定の根拠には使わない ([docs/27](27_xcode_fw_drm_phase13.md) §2.4)。
- E2 の失敗候補は (i) エンジン内部変換のみが残る ([docs/28](28_xcode_fw_drm_phase14.md) §5)。

## 4. 調査経路と結果

### 4.1 入口 (1): `0x32FC54` と OPEN_STREAM 系の実読

**`0x32FC54` 本体** (呼出し元は表 D の FN=8 ケース `0x39969E` の 1 箇所のみ)。デバッグ出力 "strm_open" を伴うモード振り分け関数で、第1引数は要求パケットである。自身が行う書込みはパケット +0xA4C のゼロクリア (と 1 分岐での +0x594 ゼロクリア) のみで、文脈の生成もスロット予約もしない。振り分けはパケット +0x90 (種別欄) と +0x60/+0x64 (モード)、+0x94 (フラグ) で決まる:

| 条件 | 実装 | 同定した性格 (デバッグ文字列等) |
|---|---|---|
| 種別 == 1 | `0x35FCAC` | "strm_open_ts_pso" — TS/PSO 系 open |
| 種別 == 5 (フラグ分岐) | `0x35FCAC` / `0x35BAF8` / `0x352B6C` | 後述 |
| 種別 == 4、または +0x94 の 0x300 / (0x200 かつ 0x400) | `0x3315AC` | "strm_open_encoder_pso" — 最大の open 実装 |
| 上記以外 (フラグ分岐) | `0x34C3F8` | 最小構成の文脈生成 |
| 同上 | `0x34A7E4` | "strm_open_host_data_passthru" — secured strm の DRM 束縛を含む |
| 同上 | `0x34B8C4` | "strm_open_host_passthru_dvo" |
| 同上 | `0x340838` | "strm_open_host" |

**配下 8 実装の共通形**: いずれもプール `0x6B3AA8` から 0x1E18C バイトのストリーム文脈を確保し、パケット欄を文脈へ複写して (代表: パケット +0x8A0 → 文脈 +0x818C、パケット +0x90 → 文脈 +0x1C0D0)、記述子テンプレート (0xE0010000 等) やレート計算等の初期化を行う。**8 実装のいずれもスロットアロケータ `0x1BC3E8` を呼ばず、文脈 +0x8B0/+0x8B4/+0x8B8 への書込みも無い** (各関数のデコンパイル全域で確認)。なお `0x34A7E4` にはパケット +0x8B0 の読みがあるが、これはパケット側の欄 (長さ欄) であって文脈のスロット欄とは別物である。パケットと文脈はレイアウトが異なるため、オフセットの一致だけで同一視しない。

**この系統の鍵束縛 = DRMCTRL 鍵オブジェクト**: `0x35BAF8` と `0x34A7E4` は、条件成立時に束縛関数 `0x261B7C` を呼ぶ:

- `0x35BAF8`: 文脈 +0x818C の bit 0x8/0x10、または文脈 +0x8178 (パケット +0x88C の複写) が 6/7/8 のとき、`0x261B7C (文脈, スタックバッファ, パケット+0x38, パケット+0x3C, -1, -1)`。
- `0x34A7E4`: パケット +0x88C == 3 / +0x888 == 4 のとき、鍵指定ペア (第1ペア = +0x38/+0x3C、第2ペア = +0x40/+0x44) を渡して `0x261B7C` を呼ぶ。失敗時はデバッグ出力 "drmctrl_open_secured_strm" を残す。SECUREDTS 系の束縛はこの経路である。

**`0x261B7C` の実読** (鍵オブジェクト束縛): 鍵指定ペアを DRMCTRL 文脈の 6 件表 (`0x69735C`、第6段で言う「6 スロットの鍵オブジェクト」の実体) から解決し (指定が 0 の場合は文脈 +0x178 の種別が 0 / 1 のものを探索)、ポインタを文脈 +0x81D0 / +0x81D4 に格納する。鍵オブジェクト (KO) の作業域ポインタは文脈 +0x825C に格納される (docs/27 §2.2 の `0x261260` が読む欄と一致)。KO の能力フラグ (作業域 +0x10) と文脈 +0x818C の値 (8/0x10/0x20) の対応を検証し、フラグに応じて KO の素材欄 (作業域 +0x34C〜+0x378) を文脈 +0x81EC〜+0x8248 の領域へ複写する。フラグ 0x20 の場合は暗号セットアップ `0x15490C` も呼ぶ。**鍵ストアスロットへのアクセスも +0x8B0 台へのアクセスも無い**。

**複数出力分岐 `0x352B6C` → `0x34DC7C`**: `0x352B6C` ("strm_open_multiple_output") が既存文脈を見つけられない場合に呼ぶ文脈コンストラクタ `0x34DC7C` (呼出し元はこの 1 箇所) は、本段の OPEN_STREAM 系で唯一アロケータを呼ぶ関数である。ただし予約先は文脈 +0x8B0 台ではなく、サブストリーム記録 (基底 文脈 +0x1077C、ストライド 0x134、その +0xBC/+0xC0) と文脈 +0x107A0/+0x107A4 の対、および種別一致時の +0x10364/+0x10368、+0x11184/+0x11188、+0x11194/+0x11198 への複写である (いずれも `0x1BC3E8 (1)` = 1 スロットずつの予約)。サブストリーム側のデスクランブラ用スロットとみられ、目的も配置も +0x8B0 台とは別である。

**アロケータ呼出し元の census (主 FW)**: `0x1BC3E8` への参照は 29 箇所・11 関数 — `0x15E378`、`0x15F5EC`、`0x162184`、`0x156830` (DRMCTRL 系ライブラリ域)、`0x2B2500`、`0x34DC7C`、`0x33FFC8`、その別入口 `0x1BC46C` 自身、`0x20D918`、`0x261520`、`0x2629F4` (計算呼出し)。このうちライブラリ域 4 関数と `0x2B2500` のデコンパイルにも +0x8B0/+0x8B4/+0x8B8 への書込みは現れなかった (スロットは呼出し引数として渡されるか、各々の対象オブジェクトの欄に格納される)。`0x2629F4` は §4.2 の通り DRMCTRL 文脈初期化であり、対象はストリーム文脈ではない。

以上より、**ストリーム文脈 +0x8B0 台の書き手は、実読した範囲では `0x33FFC8` と `0x20D918` の 2 関数に限られる**。範囲の限定: 本段の実読は表 D の open 系 (FN=8/FN=25) から到達可能な関数群とアロケータ呼出し元全数であり、変位 census の方法限界 (docs/27 §2.4) があるため「イメージ内のどこにも無い」という全数否定はしない。ただしスロット番号の書込みはアロケータ経由が必須であるため、アロケータ呼出し元の全数確認はこの範囲では強い根拠になる。例外として docs/27 §2.2 の `0x261260` (巨大関数 `0x23FFC8` の case 0x11 から呼ばれ、(長さ, 素材) を +0x8B4/+0x8B8 のアドレスへ書く) があり、これは「スロット番号」ではなく「素材長・素材バイト列」を書く別意味論の書込みである。対象オブジェクトの同一性は docs/27 の留保のまま未確定 (§6)。

**SECUREDTS の鍵の対応づけ**: OPEN_STREAM 系 (SECUREDTS を含む) の鍵は DRMCTRL 鍵オブジェクト束縛 (`0x261B7C` → 文脈 +0x81D0/+0x81D4/+0x825C) であり、鍵ストアスロットとは対応しない。録画保存は、復号側 SECUREDTS が DRMCTRL 側の鍵 (AKE 等で確立された鍵オブジェクト) を使い、保存暗号化側 GENERIC-AES が +0x8B0 台のスロット + SCRAMBLER CW を使う、という非対称な構成である。

### 4.2 入口 (2): 後段設定関数 `0x261520` = drmctrl_open

**同定**: デバッグ文字列 "drmctrl_open"、バッファ名 "DRMCTRL_BUF"、生成タスク名 "uist_drmctrl" から、DRMCTRL の open 本体である。呼出し元は `0x33FFC8` の 1 箇所のみ (xref 全数 1)。第1引数は DRMCTRL 文脈 (最大 6 件、表 `0x69735C`、ストライド 0x10 = {使用フラグ, 文脈ポインタ, モード, …})、第2引数は open パケット (その +0x10 がモード)。

**処理の実読**:

1. 文脈を表へ登録する。文脈 +0x148 (作業域) がゼロなら 0x3F8 バイトをゼロ初期化し、モードを文脈 +0x158 に格納して初期化関数 `0x2629F4 (作業域, モード, 0)` を呼ぶ (`0x2629F4` 自身も計算呼出し経由でアロケータを呼ぶが、その実読は本段の範囲外)。
2. **モードが 0x100000 または 0x200000 のときに限り**、文脈 +0x498 (0x10 / 8)、+0x494 (0 / 0x800)、+0x178 = 0xFF を設定し、**スロット対を 3 組予約する**: 文脈 +0x4B4 ← `0x1BC3E8 (2)`、+0x4B8 ← `0x1BC46C (2)`、+0x49C ← `0x1BC46C (2)`。失敗時は `0x1E4124` で解放して戻る。
3. DRMCTRL_BUF (0x18C00 バイト) を確保し、文脈 +0x15C/+0x160/+0x198 にバッファポインタ群、+0x18C に自己ポインタ、+0x19C にパケット +0xFC を設定する。
4. モード別ハンドラ表 (`0x3ED500`、ストライド 5 ワード) からモード一致のハンドラを呼ぶ。この表は静的イメージからは内容を列挙できなかった (ファイルイメージの当該範囲は初期値を持たず、実行時登録とみられる)。
5. `uist_drmctrl` タスクを生成する (`0x3B4ED0`)。

**判定材料**: 本関数は鍵素材を一切読まず・書かず・変換しない。鍵ストアへは「自文脈 (DRMCTRL 文脈) の欄へのスロット予約」という形でのみ触れ、ストリーム文脈の +0x8B0 台には触れない (対象オブジェクトが異なる)。鍵ラダー的な導出処理は本関数内には存在せず、素材を扱うのは委譲先のモード別ハンドラ側の領分である。録画経路との関係: docs/28 で確定した通り `0x33FFC8` が本関数へ委譲するのは KEYLADDER (0x2000000) / 複合マスク 0x1330260 (AACS・DRM_AES・DRM_C2・CPRM・IVDR・BCAS 等) / 0x400000 のモードに限られ、録画の generic_mode=0x4000 は含まれない。呼出し元が他に無いこととあわせ、**本関数は録画経路では未使用であることが積極的に裏付けられた**。

### 4.3 入口 (3): AACS_BLK 経路 `0x20D918`

**位置づけ**: 呼出し元は `0x33FFC8` の 1 箇所のみで、GENERIC の AACS_BLK モード (0x80000) のときに限る (docs/28)。第1引数はストリーム文脈、第2引数は DRMCTRL 文脈 (NULL の場合は検索関数 `0x2606D0 (0x1000000)` で引く)。

**処理の実読**:

1. 文脈 +0x8B0 / +0x8B4 / +0x8B8 を -1 に初期化し、追加のスロット対配列 (文脈 +0x8CC と +0x8DC、それぞれ 4 対) も -1 に初期化する。
2. DRMCTRL 文脈が有効 (その +0x40 のフラグ 0x1000000) なら、文脈 +0x8F8 にそのポインタを束縛し (docs/27 残件だった +0x8F8 の書き手の一つ)、DRMCTRL 文脈 +0x4B8 起点の 4 ワード (0x10 バイト) を文脈 +0x8BC へ複写する (+0x8BC は docs/26 で同定した素材欄。複写元の 4 ワードの意味論は本段では未確定)。
3. スロットを予約する: 文脈 +0x8B0 ← `0x1BC3E8 (2)` (CW)、文脈 +0x8B8 ← `0x1BC46C (2)` (IV)、続いて 4 対の文脈 +0x8CC[i] / +0x8DC[i] ← アロケータ (2) ずつ。**+0x8B4 はこの経路では -1 のまま** (第2 CW を使わない)。
4. 文脈 +0xC30 の bit 0 があれば DATA_MOD_BUF (0x1000 バイト) を確保して文脈 +0xC38 に置く。
5. 失敗時は予約した全スロットを `0x1E4124` で解放し、欄を -1 に戻す。

**判定材料**: 予約と束縛のみで、鍵素材の変換は無い。GENERIC 経路の他のモードと同一のスロット機構であり、AACS_BLK 専用の鍵装填が別にあるわけではない。+0x8B0 台の書き手 (初期化 + 予約) の一つとして確定する。

### 4.4 入口 (4): 表 D の共通既定ケース `0x39A0BC`

表 D のスイッチ (`0x3994DE`) のケース `caseD_a` として Ghidra が同定した 0x39A0BC–0x39A0E1 の断片。本体は、チェックポイント記録 (0x60 にパケット +0xC = FunctionNumber、続いて 0x61) の後、0xDEADC0DE のパニック記録を書いて戻らないプリミティブ `0x3B8A64` を呼ぶ致命的エラー処理である。xref は表領域 0x399508–0x39959C からの DATA 参照 25 件 (専用ケースを持たない FN の表エントリ) と、スイッチの条件ジャンプ (0x3994D2) である。

すなわち表 D の既定行き先は「黙って捨てる」でも「汎用処理」でもなく、**FN を記録して FW を致命的停止させるトラップ**である。キュー消費タスクの完了系サブ処理の詳細は本段では追わなかった。

## 5. 判定

- **入口 (1)**: OPEN_STREAM 系は +0x8B0 台へスロット予約を書かない (配下 8 実装 + 束縛関数 + 複数出力コンストラクタの実読による)。SECUREDTS セッションの鍵は DRMCTRL 鍵オブジェクト束縛に対応し、鍵ストアスロットには対応しない。+0x8B0 台の書き手の網羅は、スロット予約については GENERIC 経路 (`0x33FFC8` / `0x20D918`) で閉じた (範囲は §4.1 の限定の通り)。
- **入口 (2)**: `0x261520` は鍵ストアに触れるが、それは DRMCTRL 文脈自身の欄 (+0x49C/+0x4B4/+0x4B8) への予約であり、ストリーム文脈の +0x8B0 台とは無関係。本体に鍵ラダー的変換は無い。録画経路での未使用は、呼出し元の一意性と委譲モードの範囲から積極的に裏付けられた。
- **入口 (3)**: `0x20D918` は GENERIC-AES と同一のスロット機構による AACS_BLK 用の束縛であり、+0x8B0 台の書き手の一つ。独自の鍵素材・変換は無い。
- **入口 (4)**: 表 D の既定ケースは致命的エラーのトラップであり、未定義 FN の黙殺は存在しない。

## 6. 残件

1. `0x261260` の対象オブジェクトの同一性 (docs/27 §2.2 の留保): 「素材長・素材」を書く +0x8B4/+0x8B8 と、GENERIC の「スロット番号」を書く +0x8B4/+0x8B8 が同一オブジェクトで両立するかは、本段でも未解消。巨大関数 `0x23FFC8` の case 0x11 分岐でレジスタが保持するオブジェクトの同定が必要。(第16段で解決: 対象はストリーム文脈で同一、意味論は経路依存。[docs/30](30_xcode_fw_drm_phase16.md) §4.7)
2. DRMCTRL 側の内部: 初期化 `0x2629F4` の実読、モード別ハンドラ表 (`0x3ED500`、実行時登録) の列挙、`0x261B7C` が呼ぶ暗号セットアップ `0x15490C` 等の実読は未実施。SECUREDTS の鍵が鍵オブジェクト内でどう保持・消費されるかはこの先の領分。(第16段で消化: 初期化とハンドラ表と暗号セットアップは実読完了。保持・消費の構造は確定したが、素材の書き手は未同定のまま残る。[docs/30](30_xcode_fw_drm_phase16.md))
3. 主 FW 投入ヘルパ `0x200E68` / `0x203274` の窓書込み実読 (docs/27 残件) は本段の入口に含めなかったため未実施のまま。製品のホスト SCRAMBLER は第2 FW 実装と確定済みであり、優先度は低い。
4. エンジン内部での鍵の扱い (E2 候補 (i)) は、従来通り FW イメージからは観測不能で実験系の問いとして残る。
