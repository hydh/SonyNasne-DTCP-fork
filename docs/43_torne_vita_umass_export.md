# 43. torne Vita 版 umass コンテナの書き出し実体 (ウケトルネ書き出し後の調査)

[39](39_torne_vita_static_analysis.md) §5 で存在を確認した録画保存先 FAT32 コンテナ (umass) は、当時ファイル 0 件で書き出し実体が未観測だった。本書は、本人が実機で録画・再生・書き出し (ウケトルネ) を一巡させた後にコピーしたコンテナを読み取り専用で調査し、書き出しファイルの構成と形式を同定した記録である。実機には接続していない。録画コンテンツや保護データの中身の復号は本調査の範囲外として実施していない (形式の同定まで)。

## 1. 対象コピーと同一性

- 所在: marnux `~/ダウンロード/torneMobileBackup/Vita_App02/ux0/umass/98D0C1F1…C72.img` (ファイル名は 16 進 32 文字、[39](39_torne_vita_static_analysis.md) と同じ名前)。
- サイズ: 4,294,967,296 バイト (ちょうど 4 GiB、[39](39_torne_vita_static_analysis.md) と同一)。
- SHA-256: `6eeb84ce35f37a31ababc9d1aaa6e8d57e4ec7dcffcd2e0ece4c4dfef0051491`。
- 同日午前にコピーされた VitaStorage 側の同名イメージ (SHA-256 `a9e38dd4…`) とはハッシュが異なり、VitaStorage 側は [39](39_torne_vita_static_analysis.md) と同じく空ディレクトリのみだった。つまり今回の Vita_App02 側コピーが書き出し後の状態であり、コンテナは書き出しによって更新されることがハッシュ差分でも確認できた。
- 調査方法: 7z による読み取り専用リスト、mtools による読み取り専用表示、自前の FAT32 パーサによるディレクトリエントリ走査 (削除エントリ含む)。マウント・書き込みはしていない。ファイル 3 件は一時領域へ読み取り抽出して形式を調べた。

## 2. コンテナの中身 (全リスト)

ディレクトリ構成 (括弧内は FAT 上の作成・更新時刻、いずれもイメージ内の記録値):

```
SceIoTrash/                              (2026-08-04 06:19:40、空)
MPE_ROOT/                                (2026-08-04 06:19:40)
  100AEV01/                              (2026-11-16 03:52:56、空)
TORNE/                                   (2026-08-04 06:19:40)
  recording/                             (2026-08-04 06:19:42)
    <送信元 nasne の MAC (16 進)>_<数値>.sth    3,456,268 バイト
    <送信元 nasne の MAC (16 進)>_<数値>.rid    2,333 バイト
    <送信元 nasne の MAC (16 進)>_<数値>.ts000  48,764,928 バイト
  unpromoted/                            (2026-08-04 06:19:42、空)
  epg/                                   (2026-11-16 03:52:02、空)
```

事実としての観測点:

- ファイルは `TORNE/recording/` 内の **3 件のみ** で、全て同じ接頭辞 `<MAC 16 進>_<数値>` を共有する 1 タイトル分のセットである。削除エントリは全ディレクトリを通じて 0 件、`SceIoTrash` も空だった。
- [39](39_torne_vita_static_analysis.md) 時点で存在したディレクトリ (SceIoTrash / MPE_ROOT / TORNE / recording / unpromoted) の時刻は 2026-08-04 のまま不変で、今回のセッションで `TORNE/epg/` と `MPE_ROOT/100AEV01/` が新規に現れた (どちらも空)。`TORNE/epg` は書き出し直前 (ファイル作成の約 10 秒前) に作られており、書き出しフローが初期化する作業ディレクトリとみられるが、中身は残らなかった。
- ファイル 3 件の FAT 時刻は作成 03:52:08–03:52:14、更新 03:52:10–03:52:54 (いずれも 2026-11-16)。この記録値が UTC だと解釈すると 12:52 JST となり、本人の書き出しセッションの時刻と整合する (解釈)。
- 接頭辞の MAC 部分は送信元 nasne の MAC アドレスと一致し、数値部分 (`1794796486…` で始まる 20 桁) は後述の `.rid` 内の u32 値と一致する。この u32 を Unix epoch 秒と解釈すると 2026-11-16 11:34:46 JST になる (解釈)。ファイル名は「送信元機器 + 録画 ID」で機械的に生成される命名規則である。

## 3. 各ファイルの形式同定

### 3.1 `.ts000` (48,764,928 バイト) — 映像本体 (保護済み)

- 先頭に MPEG-TS の同期バイト列 (188 バイト周期の `0x47`) は無く、全域 (先頭・中央で各 1 MiB を測定) のバイトエントロピーは約 8.0。平文の TS ではない。
- サイズは 192 では割り切れるが 188 では割り切れない (48,764,928 = 192 × 253,984)。ただし 192 バイト周期の構造 (先頭 4 バイト + TS パケット等) は観測されず、周期性のある平文構造は検出できなかった。
- 結論: 映像本体は全体が暗号化 (またはそれに準ずる保護) された形で格納されている。暗号化方式の特定は復号を要するため範囲外。

### 3.2 `.sth` (3,456,268 バイト) — PTHM コンテナ (サムネイル束)

マジック `PTHM` を持つコンテナで、構造は完全に復元できた:

| 領域 | オフセット | 内容 |
|---|---|---|
| ヘッダ | 0x00–0x17 | `PTHM`、バージョン 1 (LE u32)、LE u32 列 0x18 / 0x54 / 0x6c / 0xa0 (後続各領域のサイズ・位置と一致) |
| テーブル 1 | 0x18–0x6b | BE u32 の件数 = 20、続いて BE u32 × 20。単調増加し、増分は 2639 / 2640 の交互パターン (開始値 `0x03c072c7`) |
| テーブル 2 | 0x6c–0x10b | (LE u32 オフセット, LE u32 サイズ) × 20。オフセットは 268 から 172,800 刻み、サイズは全件 172,800 |
| ペイロード | 0x10c–終端 | 172,800 バイト × 20 ブロック (268 + 20 × 172,800 = ファイルサイズと一致) |

- ペイロード各ブロックのエントロピーは約 7.999 で、JPEG / PNG 等の画像マジックはブロック内に存在しない。172,800 バイトは 320 × 180 × RGB24 の 1 フレーム分と一致するが、平文の画像データではない (暗号化されているとみられる)。
- テーブル 1 の値の意味 (時刻か位置か) と単位は未確定。テーブル 2 がペイロードの (オフセット, サイズ) 表であることと、件数 20 が両テーブルで一致することから、`.sth` は「20 枚分のサムネイル (シーク用プレビュー) の束 + インデックス」という構造であると同定できる。

### 3.3 `.rid` (2,333 バイト) — 録画メタデータ (平文を含む)

バイナリ形式のメタデータファイルで、平文で読める項目と読めない項目が混在する:

- 先頭に BE u32 の小さな整数列 (1, 6, 12, 20, 80)。オフセット表とみられる。
- オフセット 0x14 から 32 バイトの高エントロピー領域 (ハッシュ値か暗号化ブロックかは未確定。復号は範囲外)。
- 送信元 nasne の MAC アドレス (6 バイト) が平文で含まれる。
- 時刻と読める BE u32 が複数ある: ファイル名の数値と一致する値 (= 2026-11-16 11:34:46 JST と解釈できる値) のほか、298 秒だけ離れた 2 値 (同日 20:30:30 / 20:35:28 JST と解釈できる値)。298 秒という長さは、`.ts000` のサイズから推定される書き出しコンテンツ長 (約 1.31 Mbps 換算で約 298 秒) と一致する。各値の意味 (録画時刻・放送時間帯等) の確定はしていない。
- **番組情報テキストが平文 UTF-8 で含まれる**: (ID, 長さ) 前置きのブロック形式で、番組名「５分でみんなの手話（４）家族」、概要 (120 バイト)、番組内容・出演者の詳細 (498 バイト) がそのまま読める。つまり番組メタデータは暗号化されていない。
- 末尾側には (ID, オフセット) 風のペア列や単調増加列を含む構造化バイナリが続く (チャプターや属性情報とみられるが、全パースはしていない)。

## 4. ウケトルネ仕様 ([40](40_torne_vita_pfs_decrypted_analysis.md) §3.2) と実ファイル構成の対応

[40](40_torne_vita_pfs_decrypted_analysis.md) で文面から確認した仕様と、今回の実ファイル構成は次のように対応する:

- **「書き出したビデオは、保存場所を作成した PS Vita でのみ再生できる」** ↔ コンテナ自体は素の FAT32 でコピー自体は自由にできる一方、映像本体 (`.ts000`) とサムネイル束 (`.sth` のペイロード) は全域が暗号化されており、平文として取り出せるのは番組メタデータ (`.rid`) だけだった。機器束縛はファイルシステム層ではなくコンテンツ暗号化の層で実装されている、という実装形と整合する。
- **「保存場所を削除すると、書き出したすべてのビデオも削除される」** ↔ 書き出し 1 タイトルは `TORNE/recording/` 内の 3 ファイル (`.ts000` / `.sth` / `.rid`) で完結しており、コンテナ (= 保存場所) 単位の管理と整合する。
- **「1 台の Vita で使えるメモリーカードは 4 枚まで」** ↔ 書き出し先がメモリーカード上の固定名コンテナイメージ (ファイル名 = 16 進 32 文字の ID) として管理される形と整合する (カード側の登録情報そのものは本コンテナ内には無い)。
- **`unpromoted` の役割**: 今回の書き出しは `recording/` 側に入り、`unpromoted/` は依然として空だった。名称からの推測の域を出ないが、「昇格 (promote) 前の一時置き場」ではなく、通常の書き出しでは使われない別経路 (未昇格コンテンツ用) の置き場である可能性が残る。
