# 24. XCode ファームウェア DRM モジュール解析 第10段 — ブート記述子の実読とパーソナリティ決定機構、転送番号の mhcmd 対応、リングキュー投入側の同定

第9段 ([docs/22](22_xcode_fw_drm_phase9.md)) が残した 3 つの入口 — (1) 自己初期化 `0xB0791C` の唯一の呼出し元 `0xB8BDE0` とブート記述子の出所、(2) 送信関数 `0xC5C8A4` と転送番号 10/12/14/16・定数 `0x40003` の意味、(3) 孤児コード境界復元の継続 — を実読した。結論として、ブート記述子は静的構造体 `0xD06378` でポインタはコンパイル時定数であり、タスク表は単一の静的表を全プロセッサが共有すること (「proc6 用タスク表」は存在しない)、転送番号は mhcmd の FunctionNumber そのもの (10 = CTRL_STREAM、12 = OUTPUT_READY、14 = STREAM_STATUS、16 = RSA_INPUT_READY) であること、リングキュー `0x1483840` の投入側 (投入 API `0xBC390C` と呼出し元 4 件) を同定した。第9段の読解 2 件 (アロケータとされた `0xB87A44`、転送器が書く「記述子の第 1 ワード」) は本段の実読で訂正する。SCRAMBLER (mhcmd 37) / READ_FROM_OTP (45) のハンドラ本体は本段でも未同定で、(a)/(b) 境界・OTP index 境界も未判定のままである。ただし proc6 の wrapper メインとその継続部まで実読が進み、探索範囲は §6 の候補群まで狭まった。

## 1. 対象と方法

### 1.1 対象

- 第2 FW イメージ `fw_second_plain.bin` (2,771,804 バイト、SHA-256 `a4ff86b2d7287356519d9955da2f26a4e886b79be7ae3aa212c9e2f0298a9c3a`、ロードベース `0xB00000`、ISA = ARC (ARCompact))。第9段と同一イメージであることを本段開始時に再検証した。
- 実機には触れていない。静的解析のみ。

### 1.2 方法

- Ghidra 12.1.3 + ARCompact SLEIGH。第9段の解析済みプロジェクト (2,595 関数 / 325,017 命令) のコピーと、未解析の新規インポートの 2 本立てで進めた。前者は既存の関数範囲と xref を使う実読用、後者は M2 (既知入口からの線形逆アセンブル) 用。
- 手法は第9段 §1.2 の M1〜M6 を踏襲し、本段ではヘッドレス用スクリプト 4 本を追加した: Dump10 (関数単位の listing + xref + デコンパイル試行)、DisRange10 (未解析プロジェクトでの指定範囲の線形逆アセンブル)、ListRange10 (解析済みプロジェクトの既存逆アセンブルを範囲表示)、ScalarScan10 (スカラー即値と参照先の census、M6 の実装)。
- Ghidra のデコンパイラは本段の対象関数でも大半が空出力を返したため、実読は listing ベースである (第9段と同方針)。
- 本段で解析プロジェクトへ加えた変更は 1 件のみ: 関数 `0xB8BDE0` の範囲を `[0xB8BDE0, 0xB8BE7F]` に再定義し `boot_config_init` と命名した (自動解析の範囲は末尾を取りこぼしていた)。

## 2. 結論サマリ

1. **呼出し鎖は一本道**: リセットスタブ (`0xB00000`) → `0xB864B0` → `0xB8BDE0` → `0xB0791C`。各段とも xref は単一で、ブート記述子ポインタ `0xD06378` は `0xB8BDE0` 内のリテラルプールから供給されるコンパイル時定数である (§3.3、§3.4)。
2. **パーソナリティの決定機構**: タスク表は単一の静的表 (`0xCF1DC4`、6 レコード) で全プロセッサ共有であり、設定ブロック経由で切り替わることはない。ブート時に OS が生成するのは初期タスクと `wrapper_task` のみ (レコード `+0x14` の bit0 規則、§3.8)。残り 5 タスクは実行時の生成サービス (ID 引き、§3.9) で作られる。プロセッサ差は IDENTITY による分岐と、各メインが登録するハンドラ集合の差で生じる (§3.10、§3.11)。
3. **転送番号 = FunctionNumber**: 10/12/14/16 は mhcmd の CTRL_STREAM / OUTPUT_READY / STREAM_STATUS / RSA_INPUT_READY (一次資料で確定、§4.5)。内側パケット `+0x08` の `0x40003` は下位ハーフワードが宛先プロセッサ索引 (= 3) で、投入関数 `0xC70530` が宛先のメールボックススロットへ内側パケットポインタを直接書く (§4.4)。
4. **リングキューの投入側を同定**: 投入 API `0xBC390C` + エンキュー核 `0xC4E3E8`。呼出し元は `0xC75Dxx` のスイッチ内 4 件で選択子 1–4 に対応し、投入後には受信タスクを起床させる機構がある (§4.7)。
5. **第9段の訂正 2 件**: `0xB87A44` はアロケータではなくコンテキスト保存 (setjmp 型) ルーチン (§3.6)。転送器がパケットへ書くのは「記述子の第 1 ワード」ではなく、要素として渡された値そのもの (§4.2)。
6. **SCRAMBLER ハンドラは未同定のまま**。ただし proc6 の wrapper メイン `0xC4E4FC` とその継続部 (孤児ブロック) まで実読し、要求ディスパッチが含まれないことを確認した。残る候補は §6 に列挙する。

## 3. 入口 1: `0xB8BDE0` とブート記述子の出所

### 3.1 リセットスタブ (事実)

`0xB00000` から `0xB00140` を未解析プロジェクトで線形逆アセンブルして実読した。

- aux レジスタ 0x10 へ 0、0x47 へ 1 を書き、aux 0x200 の値を `[0x200]` へ複写する。
- IDENTITY (aux 0x04) の bits 15–8 = プロセッサ id を読む。id 3 と id 6 はカウンタ `[0x90]` を、id 4 はカウンタ `[0x98]` を増やし、それ以外は `[0xA0]` へ `0xBAD70000 + id` を記録する (ブート回数の数えと異常 id の記録)。
- スタック設定前に `r0 = 0` で `0xC93D34` を呼ぶ (この領域の関数は §5.2 のメールボックス系プリミティブと同じ 0xC93Dxx 域にある)。
- スタックポインタは id 別: id 4 → `0x1543FB0`、id 6 → `0x1545FB0`、その他 (id 3 を含む) → `0x1541FB0`。`gp = 0xDA4B20` (全プロセッサ共通)、`fp = 0`。
- `0xB864B0` を呼び、復帰後は halt ループ (`flag 1` と nop の繰返し) に入る。

### 3.2 `0xB864B0` プラットフォーム初期化 (事実)

- リセットスタブからの唯一の xref を持ち、`0xB8BDE0` の唯一の呼出し元である。
- フラグセル `0xCF1C48` / `0xCF1C4C` のガードの下で、リテラル (実測値 `0xDA0F80` と `0x140046C0`) から共有 RAM 域 `[0xDA0F80, 0x140046C0)` を `0xB8CCEC` (ゼロフィル) でクリアする。担当範囲 (§3.5) を含む広い域の一度きりのクリアである。
- `0xB8E600`、`0xB89378` (リテラルが 0 の場合)、`0xB89414` を経て、`0xCF1C48` のバイトをクリアした直後に `0xB8BDE0` を呼ぶ。復帰側は `0xB86414` / `0xB86428` への末尾呼出しと `0xB8E66C` への分岐で構成される (`0xB8E6xx` は共有末尾サンク群とみられ、本段では未読)。

### 3.3 `0xB8BDE0` の実読 (事実)

関数範囲を再定義したうえで実読した。

- `0xB0791C` の呼出しは `bl.d` で、その遅延スロットがリテラルプールのワード (= `0xD06378`) を `r0` へロードする。**ブート記述子ポインタはコンパイル時定数であり、ブートスタブや他プロセッサから渡されるものではない**。
- 続いて `0xB8678C` を呼ぶ (ロックワード `0xCF1C54` による一回性ガード付きの初期化で、戻り値はポインタとして保持される)、セル `0xCF1D6C` (静的値 1) の一回性ガードで同期オブジェクト初期化 `0xB095C0` を 1 回だけ実行し、`0xB0679C` / `0xB08418` / `0xB08644` の列 (エラー時は末尾の `0xB8BFCC` へ合流) を経る。
- 最後に、リスト (ヘッドセル `0xCF1D70`、静的ヘッド `0xD05C98`、ノード間隔 0x28 とみられる記述子ブロック列) からノードを取り出し、その `+0x0C` を `0xB095C0` で初期化し、ノードポインタを `0xB8678C` の戻り先 (`*r16`) へ格納して `0xB8E65C` へ末尾分岐する。

### 3.4 ブート記述子 `0xD06378` の全フィールド (事実)

静的バイト列の実測 (ファイルオフセット `0x206378`):

| オフセット | 値 | 意味 (実読で確定した範囲) |
|---|---|---|
| +0x00 | 1 | ブートしたプロセッサの id で `0xB0791C` が上書きする |
| +0x04 | `0x00DA8000` | 担当範囲の始点 S |
| +0x08 | `0x013A7FFF` | 担当範囲の終端 E |
| +0x0C | `0x1000` | §3.7 の部分割当てサイズの下限に使われる |
| +0x10 | `0x00CF1DC4` | タスク表ベース |
| +0x14 | 2 | 未確定 |
| +0x18 | `0x10` | 未確定 |
| +0x1C | `0x80` | 未確定 |
| +0x20 | `0x00CD3D74` | デバイス表ポインタ (先頭は文字列 `ttya:` と小レコード列) |
| +0x24 | 7 | 未確定 |
| +0x28 | 0 | — |
| +0x2C | 0 | — |

`+0x10` はセル `0xD06388` の保持値と一致する。第9段 §4.3 で「タスク表ベースポインタを保持するセル」とした `0xD06388` の実体は、この記述子内のフィールドだった。

### 3.5 範囲分割の精密化 (事実、第9段 §4.3 の補足)

- `0xB0791C` の `r3 = (E − S + 1) / 3` はソフトウェア除算で実装される (小さい商向けの反復減算経路と、正規化つきビットシリアル除算経路の双方とも除数は 3)。
- 実数: 件数 `0x5F8000`、1/3 は約 `0x1FB555`。proc3 = `[S, S+r3−1]`、proc4 = `[S+r3, S+2r3−1]`、proc6 = `[S+2r3, E]` (剰余は proc6 が吸収する)。
- コンテキスト保存先 `0x13A8000` は E + 1 ちょうどである。
- id が 3/4/6 以外の場合は致命的エラーレコード (`0xDEADC0DE`) を書いて無限ループする。

### 3.6 訂正: `0xB87A44` はコンテキスト保存ルーチン (事実)

実読の結果、`0xB87A44` は割当て器ではない。`r13–r25`、`gp`、`fp`、`sp`、`ilink1`/`ilink2`、`blink`、`lp_count`、`lp_start`/`lp_end` (aux 0x2/0x3)、`status32` (aux 0xA) を `[r0 … +0x58]` へ保存し、遅延スロットで `r0 = 0` として戻る setjmp 型のルーチンである。

`0xB0791C` ではセル書込みの前に `r0 = 0x13A8000` で呼ばれる。戻り値 0 → 本初期化経路へ進む。後刻にコンテキスト復元で非ゼロ再入した場合は、自設定の `+0x178`/`+0x17C` を読み、`0xB08FE4` を呼んで `0xB07CD0` へ復帰する。第9段 §4.3 の「割当て失敗時のフォールバック」という読解は本実読で置き換える。

### 3.7 設定ブロック初期化の内訳 (事実)

- 設定ブロックのベースは担当範囲始点を 32 バイト整列した点で、サイズは `0x494` (`0xB09060` = ゼロフィル `0xB8CCEC` のラッパで初期化)。`cfg+0x21C` の bit0 が立つ。
- 記述子の 0x30 バイトを `0xB86808` (memcpy と同定) で `cfg+0x100` へ複写する。`cfg+0x104` へは自己ポインタ、`cfg+0x108` (複写された E) は `−0x20` でマスクされる。
- `0xB09354` (設定プール内アロケータ) による部分割当てが 2 件ある: 1 件目は `max(cfg+0x10C [= 記述子 +0x0C = 0x1000], 0x134) + 0x20`、2 件目は固定 `0x134`。`cfg+0x60` へ 1 件目の整列済み終端、2 件目の終端・上限は `cfg+0x370`/`+0x374`/`+0x378` へ書かれる。またセル `0xCF00E4` へも値が書かれる (3 つの設定セルに加わる 4 本目のポインタセル。意義は未確定、§7)。
- `0xB0910C` (フィールド初期化、呼出し元は `0xB0791C` のみ) の主な書込み: `+0x00 = 8`、`+0x04 = 1`、`+0x0A`/`+0x0C` (ハーフワード) `= 0x1F`、`+0x0E = 2`、`+0x10 = 0x2BFE`、`+0x12 = 0x7C`、`+0x30 = cfg+0x100` (複写された記述子 +0x00、すなわちブート時 id)、`+0x178 = 0xB09014 の戻り` (aux 0x25 を読み下位 10 ビットを落とした値。ハードウェアリビジョン相当)、**`+0xC8 = cfg+0x110` (= 記述子 +0x10 = `0xCF1DC4`)**、`+0xCC = 1`、`+0x188 = 1`、`+0x1C = cfg+0x3AC` (設定ブロック内蔵の初期 TCB)、`+0x36C = id << 16`、`+0x368 = 3`、`+0xE0 = 0x80000003`、`+0xE8 = 0x150`、`+0xE4 = 0xB09CEC` (コードポインタ)、`+0xF0 = 0xCE325C` (データポインタ)、リストヘッド類の自己参照初期化。`+0xC8` が 0 ならエラー `0x1001` を `0xB07D2C` で報告する。
  - **タスク表ポインタ `+0xC8` は全プロセッサとも単一の静的表 `0xCF1DC4` を指す**ことがここで確定した。
  - タスク表走査: レコード (ストライド 0x20、先頭ワード 0 で終端) を数えて `cfg+0xC4 = 6`。併せてレコード `+0x0C` の値を `cfg+0x184` へ集約し `cfg+0xEC = その値 + 1` とする。集約が最小・最大のいずれかは比較と条件付き代入のパターンから本段では確定できなかった (§7)。
- `0xB092B8` (プール初期化、呼出し元は `0xB0791C` のみ): `cfg+0x170 = 0x6D656D70` (ASCII `pmem`)。`0xB09D68 (cfg+0x494, cfg+0x108, cfg+0x64)` が `[cfg+0x494, 範囲終端)` をそのプロセッサのヒープとして初期化する。すなわち担当 1/3 の残り全部がヒープである。
- `0xB094F8`: 優先度別キューヘッド配列を `cfg+0x28` に構築する (`(cfg+0xEC + 1) × 0x10` バイトを `0xB09F94` で確保し、各エントリ {自己, 自己, 旧ヘッド, `+0x0C` (hw) = 6, `+0x0E` (hw) = 索引} を連結)。
- `0xB095C0` は同期オブジェクト (ミューテックス/セマフォ) の初期化子である: `obj+0x18` へ初期値、`obj+0x08`/`+0x0C` は自己参照リストヘッド、`+0x10`/`+0x12` (hw) を 0 とし、`0xB0497C` を呼ぶ。`cfg+0x21C` bit0 が立つ場合は OS イベント通知プリミティブ `0xB05ADC` で包む。`0xB05ADC` のコードの実測例: `0x101` = タスク起動 (§3.9)、`0x1007` (`0xB09354` 内)、`0x2000F` (本関数内)。
- `0xB80080` は `0xB0791C` から呼ばれるサブシステム初期化で、`+0x1F8 = 3`、`+0x1FC = 0xFFFF159F`、`+0x200 = 200`、`+0x204 = 60000`、関数ポインタ `0xB80240`/`0xB80264` を書き、`0xB804D8 (i, 0x26)` のループと `0xB06A20 (3, 0xB802BC, 0)` を実行する。実体は未同定 (§7)。

### 3.8 ブート時タスク生成の規則 (事実)

- `0xB0791C` はまず `r0 = cfg+0x1C` で 1 回タスク生成する。設定ブロック自身のフィールド群が擬似レコードとして使われる初期タスクである (レコード相当の読み: `+0x08 = cfg+0x24`、`+0x0C = cfg+0x28`、`+0x14 = cfg+0x30` = プロセッサ id、`+0x1C = cfg+0x38`、複写フラグ `r3 = 1`)。
- 続いてタスク表 (`cfg+0xC8`) を走査し、**レコード `+0x14` の bit0 が立つものだけ**を生成し `0xB07820` で起動する。静的表で bit0 が立つのは `wrapper_task` (ID 7、`+0x14 = 1`) のみで、他の 5 レコード (ID 11 `uist_mv_conversion`、ID 12 `proc4_incoming_request_process`、ID 14 `avc_dec_init_task`、ID 13 `avc_encoder_task`、ID 15 `proc4_SoftGVD`) は全て `+0x14 = 0` である (レコードと名前文字列は静的バイト列で再確認した)。生成失敗は `0xB07D2C` でコード `0x1004` として報告される。
- 走査後に `0xB04C28` が `cfg+0x12` (ハーフワード) の bit `0x8000` を立てる (ブート完了フラグ相当とみられる。解釈)。

### 3.9 タスク生成・起動プリミティブと実行時生成サービス (事実)

- `0xB074C0` = create_task (引数: レコード `r0`、`r1`、`r2`、`r3` = 複写フラグ、`r4`、`r5`): TCB を `0xB08D7C` で確保する (サイズはレコード `+0x08` のスタックサイズ、最小 `0x134`、32 整列、`+0x20` 追加)。`TCB+0x08 = 3` (状態)、`r3 ≠ 0` ならレコード 0x20 バイトを TCB 域へ複写し先頭ワードに bit31 を立てる。スタック域は `0xB077F4` で `0x7374616B` (ASCII `task` 相当のパターン) のスタック塗装がされる。`TCB+0x1C`/`+0x8C = [cfg+0x28] − (優先度 << 4)` (優先度別リスト)、`TCB+0x50` へそのヘッドの `+0x0C` (hw)、`TCB+0x40` = レコード ID、`TCB+0x54` = レコードポインタ、`TCB+0x6C` = レコード `+0x14` (フラグワードの複写。`r4 ≠ 0` なら bit5 も立てる)。レコード `+0x1C ≠ 0` なら時刻経路 (`cfg+0x18C` の 64 ビット tick を 1000 で割る等) を通る。エラーは `0xB07E04` (コード `0x100E`/`0x1002`/`0x100A`)。
- `0xB07820` = activate_task: TCB を doubly-linked な ready リストへ挿入し (`cfg+0x2C` を維持)、`TCB+0x08 = 2` (ready) とし、`TCB+0x7C`/`+0x80`/`+0x84` をゼロ化する。`cfg+0x21C` bit0 が立つ場合は `0xB05ADC (1, 0x101, task)` / `(2, 0x101, 0)` で包む。
- `0xB082E8` = 実行時のタスク生成サービス: 第 1 引数 (id) が非ゼロなら自設定のタスク表 (`cfg+0xC8`) から ID 一致レコードを検索し、0 なら第 2 引数のレコードを直接使う。内部で `0xB08418` を経て `0xB074C0` を呼ぶ。呼出し元は OS 域の `0xB064FC` (内部 `0xB066D8`) と `0xB067E0` (内部 `0xB069C0`) の 2 件。後者は §3.10 の proc4 メインから `(0, 14, 0)` で呼ばれた実測もある。
- 以上より、**静的表の 5 タスク (ID 11–15) はブート時には生成されず、この ID 引きサービス経由で実行時に生成される設計**であることまで確定した。どの呼出しがどの ID を生成するかは未確定 (§7)。

### 3.10 `wrapper_task` の分岐と 3 本のメイン (事実)

- `wrapper_task` 本体 `0xC8BAA8` は IDENTITY で分岐するだけの小関数である: id 4 → `0xC4DB98`、id 6 → `0xC4E4FC`、その他 (id 3 を含む) → `0xC4D63C`。
- 3 本とも同型の骨格を持つ: 共有通信域の先頭ワード `[0xAFE000] == 0x1D2C` のマジック確認 (不一致は致命的エラー)、通信記述子ブロック `0xAFF7F4` へのハンドラ登録、チェックポイント登録 (第9段 §3.5 と同型)、状態確認 `0xB04940`、`0xB0497C`、`0xB04A28` (yield) までが Ghidra の関数範囲に収まり、本ループは範囲外の孤児ブロックに続く (§5.1)。
- ハンドラ登録: `+0x174 = 0xC824A4` と `+0x17C = 0xC82410` は 3 本共通。proc4 メインはさらに `+0x178 = 0xC768E4`、`+0x180 = 0xC7BBAC`、`+0x184 = 0xBE31E8`、`+0x188 = 0xC48A4C` を登録し、OS プリミティブ `0xB04940`/`0xB0497C`/`0xB04A28` のポインタを共有表 `0xAFFD18`/`0xAFFD20`/`0xAFFD28` へ書く。
- チャネルハンドラ登録 `0xB06A20 (チャネル, 関数, 0)` の実測: proc3 メイン = (4, `0xBC3740`)、(8, `0xC74BBC`)、(7, `0xC74BBC`)、(6, `0xC75384`)。proc6 メイン = (4, `0xC7609C`)、(8, `0xC74BBC`)、(6, `0xC75294`)。proc4 メイン = (8, `0xC74BBC`)、(6, `0xC75294`)、(4, `0xBC3E58`) (§5.2)。
- proc4 メイン (`0xC4DB98`) の追加初期化: キュー文脈 `0x1483840` の初期化 (§4.7)、文脈 2 (`0x1483980`、サイズ `0x5CC` のゼロ化とエントリ初期化)、文脈 3 (`0x1483F4C`、先頭ワード = `0x13F99A0`)、記述子ブロック `0xD8B05C` へのマジック書込み (`+0x40 = 0xABCD0000`、`+0x140 = 0xABCD1111`)、共有構造 `0xCF0000` の初期化、`0xB067E0 (0, 14, 0)` の呼出し等。
- 補助レジスタ 0x100/0x101/0x102 への割込みコントローラ相当の設定は周期値がプロセッサごとに異なる: proc6 メイン = `0x200000`、proc3 メイン = `0x2D5190`、proc4 メイン = `0x400000`。

### 3.11 パーソナリティ決定機構のまとめ (確定範囲)

- 静的に切り替わるタスク表は存在しない (記述子 `+0x10` は単一値、設定 `+0xC8` は全プロセッサとも同値)。
- プロセッサ差は (a) IDENTITY による設定セル・担当範囲・スタックの選択、(b) `wrapper_task` の 3 分岐、(c) 各メインの登録ハンドラ集合と初期化対象の差、で全て生じる。
- したがって「proc6 に SCRAMBLER ハンドラが載るか」はタスク表では決まらず、proc6 側の実行コード (メイン `0xC4E4FC`、その登録ハンドラ、実行時生成タスク) の中に在るかで決まる。本段で `0xC4E4FC` とその継続部は実読したが要求ディスパッチは無かった (§5.1)。登録ハンドラ `0xC82410` / `0xC824A4` / `0xC7609C` / `0xC75294` 等は未読であり、断定はしない (§6)。

## 4. 入口 2: 送信関数 `0xC5C8A4` と転送番号

### 4.1 パケット取得 `0xBF6E00` (事実)

- 引数は (FunctionNumber N, `0x40003`)。プール (セル `[0xAFEB68]` の指す先) から `0xBDF164` でパケットを取り、`+0x08 = 0x40003`、`+0x0C = N`、`+0x10 = 0`、`+0x14 = パケット +0x2C` (ヘッダ直後のインラインペイロードへのポインタ)、`+0x18 = 0` を書く。
- [docs/12](12_xcode_fw_drm_phase4.md) §3 の `MIPSHOSTCOMPACKET` (全て uint32、サイズ 0x2C) と対応させると、`+0x0C` = FunctionNumber、`+0x14` = Input で符合する。`+0x08` はホスト側ヘッダの Direction (1 = HOST2MIPS / 2 = MIPS2HOST) とは異なる値であり、FW 内部パケットでは宛先索引を含む符号化になっている (§4.4)。

### 4.2 転送器の精密化 (事実、第9段 §3.7 の訂正を含む)

転送器 `0xC45BEC` (選択子 1) を実読した。

- カウンタ `0xCF88E0` を増やし、`[0xCF88DC]` へ引数 (要素の第 2 ワードとして渡された値) を保存する。
- `0xBF6E00 (10, 0x40003)` を呼ぶ。第 2 引数は `mov r1, 3; bset r1, r1, 0x12` で組み立てられる (= `3 | 1<<18`)。
- パケット `+0x14` の指す先 (インラインペイロード先頭) へ **引数そのもの**を書く。第9段 §3.7 の「記述子の第 1 ワードを書く」は、「要素として渡された値を書く」に訂正する。その値の出所は投入側 (§4.7) で、要素の第 2 ワードは投入者の記述子の `+0x04` ワードである。
- 送信呼出しは `0xC5C8A4 (値, N, パケット, 0, 0, 0x40003)` で、成功するとカウンタ `0xCF88E4` を増やす (第9段の観測と一致)。

### 4.3 送信 `0xC5C8A4` (事実)

- プールから封筒パケットを `0xBDF164` で別途確保する。失敗時はエラーカウンタ `[0xDA3DA4]` を増やして戻り値 2 で戻る。
- 引数のパケットが 0 の場合は `0xBF6E00 (N, 0x40003)` で内側パケットを作る。失敗時は封筒を `0xC2C41C` で解放し、戻り値 2 で戻る。
- 封筒への書込み: `+0x0C = 0x100`、`+0x10 = 0`、`+0x14 = −1`、`+0x18 = 第 1 引数`、`+0x24 = 内側パケットポインタ`、`+0x2C = 第 4 引数`、`+0x28 = (第 4 引数 ≠ 0 のとき第 5 引数、0 のとき 0)`。
- `+0x24` にポインタが入る点で、この封筒は `MIPSHOSTCOMPACKET` (同オフセットは procIdx) とはレイアウトの異なる内部転送構造である (事実)。`+0x0C = 0x100` の意味は未確定 (§7)。
- 送信はスピンフラグ `[0xAFEB08]` を `0xC8A868` で待ち、`0xC70530 (封筒)` で投入し、`0xC8B488` でフラグを解放する。戻り値 0 = 成功、2 = 失敗。

### 4.4 投入 `0xC70530` と宛先決定 (事実)

- 自己索引は `0xC8B5E0` の戻り値で、通信記述子をストライド `0xF4` で索引化する (第9段 §3.5 で、致命的エラーレコードへ書かれるプロセッサ番号の出所として同定済みの関数)。
- `0xC5B898 ([自記述子 +0x78], 封筒)` で変換/検証し (戻り 0 なら中止)、送信元別カウンタ `[0xD8F33C + 自己索引]` を増やす。
- **宛先は内側パケット `+0x08` の下位ハーフワード** (`extw` で取り出す)。宛先が 7 以上、または自己索引と一致する場合はエラー記録 (`0xC8B348` にコード `0x60`/`0x61`) のうえ致命的エラー経路へ進む。
- 宛先スロットのアドレスは `[0xAFE004] + ([自記述子 +0x7C + 宛先×4] >> 2)` と計算され、内側パケットポインタが直接書かれる (共有 RAM 上のメールボックススロットへのポインタ受け渡し)。
- 転送器のパケットでは `+0x08 = 0x40003` なので宛先索引は常に 3 である。bit 18 (`0x40000`) の意味は未確定 (§7)。

### 4.5 転送番号の mhcmd 対応 (確定)

GPL ドライバ一次資料 `mipshost.h` の `mhcmd` 列挙 (第4段で使用したものと同一系統のコピー) による対応:

| 選択子 | 転送番号 (FunctionNumber) | mhcmd 名 |
|---|---|---|
| 1 | 10 | CTRL_STREAM |
| 2 | 12 | OUTPUT_READY |
| 3 | 14 | STREAM_STATUS |
| 4 | 16 | RSA_INPUT_READY |

いずれも MIPS 側から相手側へ送る通知系コマンドであり、proc4 のワーカーが生成したイベントを他プロセッサへ転送する経路であることと整合する。第9段 §3.10 で未確定とした「転送番号と mhcmd 体系の対応」はこれで確定した。

### 4.6 宛先索引 3 のコア (事実と解釈)

- 索引 3 は IDENTITY id 3 のコア (wrapper メイン `0xC4D63C`) に対応すると読むのが自然である (番号空間の同一性は `0xC8B5E0` の使用法からの推定。解釈)。
- そのメインループ継続部 (§5.1) は共有パケット域 (`[0xAFE004]` 基点) の `+0xA0FC` ワードをポーリングし、`(値 & 0xF000) == 0x1000` のときにそのビットを落として書き戻す処理を行う。proc4 のチャネル 4 ハンドラ `0xBC3E58` (§5.2) も同じ `+0xA0FC` ワードを `0xC93D78`/`0xC93DD0` で読み書きする。`+0xA0FC` ワードはプロセッサ間 (およびホスト) のメールボックス/ドアベルであり、索引 3 のコアがその集約・中継点であるという像が得られる (構造は事実、役割の命名は解釈)。

### 4.7 リングキューの投入側 (事実、同定完了)

- 初期化 `0xC4E4B8` (呼出しは proc4 メイン `0xC4DB98` のみ): 文脈 `+0x01` から `0x12C` バイトをゼロ化し、`+0x108 = 文脈自身`、`+0x100 = +0x104 = その値` (リング先頭) とする。リング本体は文脈先頭からで、ポインタ 3 本は `+0x100` (書込み) / `+0x104` / `+0x108` (読み) にある (第9段 §3.3 の読みと整合)。
- 投入 API `0xBC390C (記述子ポインタ r0, 選択子 r1)`: スタック上に要素 `{選択子, [記述子 +0x04]}` を組み、エンキュー核 `0xC4E3E8 (文脈 0x1483840, 要素)` を呼ぶ。戻りが負なら `0xB8EA08 (0, 0x3B2)` でエラー記録する。その後、セル `[0xD8B45C]` が非ゼロで、現在タスクの `[task+0x08]` のマジック `0xABCD00F1` が受信タスクのものと一致すれば、`0xB0582C` でそのタスクを起こす。
- 呼出し元は 4 件とも `0xC75Dxx` の同一スイッチ内にある。いずれも `r0 = [r18 +0x14]` (呼出し側文脈の記述子フィールド) を渡し、選択子は 1/2/3/4。選択子 1・2・4 の経路では先に `0xBC3698` をオブジェクト `0xCE0960` / `0xCE0980` / `0xCE09A0` (0x20 間隔の列。ロック相当) に対して呼び、結果に応じて `[r18 +0x10]` のカウンタを進める。
- census の範囲 (事実): イメージ内で文脈アドレス `0x1483840` とポインタセル (`+0x100`/`+0x104`/`+0x108`) を即値・参照で触るコードは、解析済み関数の範囲では `0xBC390C` (投入)、`0xBC39A4` (受信)、`0xC4DB98` (初期化呼出し) のみである。孤児コード内とポインタ経由のアクセスはこの census の範囲外であり、投入者がこの 4 件に限るとまでは断定しない。

## 5. 入口 3: 孤児コード境界復元の継続

### 5.1 wrapper メイン 3 本の継続部 (孤児ブロック) の実読 (事実)

Ghidra の関数範囲から漏れていた継続部を、未解析プロジェクトでの線形逆アセンブル (M2) で実読した。

- **proc4 メイン継続部** (`0xC4DF5C`–): チャネル登録の残り (8, `0xC74BBC`)、(6, `0xC75294`)、(4, `0xBC3E58`) を行い、`0xC2D2A4 (0xD8EA38, 0x101B00)`、`[0x1017F0 +0x68] = 0xD8E938` / `+0x58 = 0xD8E13C` の書込み、`0xBB3C8C` を経て yield 後に主ループへ入る。主ループは文脈 2 の `[0x1483980 +0x8C]` をポーリングし、非ゼロなら `0xBB5E6C` を呼ぶ (ポーリング回数の上限 `0x2710` = 10000)。
- **proc6 メイン継続部** (`0xC4E670`–`0xC4E70C`、およびタイムアウト側 `0xC4E7C0`–): ドアベルバイト `[0x100508]` が `0xCC` になるのをポーリングする (上限 `0x989680` = 10,000,000 回)。途中でカウンタ `[0xD8BF30]` が 0 を打つたび `0x3E8` に戻して `0xC6B118` を周回呼出しする。タイムアウト側では共有パケット域の `+0xA0FC` ワードを読む。**この範囲に要求処理のディスパッチは含まれない** (事実の範囲: `0xC4E4FC` の関数範囲 + 継続部 + タイムアウト側の線形逆アセンブルで読んだ範囲)。
- **proc3 メイン継続部** (`0xC4D7FC`–): カウンタ `[0xD8FF0C]` を増やしながらドアベルバイト `[0x100508] == 0xCC` を待ち (上限 10,000,000 回)、タイムアウトで `+0xA0FC` メールボックス処理 (§4.6) を行う。
- ドアベルバイト `[0x100508]` とカウンタ `[0xD8BF30]` は、受信タスクのデキュー関数 `0xC4E450` (第9段) でも同じパターンで現れる共有シグナルである。

### 5.2 `0xBC3E58` は単一の巨大関数 (事実)

- proc4 メインが `0xB06A20 (4, 0xBC3E58, 0)` で登録するチャネル 4 ハンドラである。
- プロローグ census (M3 のバイトレベル版): 範囲 `0xBC3E58`–`0xBC5162` 内に、フレーム確保型プロローグ (`st.a fp,[sp,−N]` のバイトパターン) は開始点の 1 件のみ、`push_s blink` 型プロローグは 0 件だった。**この範囲は関数分割されておらず、`0xBC3E58` から始まる単一関数の内部ブロックである** (2 種のプロローグパターンの全数走査による裏付け)。
- 内容 (頭部〜中部の実読): 呼出しカウンタ `[0xDA4378]` と `[0x101908]` の増加、ドアベルバイト処理 (`0x88` なら `0xB05E9C` を呼んでバイトを 0 に戻す。`0xCC` なら致命的エラー)、メールボックス `+0xA0FC` の読み書き (`0xC93D78`/`0xC93DD0`、状態ワードの `(値 & 0xF0000) == 0x10000` 分岐、スピンフラグ `[0xAFEB10]`)、記述子ブロック `0xD8B05C` のフィールドポインタ群の構築 (`+0x34` へ 1 を書く)、文脈 2 のパケットリスト (`[0x14839F0]` を先頭に `+0x18` = NextPacket で連結され、`+0x0C` = FunctionNumber を見て振り分ける) の走査と多数のヘルパ呼出し (`0xBC94F4`、`0xBA1FF8`/`0xBA2088`、`0xC94018` 等)。受信パケットの FunctionNumber による振り分け本体はこの関数の中にある (個別コマンドの分岐先の確定は次段の残件、§7)。
- この関数はリングキュー `0x1483840` へは書かない (範囲内の実読と §4.7 の census の双方で確認)。

### 5.3 ワーカー 4 (`0xC6B5AC`) の構造 (部分実読)

- 全 1,784 命令。呼出しの大半は `0xC95AE0` の反復 (数十回) で、境界値 `0x10`/`0x20`/`0x40`/`0x80` の比較が密に現れる。頭部では `0xC93D50` (メールボックス系プリミティブ) を 2 回呼ぶ。
- 選択子 4 = RSA_INPUT_READY (§4.5) のワーカーであり、バッファを小さいチャンク単位で繰り返し処理するデータステージング動作と整合する (解釈)。全行の実読はしていない。

### 5.4 主 FW 側の孤児コード (未着手)

本段では未着手である (第2 FW 側の入口 1・2 の実読を優先した)。主 FW の孤児コード (約 23%) への M1〜M6 の適用は次段以降の残件とする。

## 6. SCRAMBLER / READ_FROM_OTP ハンドラの所在についての現時点の整理

- ホストからの配送は [docs/12](12_xcode_fw_drm_phase4.md) の確定通りで、SCRAMBLER は procIdx 6、その他のセキュリティ系 (SET_KEYSTORE_KEY / READ_FROM_OTP / RSA 系) は proc0 である。proc0 は本イメージ (第2 FW) の担当範囲 (id 3/4/6) には無い。
- proc6 側で本段までに実読した範囲 (ブート初期化一式、wrapper メイン + 継続部、タスク表) には、mhcmd の受信ディスパッチも SCRAMBLER 相当の処理も無い。
- 未読のまま残る proc6 関連の候補:
  - (a) 登録ハンドラ `0xC82410` / `0xC824A4` (全コア共通で通信記述子 `+0x174`/`+0x17C` に登録される。proc4 はさらに 4 本を登録する)。
  - (b) チャネルハンドラ (proc6 では (4, `0xC7609C`)、(6, `0xC75294`)、(8, `0xC74BBC`))。
  - (c) 実行時生成タスク (ID 11–15) のうち proc6 で生成されるもの。
  - (d) `0xC6B118` (proc6 メインが周回呼出しする関数。ワーカー 3 `0xC6B03C` / ワーカー 4 `0xC6B5AC` と同じ `0xC6Bxxx` 域にある)。
- (a)/(b) 境界 (トークンが ARC コードで加工されるのか、そのまま HW / 他プロセッサへ渡るのか) と OTP index 境界は引き続き未判定である。本段の結果は「ハンドラは少なくともブート経路と wrapper メインには無い」という探索範囲の縮小であり、不在の断定ではない。
