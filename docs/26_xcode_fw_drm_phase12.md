# XCode ファームウェア DRM モジュール解析 第12段 — 鍵ストアスロットの消費側

対象: 第2 FW (`fw_second_plain.bin`、ロードベース `0xB00000`) と主 FW (`fw_main_plain.bin`、ロードベース 0)。第11段 ([docs/25](25_xcode_fw_drm_phase11.md)) で未確定として残った「鍵ストアスロットの消費側」を追った。入口は (1) 投入先 `0xC5C344` と完了コールバック `0xC4AD58` の実読、(2) スロット参照の消費側 census (両イメージ)、(3) 消費側での変換の有無、(4) 状態ブロック +0x8B0 台の書き手、(5) IVDR/AACS ヘルパと完了系ハンドラの実読。

**結論 (本段の到達点)**:

- **投入先の追跡を完了した**。`0xC5C344` は FN=0x100 の通信オブジェクトを組み、チャネルオブジェクト `[0xAFF938]` のキューへ入れる。先頭オブジェクトは `0xC6FFF4` が即時実行開始し、記述子チェーン基底を共有域 `[B+0xC04]` (B = `[0xAFE004]` の値) へ書き、開始ビット `[B+0xC58]=2` / `[B+0xC5C]|=2` を立てる。完了は `0xC7488C` が状態ビットを見て検出し、登録コールバック `0xC4AD58` を呼び、次オブジェクトを起動する。**「記述子を受け取るプロセッサ」は存在せず、チェーン実行は共有域レジスタを介してエンジン側が担う構造**である。
- **スロットのデータワードを読む FW コードは、両イメージの解析範囲に存在しない** (census の方法と範囲は §3)。投入側と消費側の接点は index ワードの bit31 ハンドシェイクのみであり、消費者は FW の外 (エンジン側) である。
- **消費側でも FW コードによる変換は存在しない** (読み手自体が FW 内にいない)。実効鍵の「解決」は、エンジンが記述子のスロット番号で鍵ストアを引く行為そのものである。エンジン内部でスロット値がそのまま鍵になるか内部変換があるかは FW イメージからは観測できない (未確定、§8)。
- **主 FW にも SCRAMBLER ハンドラの並行実装 `0x22F9E0` を同定した** (構造同型、§4)。両実装で AS_INDEX の極性が一致することを命令水準で確認し、**docs/25 §3.4 の極性の記述が逆だったことを訂正する**。あわせて docs/25 §3.6.4 の通信オブジェクト欄の帰属も訂正する (§2.1、§9)。
- **+0x8B0 台の書き手の一部を同定した**: +0x8B4 は AACS ヘルパ `0xBF9D4C` が +0x8B0 を複写する。+0x8BC (16 バイト素材欄) は `0xBF9D4C` が要求の IV 欄を複写し、IVDR 経路ではエンジン演算の宛先になる。**+0x8B0 と +0x8B8 の書き手は未同定**で、ストリームオープン/設定経路が次の入口になる (§5)。
- IVDR ヘルパ `0xBFA258` / AACS ヘルパ `0xBF9D4C` を実読した (§6)。IVDR では、素材の変換が FW コードではなく **FW がコマンドスロット経由で駆動するエンジン演算** で行われる実例を確認した。完了系ハンドラ 3 本 (`0xC43658` / `0xC464B8` / `0xC46F68`) も実読し、いずれも鍵・スロットに関与しない (§7)。

## 1. 手法と素材

- 手法は第9段の M1〜M6 ([docs/22](22_xcode_fw_drm_phase9.md) §1.2) を踏襲。本段では消費側 census のために次を併用した:
  - スカラ走査 (ScalarScan10): 解析済み命令の全オペランドと命令からの参照を対象に、指定値 (オフセット・アドレス) の出現を全数える。両イメージ (第2 FW = プロジェクト ghp12、主 FW = ghp12m) で実施。
  - バイナリ全域のリテラル走査: 対象アドレスの 32 ビット LE 値がバイナリ内のどこ (コード・データ・リテラルプール) にも現れないかをバイト列で確認。
  - デコンパイル水準の確認: スカラ走査には分割アドレッシング (例: 基底 +0x7FC に対して +0xB4 で +0x8B0 に届く形) が現れない盲点があるため、主要関数についてはデコンパイル/リスティングでオフセットを個別に確認した。盲点の実例は §3.2 と §4.2 に明記する。
- 主 FW のプロジェクトは関数境界の分断が多く (第9段の noreturn 誤判定と同種の原因)、一部関数はデコンパイルが崩れる。その場合はリスティングと呼出し側の同型性で補い、確認できた範囲を各節に明記する。
- 作業素材は開発側の作業領域 `2026-11-13-fw-drm/phase12/` (§11)。第2 FW のバイナリの SHA-256 は docs/16 記載のものと同一であることを本段開始時に再照合した。

## 2. 入口 1: 投入先の追跡

### 2.1 `0xC5C344` — 通信オブジェクトの構築と投入

引数は (handle, 記述子基底, コールバック)。処理:

1. プール `[0xAFEB68]` から通信オブジェクトを確保する (失敗時はカウンタ `[0xD8E8BC]` を増やして 2 を返す)。
2. 記述子チェーンを走査検証する。エントリ語 [e+8]|[e+0xC] が両方 0 なら致命的エラー (`0xC435C4 (0xEFEF4444, …)` + 停止)。[e+0x10] の bit31 が終端、bit 0x80000 が 0x30 形式 (前進量 0x30、それ以外は 0x20)。走査上限は基底 +0x800。
3. `[基底 + 0x854]` へ自己コア索引 (`0xC8B5E0` の戻り) を書く (投入者コアの記録。§2.3 で使われる)。
4. 通信オブジェクトへ詰める: **[obj+0x0C] = 0x100 (FunctionNumber)**、[obj+0x10] = (基底の bit31 が立っていれば 2、なければ 0)、[obj+0x14] = −1、**[obj+0x18] = handle**、**[obj+0x24] = 基底 & 0x7FFFFFFF**、[obj+0x2C] = コールバック、[obj+0x28..0x3C] = 0。
5. スピンフラグ `[0xAFEB08]` の下で `0xC5B898 ([0xAFF938], obj)` を呼ぶ。戻りが非 0 (先頭挿入) なら `0xC6FFF4 ()` で即時実行開始、0 ならカウンタ `[0xD8E6E4]` を増やして待機する (実行中チェーンの完了時に §2.4 経由で起動される)。

呼出し元は 22 件ある汎用の記述子投入経路で、SCRAMBLER ハンドラ (2 件)、IVDR ヘルパ `0xBFA258`、`0xC464B8` 等が含まれる。

> **docs/25 §3.6.4 の訂正**: 同節は「`[obj+0x24] = handle & 0x7FFFFFFF`」と書いていたが、実読では **[obj+0x24] は記述子基底 & 0x7FFFFFFF であり、handle は [obj+0x18]** である。あわせて [obj+0x10] (基底 bit31 由来の 0/2) と [obj+0x14] = −1 の初期化も本段で確定した。

### 2.2 `0xC5B898` — チャネルキューへの登録

チャネルオブジェクト `[0xAFF938]` への連結リスト挿入。obj[3] へ状態 (0x101/0x102) を、obj[2] へチャネルを、obj[5] へチャネルのスロット索引を書き、チャネル側のビットマスク (1 << 索引) を立てて索引を前進させる。先頭挿入に成功すれば obj を返し、それ以外は 0 を返す (チャネル [4] != 0 の分岐では obj[3] = 0x100 としカウンタ `[0xDA3C1C]` を増やす)。引数 NULL は致命的停止。

### 2.3 `0xC6FFF4` — 実行開始

対象はチャネル先頭のオブジェクトで、次を行う:

1. 記述子チェーンを自ら走査検証する (エントリ形式のステートマシン。0x30 形式については pitch/line 欄 [10]/[11] からチャンク数を計算する)。
2. 先頭エントリが 0x30 形式なら、チェーン末尾へ終端エントリを追加する (src = dst = セル `0xD8E6F0`、cmd = (先頭 cmd & 0xB0000000) | 0x3000004) してセルを前進させる。
3. **[B+0xC58] = 2、[B+0xC5C] |= 2** を書く (B = `[0xAFE004]`)。
4. スピンフラグ `[0xAFEB5C]` の下で、投入者コア索引 ([基底+0x854]) を読み、コア別表 (`0xAFEA68 + idx*0x18`) のオフセット語/マスク語を使い、共有制御語の投入者ビットを立て、他コア (コア 2 と 5 を除く) の同ビットを落とす。
5. [handle+0x20] == 2 かつ [handle+0x24] != 2 なら `0xBF5DF8 (基底)` を追加で呼ぶ。
6. **記述子チェーン基底を [B+0xC04] へ書き**、カウンタ `[0xD8E6E8]` を増やす。

すなわち実行の開始は「共有域レジスタへのチェーンポインタ書込み + 開始ビット」で行われ、パケットを他プロセッサへ送る形ではない。

### 2.4 `0xC7488C` — 完了処理と次オブジェクトの起動

チャネル 6 の殻 `0xC75294` から呼ばれる完了処理 (第11段 §2.2 の再読で確定):

- コア別カウンタを数える。[B+0xC58] の bit0 が立っていればカウンタのみ。
- bit1 が立っていれば、まず **[B+0xC34] の bit1 (エンジン busy) が落ちるまでスピン**する。次に obj = `[[0xAFF938]+0x1C]` について、[obj+0x10] の bit0 がクリアで [obj+0x2C] != 0 なら、**登録コールバック [obj+0x2C] を (0, [obj+0x24]) で呼ぶ** ([obj+0x10] の bit1 が立っている = residue の場合は第2引数に 0x80000000 を OR する)。
- `0xC5A2B4 ([0xAFF938], obj)` でチャネルスロットを前進させ、**戻りが非 0 なら `0xC6FFF4 ()` で次オブジェクトを実行開始**する。`0xC69028 (基底, 0x860)` の後処理の後、通信オブジェクトをプール `[0xAFEB68]` へ返し、コールバックの戻りが 0 で非 residue なら作業オブジェクトもプール `[0xAFF93C]` へ返す。

### 2.5 `0xC4AD58` — 完了コールバックの実読

SCRAMBLER 系の投入で登録される完了コールバック。全行実読した:

1. カウンタ `[0xD8FEC8]` を増やす。handle の復元: 非 residue は [基底+0x830] (作業オブジェクトの stream_handle 欄)、residue は *[基底−0x10] (residue オブジェクトヘッダの stream_handle) で、後者はログ呼出し `0xB9A894` (書式データ `0xCE1870`) を伴う。
2. スピンフラグ `[0xAFEB10]` の下で **[handle+0x48] の bit3 を落とす** (投入時に立てた in-flight ビット)。
3. **TDES 検証列**: ステージ済み scramble_mode ([handle+0x810]) が TDES 系モード {14, 15, 16, 17, 19, 22, 23, 24, 25, 27} (TDES のうち 18 のみ除外) の場合、カウンタ `[0xD8FECC]` を増やし、スピンフラグ `[0xAFFADC]` の下で共有コマンドスロット `[B+0xC80]` 経由のエンジン演算を 4 回行う。各演算の欄は +0xC80 = src `0xD8E574`、+0xC84 = 0、+0xC88 = dst `0xD8E594`、+0xC8C = 0、+0xC90 = 制御値、+0xC94 = 鍵ワード、+0xCD0 = 0 で、演算列は (制御 0x3000010, 鍵 0)、(0x3130010, 0x80000000)、(再試行: 0x3100008, 0x80000000)、(0x3130010, 0x80000000)。各演算は **[B+0xC34] の bit2 が落ちるまでポーリング**する。演算 1–2 の後に [0xD8E584] と [0xD8E594] の 16 ワードを比較し、不一致ならカウンタ `[0xD8FED0]` を増やして再試行列を実行し、なお不一致なら致命的エラー記録 + 停止 (`0xB04900`) する。
   - バッファ `0xD8E574` / `0xD8E594` への参照は、走査 (§3) の範囲で本関数内のみであり、イメージ内では BSS (ゼロ) である。**この検証列は実際の鍵素材ではなく固定 (ゼロ) データに対するエンジンの自己検証であり、完了経路がスロット内容を検査することは無い**。
4. 末尾 (全完了共通): **FN 0x26 (38) の完了パケット**を `0xBF6D7C (0x26)` で組み (失敗時はカウンタ `[0xD8FED4]` を増やして 1 を返す)、[handle+0x18]、[handle+0x1C] とステージ済み要求欄 [handle+0x7FC..0x818] を Input へ複写し、スピンフラグ `[0xAFEB10]` の下で [handle+0x48] |= 0x20000 とし、`0xC5C6B4 (handle, 0x26, pkt, 0xC4B458, 1)` で送信する (非 0 が返る間リトライ)。カウンタ `[0xD8FED8]` を増やす。

## 3. 入口 2: スロット参照の消費側 census

### 3.1 第2 FW

スカラ走査 (対象: 解析済み命令。ターゲット 0x1824 / 0x1828 / 0x182C) の出現は **5 件のみ**で、全て投入ヘルパの内部だった:

- `0xBCE950`: `add r2, r2, 0x1824`、`ld r21, [r8, 0x182C]`
- `0xBCEBD0`: `ld r16, [r7, 0x182C]`
- `0xBCED1C`: `add r0, r0, 0x1824`、`ld r16, [r7, 0x182C]`

データワード (+0x1824/+0x1828) を読む命令は存在せず、出現する読みは全て index ワード (+0x182C) のハンドシェイク確認である。0x1800 の出現 8 件は全て無関係だった (サイズ比較・マスク・加算)。スピンフラグ `[0xAFFADC]` への参照は 25 件・10 関数 (投入ヘルパ 3 本のほか `0xBF894C`、`0xBFA258`、`0xC1475C`、`0xC43E38`、`0xC443BC`、`0xC4AD58`、`0xC8A95C`) で、共有窓一般のロックでありスロット専用ではない。

状態・制御側の走査 (ターゲット 0xC34 / 0xC04 / 0xC58 / 0xC5C / 0xC80、合計 17 件):

- **[B+0xC34] (状態語) の出現 11 件は全て `ld`** (`0xBF894C`、`0xBFA258`、`0xC1475C`、`0xC43E38`、`0xC443BC`、`0xC4AD58`、`0xC7488C`)。実読した各関数でもポーリング読みのみであり、**[B+0xC34] へ書く FW コードは解析範囲に存在しない** — busy ビットの書き手はエンジン側である。
- [B+0xC58] は `0xC6FFF4` (書込み) と `0xC7488C` (読み) のみ。[B+0xC80] は `0xC4AD58` のほか `0xBFA258` がデコンパイル水準で使う。
- [B+0xC04] への書込み (§2.3) は分割アドレッシングのためスカラ走査には現れなかった。走査の盲点の実例として明記する (だからこそ §3.5 の判定は走査単独ではなく実読との組合せに基づく)。

### 3.2 主 FW

スカラ走査 (ターゲット 0x1824 / 0x1828 / 0x182C) の出現は **0 件**。一方、共有窓基底 `0xAFE000` の即値ロードは多数あり (スカラ出現 484 件)、主 FW でも共有窓へのアクセス自体は広く行われる。基底セル `[0xAFE004]` の直接ロードは 1 件 (`0x16F640`、関数 `0x16F5D8`) のみで、実読すると読むのは `[B+0x6130]` (共有の時刻/カウンタ。第2 FW の `0xC01B18` も [B+0x6130]/[B+0x6134] を読む) であり、スロット窓とは無関係だった。

### 3.3 絶対アドレスのリテラル走査

スロット窓の絶対アドレス 0xAFF828 / 0xAFF82C / 0xAFF830、チェーンポインタ 0xAFEC08、状態語 0xAFEC38、[B+0xC58] の 0xAFEC5C、コマンドスロット 0xAFEC84、基底セル 0xAFE004、TDES 検証バッファ 0xD8E574 / 0xD8E594 の各 32 ビット LE 値は、**主 FW・第2 FW 両バイナリの全域 (コード・データ・リテラルプールを含む) に 1 件も存在しない**。両イメージとも共有窓へは基底セル `[0xAFE004]` の値 (基底ポインタ) 経由でのみアクセスする。

### 3.4 TDES 検証バッファの参照範囲

`0xD8E574` / `0xD8E594` への参照 (スカラ + 参照走査) は第2 FW の全域で `0xC4AD58` の内部のみ (13 件) だった。他にこのバッファへ書く関数は解析範囲に無い (§2.5 の自己検証という解釈の根拠)。

### 3.5 判定 (消費側の同定)

- **事実**: 解析済み命令の範囲 (両イメージ) で、スロットのデータワードを読む FW コードは存在しない。主要な到達経路 (ハンドラ・両ヘルパ・投入・完了処理・コールバック) についてはデコンパイル/リスティング水準でも個別に確認し、読み手は無かった。状態ビット [B+0xC34] の書き手も FW 内にいない。FW と消費側の接点は、投入時の index ワード bit31 ハンドシェイク (投入側が立つのを 5 回観測するまでスピンする受領確認) のみである。
- **判定**: スロットの消費者は FW コードではなく、**記述子チェーンと共有域レジスタ ([B+0xC04] のチェーンポインタ、[B+0xC58]/[B+0xC5C] の開始ビット、[B+0xC34] の状態ビット) を介してエンジン側 (HW) が直接参照する**構造である。
- **範囲の限定**: 未解析の孤児コード (主 FW の約 23% 等) と分割アドレッシング経由のアクセスはスカラ走査では拾えないため、「読み手が居ない」は上記の確認範囲での結論である。エンジン内部の実装そのものを観測したわけではなく、判定は「FW が書くのはチェーンポインタと開始ビットまでで、それ以降の進行と状態ビットの書込みは FW の外で起きる」という構造的事実からの帰結である。

## 4. 主 FW の並行実装 (本段の新規発見)

### 4.1 ハンドラ `0x22F9E0` の同定

+0x8B0 の書き手を主 FW 側で探す過程で、主 FW 内に SCRAMBLER ハンドラの並行実装 `0x22F9E0` を同定した。全行実読した `0xBF894C` と構造同型である:

- 入口の振り分け: 要求欄 [7] (scramble_mode) が 9/10 なら `0x23237C` (IVDR 相当)、12/13 なら `0x230E34` (AACS 相当) へ委譲し、それ以外は自ら処理する。
- 要求のステージング: handle (= 要求先頭語) の +0x7F4 へ要求を 0xBC バイト複写する (`0x2ACFB0`)。
- 検証: [8] < 0x800 の検査、モード/フラグ検査。詳細エラーコードはセル `0x690CEC` へ書き、戻り値は 4 / 1 等 (`0xBF894C` と同じコード体系)。
- 作業オブジェクトは `0x22B7D8` が確保し、+0x830 へ handle を置く。residue 系モードでは "TSDMA" と名付けたチャネルオブジェクトを別途構築する。
- 鍵ワードの packing は同一: (CW2 選択値 << 24) | (CW 選択バイト << 16) | (IV 由来バイト << 8) | IV 選択バイト。SF bit1 セット時の IV 由来バイトは大域セル `0x6ADEF0` から取る (第2 FW 側の `[0xDA3EB4]` に対応)。
- 記述子は 0x20 / 0x30 形式で構築され、終端エントリの cmd は 0xA3000004 (src = dst = セル `0x69731C`)。
- 投入: スピンフラグ `[0xAFEB10]` の下で [handle+0x48] の bit3 を立て、`0x2EB7B4 (handle, 記述子基底, 0x2CAF24)` を呼ぶ (`0xC5C344` と同型の引数で、完了コールバックは主 FW 側の `0x2CAF24`)。

相違点は、エラーカウンタ/コードの置き場、ヘルパのアドレス、residue 経路の TSDMA 構築など実装詳細に留まる。同一ソースの別ビルドか書き直しかは未確定。

### 4.2 AS_INDEX 極性の確定と docs/25 §3.4 の訂正

両実装で、CW/IV 選択の極性が一致することを確認した:

- 第2 FW `0xBF894C` (命令水準): SF 語は要求 +0x18。`0xBF8CC4` の `bbit0 r7, 0x6` は bit6 がクリアのとき `[handle+0x8B8]` の読みへ分岐し、セットのときは `[req+0x4C]` (IV_seed[0]) を読む。CW 側も `0xBF8CE8` の `bbit0 r6, 0x5` で同型で、クリアのとき `[handle+0x8B0]` / `[handle+0x8B4]`、セットのとき要求バイト ([req+0x34]、residue 系は CW2 も [req+0x6C]、非 residue の CW2 は [handle+0x8B4]) を読む。なお +0x8B0 の読みは handle+0x7FC を基底に +0xB4 で行われており、スカラ走査に 0x8B0 として現れない形だった (盲点の実例)。
- 主 FW `0x22F9E0` (デコンパイル): bit6 クリア → `[handle+0x8B8]`、セット → (byte) req[0x13]。bit5 クリア → `[handle+0x8B0]` と `[handle+0x8B4]`、セット → 要求バイト (residue 系は CW2 も req[0x1B]、非 residue の CW2 は [handle+0x8B4])。

すなわち **AS_INDEX ビットがセットのとき要求内のバイト欄 (それ自体がスロット番号を兼ねる) を使い、クリアのとき状態ブロックの解決済み語を使う**。docs/25 §3.4 の記述 (クリアなら要求欄、セットなら状態ブロック) は逆であり、本段で訂正する。

### 4.3 主 FW 側の投入ヘルパ

`0x22F9E0` からは、スロット投入が `0x200E68 (index, buf)` と `0x203274 (index, ptrA, ptrB)` で呼ばれ、第2 FW 側の `0xBCE950` / `0xBCED1C` と同じ役割分担である。index > 0x7F でカウンタを増やして戻るガードも同型である。ただし主 FW のプロジェクトでは両関数の本体が関数境界の分断でデコンパイルが崩れており (入口のガード部のみ読めた)、**共有窓への書込みそのものの命令水準の確認は本段では未達**である。同定は呼出し側の同型性に基づくもので、この限定を明記する。

### 4.4 未実読の部分

主 FW 側の投入 `0x2EB7B4` と完了コールバック `0x2CAF24` は同定のみで未実読。`0x22F9E0` の呼出し元 (主 FW 側ディスパッチ) も未同定である (関数ポインタのリテラルはバイナリ内に存在せず、登録テーブル経由とみられる)。

### 4.5 並行実装の意味 (解釈)

SCRAMBLER の配送先は proc6 とされてきた (docs/12) が、主 FW (proc0 側が実行するイメージ) にも同型の完全な実装が存在する。どちらが実機で使われるか、片方が使われないコードかは静的には決められない。少なくとも「SCRAMBLER の処理実体は第2 FW だけにある」という前提は成り立たない。

## 5. 入口 4: 状態ブロック +0x8B0 台の書き手

### 5.1 読み手の全数と、候補の切り分け

本段までの実読で +0x8B0 / +0x8B4 / +0x8B8 を読むのは `0xBF894C` (選択)、`0xBFA258` (+0x8B0 を投入 index に、+0x8B8 を IV スロット値に、+0x8BC を素材に)、`0xBF9D4C` (+0x8B0 / +0x8B8)、主 FW `0x22F9E0` (選択) の 4 関数である。

候補だった `0xC01B18` (登録ハンドラ `0xC82410` の転送先、スカラ走査で +0x7F4 の出現があった) は全行実読の結果、+0x7F4 への書込みは定数 (0xA8C00 / 0x3D090) を自オブジェクトの欄へ書くもので、読むのは自オブジェクトの +0xBC / +0xC0 であり、**+0x8B0 台への書込みは無い** (デコンパイルに該当オフセットの出現なし)。スカラ走査の残りの出現 (`0xB02300` の `add r0, r14, 0x8B8`、`0xB24F9C` の `add_s r13, r13, 0x8B0`) は実読の結果、別オブジェクト (補助レジスタ初期化、レジスタ表構築) で無関係と分類した。主 FW 側のスカラ出現は 0x8B0 / 0x8B8 が 0 件、0x8B4 が 2 件で、いずれも無関係だった (`0x26336C` の add は AKE 系文脈オブジェクトの欄、`0x169DC8` のストアは値としての 0x8B4)。

### 5.2 同定できた書き手

- **+0x8B4**: AACS ヘルパ `0xBF9D4C` が成功経路で `[handle+0x8B0]` を `[handle+0x8B4]` へ複写する (CW の解決済みスロットを CW2 側へ流用する)。
- **+0x8BC (16 バイトの素材欄)**: `0xBF9D4C` が SF bit3 セット時に要求の IV 欄 (req+0x4C、16 バイト) を複写する。IVDR 経路ではエンジン演算 (制御 0x3130010) の宛先がこの欄であり、演算結果がここへ書かれる (§6.1)。
- **+0x8EC / +0x8F0**: `0xBF9D4C` がステージング時に 0 クリアする。

### 5.3 未同定の書き手 (+0x8B0 / +0x8B8)

+0x8B0 と +0x8B8 の書き手は、ハンドラ・両ヘルパ・完了系・転送系・登録ハンドラの実読範囲と、両イメージの census (§3 の範囲) のいずれにも現れなかった。状態ブロックの確保・初期化はストリームのオープン/設定経路 (docs/13・14 の drmctrl_open / OPEN_STREAM 系。open 本体が要求の鍵指定ペア +0x38/+0x40 を読むことは docs/15 で確定) が担うとみるのが自然であり (解釈)、次段の入口はその経路で +0x8B0 / +0x8B8 への書込みを確認することである。

## 6. 入口 5 (前半): IVDR / AACS ヘルパの実読

### 6.1 IVDR ヘルパ `0xBFA258` (モード 9/10)

- 静的表 `0xCD4EF0` の 16 バイトを初期素材 (ローカルバッファ) とする。[handle+0x8B8] を IV スロット値として読み、要求を handle+0x7F4 へステージングする。
- SF bit1 がクリアなら IV スロット値に 0x20 を OR する。セットなら [handle+0x8BC] の 16 バイトを `0xBCEBD0` でそのスロットへ投入し、0x20 を落とす。
- SF bit3 がセットの場合: 要求の CW 欄を `0xBCE950 ([handle+0x8B0], …)` へ投入したうえで、コマンドスロット `[B+0xC80]` 経由のエンジン演算 (src = req+0x5C、dst = handle+0x8BC、制御 = 0x3130010、鍵ワード = IV スロット値) を駆動し ([B+0xC34] bit2 のポーリング待ち)、結果が書かれた [handle+0x8BC] を再び `0xBCEBD0` で IV スロットへ投入し、さらに要求の CW を `0xBCE950` で再投入する。
- SF bit2 がセットの場合も、要求の CW を `0xBCE950 ([handle+0x8B0], …)` へ投入する。
- 作業オブジェクト +0x830 へ handle、+0x840 へ鍵ワード ([handle+0x8B0] | IV スロット値 << 24 | 0x80) を置き、記述子 (cmd 基底 0x1030000、モード 9 で 0x1130000、10 で 0x1230000) を `0xBF6794` / `0xBE0118` で構築し、スピンフラグ `[0xAFEB10]` の下で [handle+0x48] bit3 を立てて `0xC5C344` で投入する。

**素材に対する変換は FW コードではなく、FW がコマンドスロット経由で駆動するエンジン演算で行われる**。本段で確認した唯一の「変換」の実例であり、対象は鍵 (CW) そのものではなく IVDR の IV 素材である。

### 6.2 AACS ヘルパ `0xBF9D4C` (モード 12/13)

- 静的表 `0xCD49CC` の 16 バイトを初期素材とする。前提条件 (req[8] == 1、req[9] != 0、req[10] == 0、req[0xB] に対する検証 `0xB8C288`) を満たす場合のみ処理し、外れれば詳細コードを残して戻る。
- 要求をステージングし、+0x8EC / +0x8F0 を 0 クリアする。SF bit1 がクリアならエラー (詳細コード 2)。
- 素材は、SF bit3 がセットなら要求の IV 欄 (16 バイト。あわせて [handle+0x8BC] へ保存する)、クリアなら [handle+0x8BC] を使い、`0xBCEBD0 ([handle+0x8B8], …)` で IV スロットへ投入する。
- [handle+0x8F8] のサブオブジェクト (AACS 処理系) が有効で、その状態欄 (+0x4B4) の許可ビットが立っていれば、メソッド (モード 12 は +0x4CC、13 は +0x4C8) を (subobj, req[0x22], [handle+0x8B0]) で呼び、成功時に §5.2 の +0x8B4 複写へ進む。
- SF bit2 がセットなら要求の CW を `0xBCE950 ([handle+0x8B0], …)` へ投入する。
- デコンパイルはモード 12/13 の分岐内で未実装命令に当たって後半が切断されており、記述子構築・投入の詳細は本段では未読である (範囲を明記する)。

## 7. 入口 5 (後半): 完了系ハンドラ

- `0xC43658` はパケット返却の低水準プリミティブだった。自コアの通信記述子 (`0xAFE09C + idx*0xF4`) からメールボックスオフセットの 2 対 (+0x9C/+0xA8 系と +0xC8/+0xD4 系) を読み、mode 1/2 に応じて共有域 [B + offset] へ引数のペアを書き、コア別カウンタ `[0xD8F1D0]` を増やす。鍵・スロットの関与は無い。
- `0xC464B8` (FN 13) はストリーム制御/状態イベントのハンドラだった。パケット欄 [2] のイベント種別で分岐し、値 ([7]) を大きなストリーム状態オブジェクトの各欄 (+0x595C、+0x59FC、+0x5A4C、+0x5A9C 等) へ記録する。実読範囲 (冒頭部と分岐構造) に鍵・スロット操作は無い。
- `0xC46F68` (FN 31) は音声受信状態のハンドラだった ("DummyRecv (nextrel) audidx" のデバッグ文字列を含む)。ストリームオブジェクト +0x71xx 台の受信リングをスピンフラグ `[0xAFEB08]` の下で処理する。実読範囲 (冒頭部) に鍵・スロット操作は無い。
- `0xC5A2B4` は §2.4 の通り、完了処理から使われるチャネルスロット前進関数で、その戻りが次オブジェクトの起動条件になる。

## 8. 判定: 消費側での変換の有無と、録画側への含意

### 8.1 事実の整理

1. スロットへ投入されるのは CW バイト列そのものである (docs/25)。
2. 記述子に載るのはスロット番号のみであり、鍵バイト列は載らない (docs/25、本段 §4 でも主 FW 側で同型を確認)。
3. チェーンの実行開始は、FW が共有域レジスタへチェーンポインタと開始ビットを書くことで行われ、完了は状態ビットのポーリングで観測される (§2)。
4. スロットのデータワードを読む FW コードは、両イメージの確認範囲に無い (§3)。
5. 完了経路はスロット内容を検査しない (§2.5 の TDES 検証列は固定データへの自己検証)。

### 8.2 判定

**消費側でも FW コードによる変換は存在しない** (変換する主体 = 読み手自体が FW 内にいない)。docs/02 §10 のモデルは本段で次の形に具体化された: 実効鍵の「解決」 = エンジンが記述子のスロット番号で鍵ストアを引く行為そのものであり、FW 側 (ホスト供給 CW の逐語投入 → スロット参照) に変換の余地は残っていない。

未確定として残る部分 (不在の断定はしない):

- エンジン内部でスロット値がそのまま鍵として使われるか、内部で更に変換 (鍵スケジュール等) が行われるかは、FW イメージからは原理的に観測できない。これは FW 静的解析の範囲外であり、実験系 (オラクル方式) 側の問いになる。
- ただし傍証として、IVDR の実例 (§6.1) が示す通り、この FW では「素材の変換が必要な場合は FW がコマンドスロット経由でエンジン演算を駆動し、結果をスロットへ再投入する」という設計が採られている。CW についてはそのような演算駆動がハンドラ・両ヘルパの実読範囲に存在しない。

### 8.3 録画側 (SECUREDTS / CW トークン) への含意

- **事実**: SCRAMBLER (GENERIC スクランブル) 経路については、投入側 (docs/25) と消費側 (本段) の双方が閉じ、FW 側変換なし・エンジンのスロット参照という形が確定した。録画保存の SECUREDTS は別経路 (docs/14 §6 で一部実読) であり、本段の判定はそちらへは及ばない。
- **解釈**: 録画時の CW トークン (ブート毎にほぼ固定で、セグメント毎に 1 バイトが変わる構造化トークン。docs/02 §10) が SCRAMBLER の control_words に対応するなら、その「解決」もスロット参照の形を取り、トークン → 実効鍵の変換が存在するとすればエンジン内部か SECUREDTS 側の経路に限られる。FW 静的解析で追える範囲は、残る SECUREDTS 経路と +0x8B0/+0x8B8 の書き手 (オープン経路) に移った。

## 9. docs/25 への訂正 (2 件)

1. **§3.6.4**: 通信オブジェクトの [obj+0x24] は handle ではなく記述子基底 & 0x7FFFFFFF。handle は [obj+0x18] (§2.1)。
2. **§3.4**: AS_INDEX の極性が逆。セットのとき要求内のバイト欄、クリアのとき状態ブロックの解決済み語を使う (§4.2)。両実装 (第2 FW / 主 FW) の命令水準・デコンパイルで一致を確認した。

いずれの訂正も、docs/25 の (a)/(b) 判定 (SCRAMBLER 経路は (b)) には影響しない。
