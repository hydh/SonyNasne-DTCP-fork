# XCode ファームウェア DRM モジュール解析 第17段

2026-11-15。第16段で残った未確定点 — **KO (鍵オブジェクト) の素材欄の書き手と、SECUREDTS の実効鍵の最終的な出所** — に重点を絞る段。第16段までに DRMCTRL の下流 (束縛 `0x261B7C`、暗号セットアップ `0x15490C` のコマンドパケット構築、ハンドラ表 4 エントリ) はほぼ判明したが、KO の素材欄 (+0x94/+0xA4/+0x154、+0x1E0/+0x1E4、+0x38C/+0x390) と能力フラグ (+0x10)・状態 (+0x0C) の書き手は、実読した全関数の範囲に存在しなかった。AKE 素材はセッションオブジェクト側に在り、KO への橋渡しは読み範囲の外にある。本段はその橋渡しを追う。

手法は第9段の M1–M6 を踏襲 (Ghidra 実読を主とし、静的データはイメージのバイト列から直接読んで照合)。素材は開発側作業領域 `2026-11-13-fw-drm/phase17/` (Ghidra プロジェクト `ghp17` = 第2 FW、`ghp17m` = 主 FW、いずれも phase16 プロジェクトの複製)。アドレス表記は各イメージのロードベース基準 (主 FW = 0、第2 FW = 0xB00000) で、ファイルオフセットと一致する。DRMCTRL 系ライブラリのデータ参照は +0x100000 ビューであり、表・文字列・リストの実内容は「コード上の参照アドレス − 0x100000」のファイルオフセットにある (第16段で実測確認済み)。**本段では、このビューがコードについても成り立つ箇所があることを新たに確認した (§4.1.4)。**

用語は第16段を引き継ぐ: **KO (鍵オブジェクト)** = DRMCTRL 文脈 (表 `0x69735C` のエントリが指す構造) の +0x148 にインラインで置かれる 0x3F8 バイトの作業域。**セッションオブジェクト** = KO +0x48 のポインタが指す大きなオブジェクトで、AKE 実体 (gen_kauth / setexchgkey) が操作するセッション文脈 (+0x10C20 起点) を内包する。

## 2. 課題と入口

### 入口 (1) `uist_drmctrl` タスク本体の入口同定

第16段の残件 1 の本線。文脈ごとに生成される `uist_drmctrl` タスクが KO 素材の書き手の残る候補であるが、タスク生成の第1引数は RAM のタスク制御ブロックであり、第16段では入口を同定できなかった。本段では:

- 名前文字列 "uist_drmctrl" の参照を両アドレスビュー (ベース 0 / +0x100000) で追い、名前引き機構 (「操作名+引数」の名前記述子を名前引きヘルパに渡す方式が本 FW に実在する) 経由の登録・解決があれば、その経路から入口を確定する。
- タスク生成サービス `0xB082E8` (ID 引き、第10段で同定) の DRMCTRL 文脈での使われ方も確認する。

### 入口 (2) KO 素材欄の書き手 (対象を絞った追跡)

変位 census の全数否定は方法限界が実測済みのため使わず、対象を絞った実読で追う:

- KO の確保・初期化サイト (drmctrl_open 内外) を起点に、KO ポインタが格納される全ての場所と、KO 基底を参照する関数を列挙し、各関数に素材欄 (+0x94/+0xA4/+0x154、+0x1E0/+0x1E4、+0x38C/+0x390) や能力フラグ (+0x10)・状態 (+0x0C) への書込みがあるかを実読で判定する。
- AKE 側からの橋渡し: DRMCTRL 文脈が所有する AKE セッション文脈と KO の間で素材を複写する処理があるか。gen_kauth / setexchgkey の出力の格納先を追い、KO 欄へ届くか判定する。
- 中核計算 `0x1FED1C` (第6・7段: gen_kauth が文脈フィールドを入力して 12 バイトの生成値を出す) の入力文脈フィールドの初期化側 (起源) も、KO へ繋がる範囲で追う。

### 入口 (3) セッションオブジェクト +0x4000 のパケット宛先

第16段の残件 3。暗号セットアップ `0x15490C` がセッションオブジェクト +0x4000 に組む 0x28 バイトのコマンドパケット (ヘッダ 02 09 01 …、KO +0x154 の 16 バイトの平文複写を含む) を読む側を同定する。`uist_drmctrl` タスク自身か、エンジン-facing の別タスクか。入口 (1) と交差する可能性が高い。

### 入口 (4) 余力項目

- DRMCTRL 文脈スロット欄 +0x49C/+0x4B4 の消費者 (第16段の残件 2 の一部。+0x4B8 の消費者は `0x20D918` と確認済み)。
- ハンドラを持たないモード (0x100000/0x200000) の close 側スロット解放と、`0x2629F4` の解放側呼出し元。

## 4. 調査記録

### 4.1 入口 (1): `uist_drmctrl` タスク本体の同定

#### 4.1.1 名前文字列とその唯一の参照

文字列 "uist_drmctrl" は主 FW 内に 1 回だけ存在し、ファイルオフセット 0x2DEC54 (= コード参照上の +0x100000 ビュー表記 0x3DEC54) にある。drmctrl_open のログ文字列群の中である (近傍: ファイル 0x2DEBD8 に "Error - drmctrl_open task_id"、0x2DEC64 に "T%05d:drmctrl_open pso:%x,cmd:%x <--%s")。

参照 census (Ghidra 参照マネージャ、両ビュー): ビュー表記 0x3DEC54 への参照は **1 件のみ**で、drmctrl_open (`0x261520`) 内の 0x261A96 から、引数として渡される形 (PARAM) の参照である。ベースビュー表記 0x2DEC54 への参照は 0 件。名前引き機構経由の登録・解決は介在せず、文字列はタスク生成呼出しの名前引数として直接渡されていた。

#### 4.1.2 drmctrl_open 内のタスク生成呼出し

drmctrl_open の実読 (デコンパイル + 逆アセンブル) で、モード別ハンドラ表 (ビュー表記 `0x3ED500`、実内容はファイル 0x2ED500) の走査と open ハンドラ呼出しの後に、次のタスク生成呼出しがあることを確認した (0x261A90–0x261ABC):

```
FUN_003B4ED0(r0 = 0x398CCC,        ; タスク本体の入口 (§4.1.3)
             r1 = 文脈ポインタ,     ; drmctrl_open の第1引数
             r2 = KO ポインタ,      ; drmctrl_open の r14
             r3 = KO ポインタ,      ; 同上
             r4 = 0x30,
             r5 = 0x800,
             r6 = ハンドラ表エントリ[4],  ; ハンドラ一致時は表から、不一致時は 0
             r7 = "uist_drmctrl",   ; ビュー表記 0x3DEC54
             スタック引数 = 0, 0)
```

- レジスタの同一性: drmctrl_open 内の r14 は KO ポインタである (そのストア先 +0x14/+0x18/+0x1C/+0x44/+0x48/+0x4C/+0x50/+0x54 が、デコンパイル上の文脈基準の書込み +0x15C/+0x160/+0x164/+0x18C/+0x190/+0x194/+0x198/+0x19C と一致する)。r16 は第1引数の DRMCTRL 文脈ポインタ (ハンドラは (文脈, KO) で呼ばれる、第16段 §4.2 の通り)。
- drmctrl_open がこの呼出しまでに KO へ格納する欄: +0x48 ← セッションオブジェクトポインタ、+0x4C ← 定数 0x18C00、+0x44 ← 文脈ポインタ、+0x50 ← 要求側構造 +0x14 の値、+0x54 ← 要求 +0xFC の値、+0x1C ← 第2引数 (open パケット)、+0x14/+0x18 ← 文脈 +400 から導かれる値。**素材欄 (+0x94/+0xA4/+0x154 等) と +0x10、+0x2C への格納はこの範囲に無い。**
- 戻り値が 0xFF と等しい場合は失敗路 (エラーセル `0x4ECD94` の増加、`0x4ECD98` へ 10 を格納して 1 を返す)。成功時は後処理 (再格納、`FUN_00297B54` の呼出し、ログ出力、`0x4ECD9C` の増加) を経て 0 を返す。
- ハンドラ表エントリ [4] (タスク引数欄) は静的 4 エントリ全てで 0 である (第16段)。したがって生成先を決める r6 は実質常に 0 である。

#### 4.1.3 タスク生成サービス `0x3B4ED0` の性格

`0x3B4ED0` は主 FW 内のプロセッサ間呼出し/タスク生成サービスである (線形スイープで 0x3B4ED0–0x3B5300 以降、少なくとも 0x3B5856 まで実読)。全引数レジスタをフレームへ退避した後、現プロセッサ識別子 (後述のゲッタ `0x3B8A64`) と r6 (宛先) を照合する:

- 宛先は {0, 1, 3, 4, 6} のいずれかでなければならず、それ以外と「宛先 = 自分」の場合は 0x3B5856 側 (ローカル実行路とみられる。本段では未実読) へ分岐する。
- 遠隔の場合は宛先に 0x10000 ビットを立てた形で通知機構 (`FUN_003B7E20`) を呼び、パケットを構築する: パケット先頭領域へ **保存した r0 (関数ポインタ)、r2、r3** の順に格納する。すなわち呼出し側の (入口, 引数1, 引数2) が宛先プロセッサへマーシャリングされる。
- 主 FW 内の呼出し元は 21 箇所 (drmctrl_open のほか `0x32FE54`、`0x34DC7C` 等)。

drmctrl_open の呼出しでは入口 = `0x398CCC`、引数1・引数2 ともに KO ポインタであり、宛先 = 0 である。第2 FW 側のタスク生成サービス `0xB082E8` (第10段) は第2 FW イメージ内のサービスであり、主 FW の DRMCTRL 経路には現れなかった (範囲: drmctrl_open の実読)。

#### 4.1.4 タスク本体 `0x398CCC` — 第16段の読みの訂正を含む

入口 `0x398CCC` への参照 census: drmctrl_open の 0x261A90 からの PARAM 参照 1 件のみ。

第16段はこの第1引数を「RAM 上のタスク制御ブロック (参照 `0x398CCC`、ファイルイメージ内はゼロ域)」と読んで入口を同定できなかった。本段でイメージのバイト列を直接照合した結果:

- ファイルオフセット **0x398CCC は確かに全ゼロ**である。しかし Ghidra プロジェクト上で `0x398CCC` にある命令列は、ファイルオフセット **0x298CCC** のバイト列と一致する (先頭: `f1c0` = push_s blink、`fc1cc8b6` = st.a fp,[sp,-4]、`0a230037` = mov fp,sp — 逆アセンブル結果とバイト単位で一致)。
- すなわちこのライブラリのコードも +0x100000 ビューのブロックに属し、実体は「参照アドレス − 0x100000」のファイルオフセットにある。第16段でハンドラ表 (ビュー 0x3ED500 → ファイル 0x2ED500) について確認したのと同じ構造であり、「ゼロ域」はファイルオフセットをビューアドレスと取り違えたことによる誤読だった。**第16段の当該記述を訂正する。**

本体の構造 (線形スイープ 0x398CCC–0x3992B0、全 427 命令を実読。Ghidra の関数体は後述の非復帰誤判定の影響で 2 ブロックに切断されたままのため、読みはスイープに基づく):

- **プロローグ (1 回のみ)**: 引数 (= KO ポインタ) を保持し、[KO+0x44] (= 所有する DRMCTRL 文脈) の +0x50 (文脈インデクス) で、基底 `0x6EC7A0` の表 (エントリ 0x30 バイト) へ自文脈を登録する: エントリ +0x00 ← 文脈ポインタ、+0x20 ← [KO+0x2C] (ストリーム文脈ポインタ)、+0x2C ← −1、他は 0。
- **メインループ (頭 0x398DAA、戻り辺 2 本)**: blink では戻らない。エラー出口は全て 0xDEADC0DE パニック記録 + 無限ループである。各反復で表エントリのカウンタ群を進め、チェックポイント記録 (後述) を挟みながら次の作業呼出しを行う (引数はいずれも KO ポインタを保持したレジスタ):
  - `0x26290C(KO+4, 2)` — 戻り値が非ゼロの場合にのみ次へ進む、受信/待機系のラッパ (本体は環境プリミティブへの尾部呼出し形で細部は未実読、§4.3.3)。
  - `0x2624E4(KO)` — コマンドディスパッチャ (§4.2.1)。
  - `0x260EF8(KO, [KO+0x2C])` — ストリーム文脈側の状態リセット系 (§4.3.3)。
  - `0x2EAA28([KO+0x2C]+0x8270, 0)` の戻り値が非ゼロなら `0x262C38([KO+0x2C]+0x825C, [戻り値+0x24])` — 遅延束縛 (§4.3.2)。
  - ストリーム文脈の +0x8268/+0x826C の検査を経て、経路により `0x262D94(KO+4, 1, 1)` と `0x3B762C()` を呼ぶ。
- 引数の同一性はレジスタの流れで確定する: タスクの引数は KO ポインタであり、[KO+0x44] = 文脈ポインタ (drmctrl_open が格納)、[KO+0x2C] = ストリーム文脈ポインタ (本タスクは +0x825C = 束縛 `0x261B7C` が KO ポインタを格納する欄そのもの、第15・16段、ほか +0x8268/+0x826C/+0x8270/+0x82A0 をこの基底で使う) はいずれも整合する。なお KO +0x2C 自体の書き手は drmctrl_open の格納範囲には無く、本段でも未同定である (§4.2.7)。

#### 4.1.5 付随する訂正: `0x3B8A64` は非復帰プリミティブではない

タスク本体や DRMCTRL 周辺の各所に現れる `0x3B8A64` は、第15・16段で「戻らないプリミティブ/タスク切替え相当の脱出」とされたものである。本段で本体を全行実読した:

```
0x3B8A64: lr r0,[0x4]        ; AUX レジスタ 4 を読む
          lsr_s r0,r0,0x8
          extb_s r0,r0
          j_s blink          ; r0 に値を返して通常復帰する
```

すなわちこれは **現プロセッサ/文脈の識別子 (AUX 4 のビット 8–15) を返すゲッタ**であり、呼出し側は戻り値を 0/1 や {0,1,3,4,6} と比較し、プロセッサ別表 (ストライド 0x30、基底 0x100608 / 0x100630 / 0x101C20) の添字に使う。呼出し前後の `mov rX,pcl` や表への pcl 格納は、活動/チェックポイントのタグ付けであり、尾部呼出しによる脱出ではない。Ghidra がこれを非復帰と誤判定したため、呼出しを含む関数 (タスク本体 `0x398CCC`、生成サービス `0x3B4ED0` 等) の関数体が途中で切断されていた — 第9段で第2 FW の OS プリミティブ `0xB04A28` に起きたのと同型の誤判定である。本段ではプロジェクト (ghp17m) 上で当該関数の非復帰フラグを解除したが、切断済み関数の体は自動では伸びなかったため、対象関数の読みは線形スイープで行った。**第15・16段の「戻らないプリミティブ」という記述は、本実読をもって訂正する。**

### 4.2 入口 (2): KO 素材欄の書き手

#### 4.2.1 コマンドディスパッチャ `0x2624E4`

タスクループから KO ポインタで呼ばれる、要求ごとの振り分けである。実読した処理:

- 時刻/登録系の前処理 (要求文脈 `*(KO+0x1C)` の +0x50 をキーとする `FUN_003B7E20` への登録、表 `0x6973CC` 周辺のタイムスタンプ処理) の後、**振り分け条件**を評価する: 要求側の語 `*(KO+0x1C) + 0xC0` が **KO +0x10 (能力/モード語) と等しい**場合に、その共通値でワーカーを選ぶ:
  - 0x20 → `0x1543C8`、0x200 → `0x16AE34`、0x10000 → `0x26FB7C`、0x20000 → `0x1666E4`、0x1000000 → `0x156C04`。
  - ワーカーへの引数は (要求文脈, KO, *(KO+0x14), *(KO+0x20), &応答ポインタ, &応答長)。*(KO+0x14) が指す構造の先頭語がコマンドコードである (§4.2.2)。
- 後処理: ワーカーの戻り値が 0 なら、フラグセル `_DAT_00AFEB6C == 1` の場合に `FUN_00261324` を呼び、応答長が非ゼロなら `FUN_00305B78(要求文脈, KO, 応答ポインタ)` で応答を送出する (§4.3.1)。エラー時はエラーカウンタ `0x4ECDB4` を増やし `FUN_00261324` をエラー引数で呼ぶ。最後に `FUN_00262D94(KO+4, 2, 0)` (通知系ラッパ) を呼んで戻る。

#### 4.2.2 能力 0x20 のワーカー `0x1543C8` とコマンド表

`0x1543C8` はコマンドコード (*(KO+0x14) が指す構造の先頭語) による副ディスパッチャである (ジャンプ表はファイル 0x15440C、オフセット符号化。デコンパイルで復元されたケース集合を採用)。呼出し元は `0x2624E4` の 1 箇所のみ:

| コマンド | ハンドラ | 応答コード |
|---|---|---|
| 0x11 | `0x1536B8` | 0x12 |
| 0x13 | `0x153C8C` | 0x14 |
| 0x15 | `0x153DB8` | 0x16 |
| 0x21 | `0x154A10` | 0x22 |
| 上記以外 (0x11–0x21 の範囲内) | 既定路: エラーカウンタ `0x4EB734` を増やして 1 を返す | — |

各ハンドラは (要求文脈, KO, コマンド構造, *(KO+0x20), &応答ポインタ, &応答長) で呼ばれ、セッションオブジェクト = *(KO+0x48) を基底に動作し、応答ポインタにはセッション +0x4000 が入る。

#### 4.2.3 コマンド 0x15 のハンドラ `0x153DB8` — 素材欄の書き手 (本段の中核)

コマンド内の長さ/オフセット欄 (コマンド +0x10 の BE32、+0x14〜+0x1F の各欄、+0x20 起点のオフセット) による範囲検査 (上限 0x400 / 0x4000) を通過した場合に、次を行う:

1. `FUN_001553E0(セッション+0x7B14, データ, 長さ)` でコマンド付随データをセッション側へ収める。
2. 応答はパケット構築子 `FUN_00154960(セッション+0x4000, 0x16, 0)` で組み、コマンドの一部バイトとコマンド +0x20 以降の複写を含む。**後述の生成値は応答には含まれない。**
3. 生成関数 `FUN_001A9278(出力バッファ, 4, 0)` で **16 バイトの値を得る** (§4.2.4)。
4. その 16 バイトを複写する: **セッション +0x4014 + (コマンド +0x10 の BE32 値)**、**KO +0x154**、**KO +0x164**。
5. 実行時グローバル素材 (アドレス `0x566768` から 16 バイト、§4.2.8) を局所へ取り込み、**KO +0x94 ← 生成値、KO +0xA4 ← グローバル素材、KO +0xD4 ← 生成値、KO +0xE4 ← グローバル素材** を格納する。

第16段で確定した欄配置とあわせると、+0x94/+0xA4 が素材欄、+0xD4/+0xE4/+0x164 が導出先欄であり、本ハンドラは導出先欄へも素材そのものを初期値として複写する (暗号セットアップ時の導出 `0x1544CC` は第16段)。すなわち **KO の素材欄の書き手は、ホスト側の open 経路ではなく、セッション確立コマンド 0x15 を処理するタスク側ハンドラだった**。

#### 4.2.4 生成関数 `0x1A9278` — 素材はエンジン側で生成される

`0x1A9278(出力, 個数=4, フラグ)` の本体 (線形スイープ 0x1A9278–0x1A9800 を実読) は、共有域メールボックス越しの発行手続きである:

- 記述子は共有域基底ポインタ **[0xAFE004] + 0x17F4** にある (第12段で同定した鍵ストア窓 +0x1824 と同じ共有域基底で、それに隣接する)。欄は +0x0C (コマンド/状態)、+0x10 (入力語)、+0x14 (結果語)、+0x20/+0x28 (状態ビット)。
- 手続き: +0x10 へ 1 を書き、+0x20/+0x28 の状態ビットの遷移をポーリングで待ち (ドアベルとしてタグ値 0x0B57AC1E と pcl を相手方スロットへ書く、第11・12段で見たのと同型の通知)、+0x0C へフラグを書いて完了 (+0x0C が 0 へ戻る) を待ち、**結果語 +0x14 を読んで出力 [i] へ格納する**ことを 4 語分繰り返す。最後に +0x0C へ 0x10 を書いて完了を待ち、カウンタを進めて戻る。
- FW 側から渡される入力は個数とフラグのみで、**素材となる入力バイト列は存在しない**。16 バイトは相手側 (共有域を挟んだエンジン/セキュリティ処理系) が生成して結果語へ返すものである。

したがって KO +0x154 の値は、FW コード内の導出でも、ホスト供給でも、OTP 読み出しでもなく、**エンジン側の生成値**である。生成が真の乱数か、エンジン内部のデバイス鍵からの決定的導出かは、相手側の実装 (主 FW イメージの外) に依存し、本イメージからは判定できない。

#### 4.2.5 コマンド 0x11 のハンドラ `0x1536B8` と導出ヘルパ `0x15364C`

- コマンド内の長さ欄 (コマンド +0x30 の BE16 等) の検査後、`FUN_001553E0(セッション+0x7B14, …)` でデータを収め、応答 (コード 0x12) をセッション +0x4000 に組む。応答にはセッション +0x7C98/+0x7C9C の長さとデータ、コマンドの一部が入る。
- 実行時グローバル素材 (アドレス `0x566708` から 16 バイト) をセッション +0x5C2C へ複写し、導出ヘルパを 2 回呼ぶ: `FUN_0015364C(KO+0x54, セッション+0x5C2C, 1)` と `FUN_0015364C(KO+0x64, セッション+0x5C2C, 2)`。
- 導出ヘルパ `0x15364C(宛先, 素材16バイト, 種別)`: 0x40 バイトのブロックをゼロ初期化し、素材 16 バイトと種別バイト (ブロック末尾寄り、オフセット 0x1F) を収め、ハッシュ `0x1EFC2C` (第16段で SHA-1 類似と構造推定したもの) を 0x20 バイト入力で回し、出力の先頭 16 バイトを宛先へ格納する。すなわち **KO +0x54/+0x64 は「グローバル素材 ‖ 種別」のハッシュ導出値**である (KO +0x5C は §4.3.2 の登録で使われる、この導出ブロックの近傍欄である)。

#### 4.2.6 コマンド 0x13 のハンドラ `0x153C8C` — 状態欄 +0x0C の書き手

- 状態 (KO +0x0C) のビット 0 が立っていない場合は、応答 (コード 0x14、状態コード 4) を組んで即座に戻る。
- ビット 0 が立っている場合: `FUN_001559BC(コマンド+0x10, セッション+0x4800, 0x100000, *(KO+0x1A8))` で大きな転送/復号系の処理を行い、セッション +0x4800 と コマンド +0x20 の **16 バイトを照合** (`FUN_002ACE5C`) する。一致した場合に限り **KO +0x0C にビット 1 を立て、ビット 2 を落とす**。応答コード 0x14 に結果 (一致 0 / 不一致 3) を載せる。

すなわち第16段で未同定だった状態欄 +0x0C の書き手の一つは本ハンドラであり、書込みは「ビット 0 が立った状態での 16 バイト照合の成功」という条件付きである。+0x0C の他のビットの書き手は本段の実読範囲では未同定。

#### 4.2.7 コマンド 0x21 のハンドラ `0x154A10` と、他のモードのワーカー

- `0x154A10` (コマンド 0x21): コマンドデータを局所へ複写し、`FUN_001557FC` でセッション側の状態 (+0x7BD4/+0x7BD8、+0x7C60/+0x7C64) を使う処理を行い、応答 (コード 0x22) を組む。**KO の素材欄への書込みは無い。**
- 他モードのワーカーはディスパッチャ本体までを実読した: 0x200 → `0x16AE34` (KO +0x28 の副モード語で 1〜0x22 のハンドラ群へ振り分け。KO +0x30 への状態格納あり)、0x10000 → `0x26FB7C` (同様に副ディスパッチ)、0x20000 → `0x1666E4` (KO +0x28/+0x30/+0x368 への状態格納あり)。いずれもディスパッチャ本体に素材欄への書込みは無いが、配下のハンドラ群は全数実読していない。
- 0x1000000 → `0x156C04` は AKE セッション文脈 (セッション +0x10C20) を直接操作する処理で、静的リスト (ビュー 0x3D35E0 / 0x3D3618) と関数ポインタ表 (0x3D34E0、セッション +0x10CD0 で添字) により AKE メッセージ処理へ振り分ける。本体 (ディスパッチャ部) の実読範囲では KO 素材欄への書込みは無く、読みは KO +0x28 と +0x48 のみ。表の先の AKE ハンドラ群 (第6・7段の gen_kauth / setexchgkey の系) は本段では個別実読していない。

#### 4.2.8 実行時グローバル素材 `0x566708` / `0x566768` の出所

コマンド 0x11 が使う 16 バイト (アドレス `0x566708`) と、コマンド 0x15 が使う 16 バイト (`0x566768`) は、いずれもイメージ内では **全ゼロ (BSS)** であり、実行時に値が入る領域である。Ghidra 参照マネージャの範囲では、両アドレスへの参照は読みのみ (0x566708 は `0x1536B8` から、0x566768 は `0x153DB8` から各 1 件) で、書込み側の直接参照は存在しない。計算アドレス経由の書込み (基底 + オフセット) の可能性が残るため、**書き手は未同定**とする (範囲: 両ビューでの参照 census)。

#### 4.2.9 未同定のまま残った書き手 (範囲明記)

本段の実読範囲 (タスク本体とその作業呼出し、能力 0x20 のワーカーと 4 ハンドラ、生成・導出ヘルパ、他モードのワーカー本体、drmctrl_open) では次を同定できなかった:

- KO の blob 欄 **+0x1E0/+0x1E4** (能力 0x20 で `0x261260` が読む) と **+0x38C/+0x390** (能力 0x200) の書き手。候補として他モードのワーカー配下のハンドラ群と、AKE ハンドラ群が残る。
- 能力フラグ **+0x10** の書き手 (ディスパッチャの振り分け条件として読まれるのみ)。文脈生成側 (drmctrl_open の呼出し元) の可能性が残る。
- KO **+0x2C** (ストリーム文脈ポインタ) の書き手。ストリーム open/束縛側の可能性が残る。
- AKE セッション文脈から KO 素材欄への複写は、本段の実読範囲には存在しない。AKE 素材はセッションオブジェクト側に留まる (第6・7・16段と整合)。

### 4.3 入口 (3): +0x4000 のパケット宛先

#### 4.3.1 コマンド応答の経路 (同定)

セッション +0x4000 は 2 種類の書込み先である: (a) 束縛時の暗号セットアップパケット (`0x154594` が構築、第16段)、(b) §4.2 のコマンド処理の応答パケット (構築子 `FUN_00154960(バッファ, 応答コード, 状態)`、応答コードは 0x12/0x14/0x16/0x22)。

(b) の宛先は同定できた: ワーカーは出力引数で (応答ポインタ = セッション +0x4000、応答長) を返し、`0x2624E4` が `FUN_00305B78(要求文脈, KO, 応答ポインタ)` を呼ぶ。`0x305B78` の実読結果:

- 経路 A (フラグセル `_DAT_00AFEB6C == 1` の場合): 転送オブジェクトを確保し、記述子 (要求文脈の +0x18/+0x1C、長さ、種別 0x10000 等) を組んで、応答バッファへのポインタと記述子を転送機構 `FUN_0022DF08` へ渡し、完了コールバック `0x2622F4` 付きで `FUN_002EC4C4` へ投入する。
- 経路 B (それ以外): 通信オブジェクト (先頭に応答ポインタ、長さ | 0xA1000000、KO +0x10 のモード語、KO +0x24 のチャネル語等を格納) を組み、主 FW の SCRAMBLER 送信ヘルパと同じ `FUN_002EB7B4` で投入する。モードが 0x200 の場合は KO +0x3D0 の 0x20 バイト (モード 0x200 の open ハンドラが文脈へ複写した欄、第16段) がパケットへ埋め込まれる。

すなわち応答の読み手は、このセッションコマンドプロトコルの要求元 (通信オブジェクト/転送の先) であり、FW 内では +0x4000 を直接読むコードを経由せず、ポインタと長さが記述子へ載って送出される。

#### 4.3.2 束縛時パケットの呼出し側 (同定) と読み手 (未確定)

暗号セットアップ `0x15490C` の呼出し側として、束縛 `0x261B7C` (第16段) のほかに、タスク側の `0x262C38` を同定した。`0x262C38(ストリーム文脈+0x825C のアドレス, 値)` の実読結果:

- ストリーム文脈 +0x8268 (束縛済みフラグ) が 0 で、かつ KO の能力 (+0x10) が 0x20 の場合にのみ、`FUN_0015490C(KO, 欄アドレス, &出力, &長, …)` を呼んでパケットを構築させる。
- 続いて `FUN_002E8690(ストリーム文脈+0x8260 の語, 0, KO 先頭語, 2, KO+0x5C)` で登録を行い、フラグ +0x8268 を 1 にする。登録の引数には §4.2.5 の導出ブロック近傍 (KO +0x5C) が含まれる。
- タスクループからは、ストリーム文脈 +0x8270 のハンドルに対する `0x2EAA28` の戻り値が非ゼロのときに呼ばれる (遅延束縛)。

パケットポインタは `0x15490C` の出力引数で `0x262C38` の局所へ返るが、その後の登録 (`0x2E8690`) の引数にはポインタ自体は含まれない。+0x4000 を直接読む命令は本段の実読範囲 (タスク一式、束縛、送信関数) には無く、**読み手は登録先のエンジン/ストリーム機構側であるという解釈**に留まる (範囲明記つき未確定)。

#### 4.3.3 タスクループの補助関数

- `0x260EF8(KO, ストリーム文脈)`: ストリーム文脈 +0x8270 のハンドルに対する取得/設定 (`0x2E99D8` / `0x2EA270`) と、束縛済みフラグ +0x8268 の 0 クリアを行う、状態リセット系の補助関数。
- `0x26290C(KO+4, 2)` と `0x262D94(KO+4, …)`: KO +4 を基底とするポートに対する受信/待機と通知のラッパ対。いずれも本体はチェックポイント記録の後に環境プリミティブへ尾部接続する形で、細部の意味論は本段では未実読である。ディスパッチャ `0x2624E4` の前後での呼ばれ方 (処理前の待機、処理後の完了通知) から役割を位置づけるに留める。

### 4.4 入口 (4): 余力項目

- 文脈 +0x49C/+0x4B4 の消費者: 本段の実読範囲では追加の同定はできなかった。第16段で確認した +0x4B8 の消費者 `0x20D918` が現時点の到達点のままである。なお隣接欄 KO +0x368 (= 文脈 +0x4B0) は、モード 0x200/0x20000 のワーカーが状態/フラグ語として読み書きすることを本段で確認した (§4.2.7)。
- ハンドラを持たないモード (0x100000/0x200000) の close 側スロット解放と、`0x2629F4` の解放側 (第3引数 1) の呼出し元: 本段では追跡しておらず、未同定のまま残る。

## 5. 残件

1. **エンジン側の生成機構**: コマンド 0x15 で KO +0x154 へ入る 16 バイトの生成が、乱数かデバイス鍵導出かは主 FW イメージからは判定不能。相手側 (エンジン/セキュリティ処理系) の実装領域の解析か、実機での実験系の問い。
2. **実行時グローバル素材 `0x566708` / `0x566768` の書き手**: 参照 census では読みのみ。計算アドレス経由の書込みを追う必要がある。
3. **blob 欄 (+0x1E0/+0x1E4、+0x38C/+0x390)、能力 +0x10、KO +0x2C の書き手**: 候補は他モードのワーカー配下のハンドラ群、AKE ハンドラ群 (関数ポインタ表 0x3D34E0 の先)、文脈生成側。
4. **他モードのワーカー配下のハンドラ群の全数実読**: 0x200 / 0x10000 / 0x20000 はディスパッチャ本体まで。残件 3 と一体。
5. **+0x4000 の束縛時パケットの直接の読み手**: 登録 (`0x2E8690`) の先のエンジン/ストリーム機構側。本段の範囲ではポインタ渡しの同定まで。
6. **生成サービス `0x3B4ED0` のローカル実行路 (0x3B5856 起点)** と、ポートラッパ `0x26290C` / `0x262D94` の細部: いずれも未実読。タスクへの引数受け渡しはマーシャリングレイアウトとタスク本体側のフィールド使用の整合で確定しており、実読は補強位置づけ。
7. 入口 (4) の残り: 文脈 +0x49C/+0x4B4 の消費者、ハンドラを持たないモードの close 側解放。

## 6. 方法・素材メモ
