## 2. 入口 (1): 状態ブロック +0x8B0/+0x8B8 の書き手

### 2.1 前提の再整理: ハンドルは主 FW (proc0) が作る

GPL ドライバ一次資料 (開発側リポジトリの GPL ソースツリー `xcodedriver_src/Kernel_Src/`、以下同様) でホスト→FW の配送先を確認した:

- OPEN_STREAM: `kdrv/drv/txc_open_ts.c:2584` で `procIdx = 0`
- CTRL_STREAM: `kdrv/drv/txc_control.c` の各送信部で `procIdx = 0`
- OPEN_GENERIC_STREAM: `kdrv/drv/txcdev.c` (`txc_open_generic_dev`) で `procIdx = 0`
- SCRAMBLER: `kdrv/drv/txc_scrambler.c:434` で CUST4_BUILD 時 `procIdx = 6` (§3.7)

すなわちストリームハンドル (状態ブロックを含む構造) は主 FW 側で生成され、proc6 (第2 FW) はホストから渡されたハンドルを共有メモリ上のポインタとして使う。書き手の候補は主 FW の open/設定経路が本命であり、第12段までの探索 (第2 FW 内) で見つからなかったことと整合する。

### 2.2 主 FW 側の実読

**巨大関数 `0x23FFC8`**: 第5–7段で言うストリーム文脈構築 (0x1E18C バイトの文脈) と open 本体 `0x24A7E4` は、Ghidra 上では単一の巨大関数 `0x23FFC8` (本体 0x23AB6E–0x251D87) に融合している。本段でそのデコンパイル全域を走査した結果:

- オフセット **+0x8B0 への言及は皆無**。
- +0x8B4/+0x8B8 への言及は、状態機械の case 0x11 分岐周辺の AACS 素材文脈でのみ現れる (後述の `0x261260` 呼出しと、0xBC バイト blob の構築部)。blob 構築部では `*(ctx+0x8B4)` を長さとして `ctx+0x8B8` から素材を複写し、blob のバイト 6 に `*(ctx+0x8B4) + 0x1A` を書く。

**`0x261260` (本段で新規実読)**: 巨大関数の case 0x11 分岐 (0x24E7B4) からのみ呼ばれる。処理は:

- `KO = *(*(第1引数) + 0x825C)` とする鍵オブジェクト KO を取る。
- KO のフラグ語 `KO+0x10` の bit 0x20 がセットなら、素材 = `KO+0x1E4`、長さ = `KO+0x1E0`。
- bit 0x20 がクリアで bit 0x200 がセット、かつゲート語 `*(第1引数 + 0x81D0)` が非ゼロなら、素材 = `KO+0x390`、長さ = `KO+0x38C`。
- それ以外は長さ 0 (または失敗 1 を返す)。
- 第2引数 (呼出し側で `ctx+0x8B4` のアドレス) へ長さを書き、第3引数 (`ctx+0x8B8`) へ素材を複写する (`0x2ACEB0` = memcpy 相当)。

つまり主 FW には「鍵オブジェクトから (長さ, 素材) を +0x8B4/+0x8B8 へ書く」コードが実在する。ただし、この ctx が SCRAMBLER ハンドラの言うハンドル構造と同一オブジェクトかは、本段では確定できなかった。巨大関数は複数の構造を扱う融合体であり、case 0x11 分岐でレジスタが保持するオブジェクトの同一性 (ストリーム文脈そのものか、その内部の AACS 文脈か) を静的に固定できていない。オフセットが一致することだけをもって「+0x8B4 は CW2 スロットであると同時に素材長でもある」とは言えないため、本関数を +0x8B4/+0x8B8 の書き手としては数えない (候補として記録するに留める)。

### 2.3 第2 FW 側の実読

**ストリーム状態初期化 `0xC824A4`**: 全体を実読した。wrapper_task のメイン群 (`0xC4D63C` / `0xC4DB98` / `0xC4E4FC`) から関数ポインタとして渡される、プロセッサ単位のストリーム管理文脈の初期化であり、0x16178 バイトの文脈の memset や登録処理を含む。+0x8B0 台への言及は無い。個別ストリームのハンドル生成はここではない。

**AACS ヘルパ `0xBF9D4C`**: 全行を再実読した (第12段の記録の裏付け)。+0x8B0/+0x8B8 は読むのみで、書き手ではない。書くのは +0x8B4 (← +0x8B0 の複写)、+0x8BC (要求の IV 欄からの素材複写)、+0x8EC/+0x8F0 (ゼロ化)。呼出し元は xref census で SCRAMBLER ハンドラ `0xBF894C` 内の 0xBF8A04 の 1 箇所のみ。セッションオブジェクトポインタ +0x8F8 の書き手も本ヘルパ内には無く、同じ残件に属する。

### 2.4 census の方法と限界 (実測)

本段でスカラ走査の限界を実測で確認した。既存の `ScalarScan10.java` (命令のスカラオペランドと参照を走査) と、本段で追加した `DispScan13.java` (全オペランドオブジェクトの Scalar を走査) の双方で、主 FW の +0x8B0/+0x8B4/+0x8B8/+0x8BC を走査した結果、ヒットは定数としての 0x8B4 の書込み 1 件と `add r25, r17, 0x8b4` の 1 件のみだった。巨大関数内に実在する +0x8B4/+0x8B8 アクセス (デコンパイルで確認済み) は**どちらの走査でもヒットしない**。理由は、ARC の ld/st 変位が Ghidra の命令モデルでスカラオペランドとして公開されないこと、および実際のアクセスが「基底 +0x20 を取ってから +0x898」のような分割アドレッシング (0x24E7A8 の `add r2, r13, 0x898`、r13 = ctx+0x20) で行われることである。

したがって、変位ベースのアクセスに対する全数 census は本段の方法では成立せず、「イメージ内に書き手が存在しない」という全数否定はできない。否定できるのは実読範囲についてのみである。

### 2.5 判定

- +0x8B0 の書き手: 実読範囲 (両 FW の SCRAMBLER ハンドラ、AACS/IVDR ヘルパ、主 FW open 経路巨大関数、第2 FW `0xC824A4`) には存在しない。範囲外は §2.4 の理由で未確定。
- +0x8B8 の書き手: 同上 (素材バッファとしての書込み候補 `0x261260` は構造同一性が未確定)。
- 「ハンドル生成時に構造全体がゼロ初期化され、+0x8B0/+0x8B8 はスロット 0 を指し続ける」という仮説は、現在の全実読と矛盾しない (ただし未証明であり、判定としては採用しない)。

## 3. 入口 (2): 主 FW 並行実装 `0x22F9E0` の位置づけ

### 3.1 ハンドラ本体の実読

主 FW の SCRAMBLER ハンドラ `0x22F9E0` (ルータ `0x22FC54` はその一部) を実読した。構造は第2 FW 実装 `0xBF894C` と同型である:

- 要求を `handle+0x7F4` へ 0xBC バイト逐語ステージング (`0x2ACFB0` = memcpy 相当)。
- 検証 (エラーコード体系も同型)、モード別処理、鍵ストア投入、記述子構築、投入 `0x2EB7B4 (handle, 記述子, コールバック 0x2CAF24)`。
- AACS 分岐は等価物 `0x230E34`、IVDR 分岐は等価物 `0x23237C` が担う (§3.6)。
- 呼出し元 (xref) は主 FW 内の 2 箇所 (0x3729CC、0x2C3808)。包含関数は Ghidra で未同定 (孤児コード領域) で、FW 内部の直接呼出しであることだけが分かる。

### 3.2 選択ロジックの確定 (docs/25 §3.4 訂正の独立裏付け)

選択部 (0x22F9E0 内) の実読で、スロット選択値の決定規則を確定した:

- IV スロット: SF bit6 (IV_AS_INDEX) が**セットなら要求バイト** `[req+0x4C]` (IV_seed[0]、それ自体がスロット番号)、**クリアなら状態ブロックの語** `[handle+0x8B8]`。
- CW スロット: SF bit5 (CW_AS_INDEX) がセットなら要求バイト `[req+0x34]` (control_words[0])、クリアなら状態ブロックの語 `[handle+0x8B0]`。
- CW2 スロット: SF bit5 がクリアなら状態ブロックの語 `[handle+0x8B4]`。セット時はモード {0x12, 0x13, 0x1B, 0x14, 0x15, 0x1A} では要求バイト `[req+0x6C]` (control_words2[0])、それ以外のモードでは状態ブロックの語 `[handle+0x8B4]`。

これは第12段が docs/26 §9 で示した訂正 (SET → 要求バイト / CLEAR → 状態語) と一致し、主 FW 実装から独立に裏付けられた。なお docs/25 §3.4 の本文は訂正前の極性のまま残っていた (第12段のコミット `a8ef031` は docs/25 を変更していないことを `git show --stat` で確認)。本段で docs/25 §3.4 の本文を修正した。

### 3.3 投入 `0x2EB7B4`

実読範囲では: 通信オブジェクトのプールは共有セル `[0xAFEB68]` から取る (第2 FW 実装の `0xC5C344` と同一セル)。記述子チェーンを走査して形式を検証する (エントリ語 [2]/[3] のゼロ検査、語 [4] の bit31 = 終端、bit 0x80000 = 拡張形式で歩幅が変わる)。Ghidra のデコンパイルは末尾 (実行開始の書込み) が noreturn 誤判定で切断されており、実行開始の詳細は未読である (範囲はここまで)。

### 3.4 コールバック `0x2CAF24` — 第2 FW 実装との差異

- スピンロックは共有セル `[0xAFEB10]` (第2 FW の完了処理と同一セル) を使い、`handle+0x48` の bit3 をクリアする。
- ハンドルの状態語 `handle+0x810` が完了対象外の値集合 {0x13, 0x1B, 0x10, 0x11, 0xE, 0xF, 0x18, 0x19, 0x16, 0x17} に含まれない場合、**CMD2_SCRAMBLER_DONE (FN=38) の応答オブジェクトを自前で構築する**: 確保関数 `0x22BECC (0x26)` で通信オブジェクトを取り、ハンドルの +0x18/+0x1C、+0x7FC/+0x800 (ステージング済み要求の +0x08/+0x0C)、+0x804/+0x808、+0x80C、+0x810、+0x814、+0x818 を複写して、`handle+0x48` に 0x20000 を立てて送信側へ渡す。

第2 FW 実装のコールバック `0xC4AD58` は「次の通信オブジェクトへのチェーン」が役割で、ホストへの完了応答は proc0 側の仕事だった。主 FW 実装は proc0 上にあるため、完了応答の構築まで自身で担う。これが両実装の実読で確認できた実質的な差異である。

### 3.5 投入ヘルパ `0x200E68` / `0x203274`

- 両ヘルパとも先頭でスロット番号の範囲検査を行い、**0x7F を超えるスロットはエラーカウンタを増やして戻る** (128 スロットは主 FW 側でも確定)。
- 呼出し形態は第2 FW の `0xBCE950` / `0xBCED1C` と一致する (ハンドラ側の呼出しパターン: AES 系は (スロット, バッファ)、TDES 系は (スロット, 要求+オフセット, 要求+オフセット))。
- ただし、共有域の窓 (+0x1824/+0x1828/+0x182C) への書込み命令そのものは、チェックポイント原語 `0x3B8A64` の noreturn 誤判定で関数本体が断片化しており、Ghidra が取り込まなかったブロック側にあるため**本段では未読**である。主 FW のスカラ走査で 0x1824/0x1828/0x182C は 0 件だったが、§2.4 の通り変位はスカラに現れないため、窓の同一性については肯定も否定もできない (未確定)。

### 3.6 AACS / IVDR 等価物

- **AACS 等価物 `0x230E34`**: 第2 FW の `0xBF9D4C` と同型であり、後半まで実読できた。セッションオブジェクト (`handle+0x8F8`) の関数ポインタ +0x4CC (モード 0xC) / +0x4C8 (モード 0xD) を (オブジェクト, 要求+0x88, `[handle+0x8B0]`) で呼び、成功時に `handle+0x8B4 := [handle+0x8B0]` を書く。第2 FW 側はこの後半が未実装命令でデコンパイルが切断されていたため、本段の等価物実読がその補完になる (§5)。
- **IVDR 等価物 `0x23237C`**: `[handle+0x8B8]` と素材欄 +0x8BC を読み、`0x200E68` でスロット `[handle+0x8B0]` へ投入し、記述子の +0x840 へコマンド語 `(IV スロット << 24) | [handle+0x8B0] | 0x80` を書く。第2 FW の `0xBFA258` と同型。スピンロック `[0xAFEB10]` も共用する。

### 3.7 ロード経路と配送 (GPL 一次資料)

- ビルド条件: `kdrv/inc/drvautoconf.h:37` に `#define CUST4_BUILD 1` (GPL 原本・開発側作業コピーの双方)。`txc_scrambler.c:433–437` で、CUST4_BUILD のとき SCRAMBLER の `procIdx = 6`、そうでないとき 0。
- FW ロード: `Os_Shared_Funct_IF.c` が主 FW 配列 `firmware_data` (製品ビルドでは暗号化版 `fwoutput_data`) を `pmipscode` に、第2 FW 配列 `fm_second_data` (同 `fwoutput_second_data`) を `second_fm_ptr` に接続し、`mips.c` の `Down_Load_Embedded_Mips_Prog` / `Down_Load_Embedded_Second_Mips_Prog` がフレームバッファへダウンロードする。第2 FW のオフセットは `DEFAULT_SECOND_FW_OFFSET = 0x00B00000` (`commsdk/include/mipshost.h:61`)。
- プロセッサ分担: 主 FW はホスト対向の proc0 系、第2 FW はメディア処理プロセッサ群 (docs/24 で同定した wrapper_task の IDENTITY 分岐 id3/id4/id6)。

### 3.8 判定

**製品構成でホストの SCRAMBLER コマンドを受け取るのは第2 FW 実装 `0xBF894C` で確定** (CUST4_BUILD の一次資料 + procIdx=6 の配送)。主 FW 実装 `0x22F9E0` は、procIdx=0 で配送される文脈 (非 CUST4 ビルド) と、主 FW 内部からの直接呼出し (呼出し元 2 箇所、文脈は未同定) で動く同型実装であり、完了応答 (FN=38) の構築まで担う点が異なる。両実装は共有セルのプール `[0xAFEB68]`・スピンロック `[0xAFEB10]`・状態ブロックのレイアウトを共有する。

## 4. 入口 (3): SECUREDTS / GENERIC 経路との対応づけ

### 4.1 配送とパケット (GPL 一次資料)

- OPEN_GENERIC_STREAM (mhcmd FN=25) は procIdx=0 = 主 FW 宛 (txcdev.c)。パケット `cmd_open_generic_stream` (mipshost.h) とドライバ API の `param_opengeneric` (drv_if.h) の双方に**鍵欄は無い**。あるのは generic_mode、DMA バッファ情報、card_type、共有入力バッファ、`generic_session_handle` (AACS 認証で交渉したセッション鍵へのハンドル)、drmflags、dma_direction、scrambling_ctrl_flags、`rng_data[32]` (DTCP 用予約) である。
- 録画時の実測では、OPEN_GENERIC パケットはゼロ初期化後に generic_mode / req_size / 共有入力バッファサイズのみが刻まれ、drmflags / scrambling_ctrl_flags / rng_data は全て 0 (docs/02 §10.2)。
- SECUREDTS は専用の mhcmd を持たず、OPEN_STREAM (FN=8、procIdx=0) のペイロード内のストリーム種別で表される。OPEN_STREAM ペイロードはスロット番号とモードのみを含み、鍵素材は含まない (docs/13 §5.1)。
- 参考: SCRAMBLER_CRI (FN=40) は procIdx=0 (txc_scrambler.c:523) で、SCRAMBLER (FN=37) とは配送先が異なる。

### 4.2 FW 側ハンドラの同定試行

主 FW 内の GENERIC 関連文字列 — ログ文字列 "== open Generic stream mode ==" (0x2DD954)、名前 "GENERIC_STRM" (0x2E3BE4)、"GENERIC" (0x2EB078) — を起点に探索したが、いずれもデバッグ表示用の名前・ログ文字列であり、Ghidra 上の xref は 0 件、32 ビットリトルエンディアンのポインタ値としての出現も全イメージ検索で 0 件だった。文字列参照が計算アドレス経由である主 FW の性質 (第5段) のため、この起点では FN=25 のハンドラに到達できなかった。**GENERIC セッションの FW 側ハンドラ同定は本段では未達 (未確定)**。SECUREDTS の FW 側鍵束縛については docs/13–15 の DRMCTRL 経路 (鍵オブジェクトの束縛) が既読範囲であり、本段での追加進展は無い。

### 4.3 §49 トークンの対応づけ (具体化できた範囲)

録画時の SCRAMBLER 呼出しの実測 (docs/02 §10.1: 4 セッション 12,081 呼出しの全数集計) と、本段までに確定したハンドラの規則を突き合わせると、トークンの行き先が具体化する:

- 録画時の呼出しは **mode 2 (AES_CBC_ENCRYPT)**、SF は 0x04 (NEW_CW) と 0x0C (NEW_CW | NEW_IV) のみ、**AS_INDEX ビット (0x20/0x40) は常にクリア**、IV_seed = 0、control_words2 = 0。
- 選択規則 (§3.2) により、この呼出しでの CW スロット = 状態語 `[handle+0x8B0]`、IV スロット = 状態語 `[handle+0x8B8]` である。**トークン自体にスロット番号は含まれない** (CW[0] がスロット番号を兼ねるのは AS_INDEX セット時のみで、録画経路は使わない)。
- ジャンプ表 #1 の合流構造 (docs/25 §3.4) により mode 2 の流れも NEW_CW 投入ブロックを通過し、**control_words の先頭 16 バイト (トークン本体 + カウンタバイトを含む) が、スロット `[handle+0x8B0]` 起点の 2 スロットへ逐語投入される**。NEW_IV のセグメントでは IV_seed 16 バイト (全ゼロ) がスロット `[handle+0x8B8]` 起点へ投入される。
- すなわちトークンの対応先は「SCRAMBLER 要求の control_words 欄 → 状態ブロックが指す鍵ストアスロット」であり、docs/02 §10 のモデルはこの形に具体化される。

E2 (docs/02 §12) の失敗との関係は、本段では次の 3 候補に整理されるに留まる (いずれも未判定):

- (i) エンジン内部でのスロット内容の変換 (第12段 §6 の未確定事項。FW イメージからは観測不能)。
- (ii) 投入が control_words 24 バイト中の先頭 16 バイトのみであること (docs/25 の実読)。エンジンが使う鍵が 16 バイトを超える場合、残りはスロットの既存内容に依存し、録画時と E2 再現時で差が出得る。
- (iii) `.dat` の暗号化そのものは GENERIC-AES セッション側の内部処理であり、録画時の SCRAMBLER 呼出しは別目的 (入力側の処理等) である可能性。GENERIC 側の鍵装填が未同定である以上、この可能性は排除できない。

### 4.4 判定

- SECUREDTS / GENERIC のセッション確立パケットに鍵文脈が無いことは、一次資料 (パケット定義) と実測 (docs/02 §10) の双方で確定している。鍵装填は確立後のコマンド (録画では SCRAMBLER) か、FW 内部状態のいずれかに限られる。
- GENERIC-AES セッションの鍵装填が鍵ストアスロット経由か、SCRAMBLER 経路と共有するかは**未確定** (FW 側ハンドラ未同定のため)。

## 5. 余力項目

- **AACS ヘルパ後半**: 第2 FW の `0xBF9D4C` はモード 0xC/0xD の分岐で Ghidra の未実装命令に当たりデコンパイルが切断されていた。本段で主 FW 等価物 `0x230E34` を実読し、関数ポインタ呼出し (+0x4CC/+0x4C8) から +0x8B4 書込みまでの後半が同型であることを確認した (§3.6)。第2 FW 側の後半の内容は、等価物経由で確認できた範囲で補完されたと扱う。
- **巨大関数 `0xBC3E58` の分岐先 census**: 未実施。残件のまま次段以降へ送る。

## 6. 残件

1. 状態ブロック +0x8B0/+0x8B8 の書き手 (実読範囲には無し。変位 census の方法限界により全数否定はできない)。セッションオブジェクトポインタ +0x8F8 の書き手も同枠。
2. 主 FW 投入ヘルパ `0x200E68` / `0x203274` の窓書込み命令の実読 (関数本体の断片化 — チェックポイント原語の noreturn 誤判定 — を解いてから)。
3. OPEN_GENERIC_STREAM (FN=25) の主 FW 側ハンドラ同定と、GENERIC-AES セッションの鍵装填経路 (E2 失敗の候補 (iii) の判定にも関わる)。
4. 巨大関数 `0xBC3E58` の分岐先 census。
5. エンジン内部での鍵の扱い (スロット内容をそのまま使うか内部変換があるか)。FW イメージからは原理的に観測不能で、実験系 (オラクル方式) の問いとして残る。
